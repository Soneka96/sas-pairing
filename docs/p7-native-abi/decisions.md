## P7-D-001 — Native Runtime, Handle, and Fatal Containment Unit

- **Inputs:** [P6-D-004](../p6-remediation/decisions.md#p6-d-004--native-panic-containment-policy) (native panic containment, including the P6.4.1 payload-disposal rule, item 14) leaves the exact containment unit to P7's handle design; [P6-D-002](../p6-remediation/decisions.md#p6-d-002--f-003-owner-session-policy) forbids any same-process accounting reset; the [P7 roadmap](../../roadmap/P7-native-abi.md) lists the mandatory handoff.
- **Decision (owner-selected):**
  1. **One runtime per OS process.** At most one sas-pairing native runtime is active per OS process. A second create while one is active returns `SAS_PAIRING_ALREADY_INITIALIZED` and does not replace it. Later increments may place several pairing authorities inside the runtime; P7.1 implements none.
  2. **The runtime is the fatal-containment unit,** and its fatal state is process-wide native ABI state. P6-D-004's "affected native context" is therefore the whole native ABI of the process.
  3. **Normal lifecycle:** process → `sas_pairing_runtime_create` → runtime handle → later P7 operations → `sas_pairing_runtime_destroy`. After a normal destroy a new runtime may be created in the same process, and it receives a new handle.
  4. **Caught panic → permanent fatal.** When the ABI's containment boundary catches a Rust panic, the process's native ABI state becomes permanently fatal: no new runtime or normal core operation can start (they return `SAS_PAIRING_FATAL` without entering the core), destroy stays allowed, and recovery requires restarting the OS process. There is no "clear fatal", "reset runtime", or registry-clearing API, in production or in tests.
  5. **Destroy is the cleanup path.** Fatal state does not prevent destroy. Destroy invalidates the handle first, then performs best-effort runtime destruction. It never clears fatal state, starts protocol work, creates fresh accounting, or re-registers an authority. After fatal + destroy, create still returns `SAS_PAIRING_FATAL` until process restart.
  6. **Opaque `uint64_t` handles.** `sas_pairing_runtime_t` is `uint64_t`; `0` is never valid. Handles are process-local and opaque: not pointers, network identities, security secrets, authority identities, or protocol identifiers. They come from one monotonic, process-lifetime counter and are never reused within one OS process, so a destroyed handle can never alias a later runtime. If the counter would wrap, creation fails closed (`SAS_PAIRING_HANDLES_EXHAUSTED`) instead of reusing a value. There is no generation-reset API.
  7. **Runtime creation is infrastructure only.** It does not call `TrustedAuthority::register`, consume an opportunity, acquire the authority OS lock, start a listener, create a ceremony, or generate protocol randomness. Authority lifecycle belongs to P7.2.
- **Why conservative:** P6-D-004 requires a caught panic to poison the context that owns the panicking core state, and P6-D-002 forbids any same-process reset of authority accounting. A process-wide fatal unit satisfies both directly: no handle juggling (destroy and re-create, a second runtime, re-registration) can reach fresh accounting after a panic, and no partially updated Rust state is used again. The cost (one fatal event disables the native ABI for the rest of the process) is accepted because a caught panic is a catastrophic internal failure, never an ordinary error.
- **Wire, cryptography, ceremony authentication, result semantics, deadlines, and accounting:** unchanged. P7 wraps the frozen candidate.
- **Status:** decided by the owner for P7.1, 2026-10-02; implemented in P7.1 (`core/src/abi`). The P6-D-004 exit test through a real core-entering ABI operation remains open until later P7 increments add one ([README](README.md#mandatory-p6-handoff)).

## P7-D-002 — Native Library Residency and Loader Lifetime

- **Inputs:** P7-D-001 states its guarantees (one runtime per process, handles never reused, fatal until process restart) for the OS process, but P7.1 stores that state in module statics of the loaded library image (`static PROCESS: AbiState` in `core/src/abi/mod.rs`; the core's authority registry is also a module static, `REGISTRY` in `core/src/lib.rs`). A module static lives exactly as long as the image that contains it. P7.1.1 measured this against the release DLL ([evidence](README.md#p711-evidence)): after `FreeLibrary` and a new `LoadLibraryW` of the same file, the handle counter and the runtime slot started over (the first handle was `1` again, even with the earlier runtime never destroyed), and two copies of the DLL under different paths each created a live runtime with handle `1` in one process. [P6-D-002](../p6-remediation/decisions.md#p6-d-002--f-003-owner-session-policy) forbids any same-process reset of authority accounting, and [P6-D-004](../p6-remediation/decisions.md#p6-d-004--native-panic-containment-policy) makes process replacement the only panic recovery.
- **Decision (owner-selected): supported loader invariant.**
  1. **Exactly one image.** Supported use has exactly one loaded sas-pairing native library image per OS process. A host must not load an independent duplicate (another path, filename, copy, or rename of the library).
  2. **Process-lifetime residency.** Once stateful ABI use begins, and no later than the first `sas_pairing_runtime_create`, that image stays resident until the OS process terminates. The host keeps its load of the library (its module handle or library object) for the rest of the process.
  3. **No unload or reload recovery.** None of these is supported, after stateful use and in particular after `SAS_PAIRING_FATAL`: `FreeLibrary` then `LoadLibrary`; `dlclose` then `dlopen`; `NativeLibrary.Free` then `NativeLibrary.Load`; loading the library from a copied, renamed, or alternate path; wrapper re-initialization that loads another image. After `SAS_PAIRING_FATAL`, the only supported recovery is an OS process restart.
  4. **Process-lifetime claims are conditional on this invariant.** Under the supported one-image, process-lifetime-residency loader invariant, the native ABI state has OS-process lifetime semantics: handles are never reused, fatal is permanent, and at most one runtime is active, for the life of the process. The implementation's storage stays module static; Rust statics do not outlive the unloading of their module, and a second image has its own. A host that breaks the invariant gets no uniqueness, singleton, or fatal guarantee across images.
  5. **Trusted in-process host.** The ABI is not a sandbox against code with arbitrary control over the process's loader. A caller that unloads the library or loads independent copies violates the ABI's preconditions and is outside the supported security contract. That is not a reset API, and the library does not try to detect it.
- **P6-D-002 connection.** From P7.2 on, the ABI will hold `TrustedAuthority` state, whose accounting (opportunity budget, START limiter and its clock, process-session state) lives in native module state. Unloading and reloading the library, or loading a second image, would give that image fresh module state, so under this decision neither is a supported way to obtain fresh opportunities, limiter history, or process-session accounting. This decision is the precondition that lets P7.2 carry P6-D-002 across the ABI. P7.1 itself holds no authority accounting. The per-account authority lock file excludes only concurrent ownership; it carries no accounting, so it is not relied on here.
- **P6-D-004 connection.** P6-D-004 requires caught panic → fatal native context → no same-process recovery → process replacement. A library reload is not process replacement, so it is not a supported panic recovery.
- **Enforcement (deliberately none in the library).** P7.1.1 adds no self-pinning (`GetModuleHandleExW` with `GET_MODULE_HANDLE_EX_FLAG_PIN`, `RTLD_NODELETE`), `DllMain` logic, named mutex, shared memory, file, registry key, or module enumeration, and no new status code. Pinning one image cannot stop a host from loading a separate copy, so it would suggest enforcement that does not exist; the wrappers are trusted local callers; and P8 and P9 own library loading, where the obligation is placed ([P8](../../roadmap/P8-dart-package.md), [P9](../../roadmap/P9-dotnet-package.md)).
- **Unchanged:** ABI version `1`, every signature and status value, and the wire, cryptography, ceremony authentication, result semantics, resource limits, deadlines, and process-session accounting implementation. P7-D-001 is unchanged; this decision states the loader condition its process-lifetime wording depends on.
- **Status:** decided by the owner for P7.1.1, 2026-10-03; normative in the [ABI contract](abi-contract.md#14-native-library-loading-and-residency) and the header.

## P7-D-003 — Authority Handles, Ownership, and Lifecycle

- **Inputs:** P7-D-001 makes the runtime the containment unit and anticipates several authorities inside it. P7-D-002 keeps one native image resident for the process, which is what lets module state carry process-session accounting. [P6-D-002](../p6-remediation/decisions.md#p6-d-002--f-003-owner-session-policy) keeps the opportunity budget and START limiter in the core's process session for each canonical authority (`REGISTRY` in `core/src/lib.rs`, never evicted), surviving release, drop, and re-registration. In the core, `TrustedAuthority::register` rejects an empty scope or one longer than `u32::MAX` bytes (`InvalidScope`), derives the canonical identity, acquires the OS lease, and creates or reactivates the process session; an active registration gives `AlreadyRegistered`, and an uncertain earlier release or a held runtime resource gives `OwnershipUncertain`. `TrustedAuthority::release` consumes the handle and ends the registration (`Busy` while another holder shares it); dropping the last holder ends it the same way.
- **Decision (owner-selected):**
  1. **Opaque handles.** `typedef uint64_t sas_pairing_authority_t;` with `SAS_PAIRING_AUTHORITY_INVALID = 0`. An authority handle is opaque, process-local, and non-zero; never a pointer, protocol identity, canonical authority identity, secret, or persistent trust material. It is valid only while the runtime that registered it owns it.
  2. **One handle namespace.** Runtime and authority handles (and later ceremony handles) come from the one monotonic process-lifetime `HandleCounter` of P7-D-001. No kind has its own counter, so each numeric value is issued once, to one kind: a runtime handle presented as an authority handle (or the reverse) names nothing and gives `SAS_PAIRING_INVALID_HANDLE`.
  3. **Never reused.** Values are never reused under the loader invariant of P7-D-002. Register A → H1, release H1, register A → H2 gives H2 ≠ H1. A handle names one ABI object lifetime (one active registration): not the authority's stable identity, and not its process session.
  4. **Reserve the handle, then enter the core.** Registration validates its raw arguments, then the fatal state and the runtime, then reserves the next handle value, then calls `TrustedAuthority::register`. On success the authority is installed under the reserved value. On a core error nothing is installed, the output stays `0`, the core's mapped error is returned, and the reserved value is burned: never issued and never reused. A burned value consumes no opportunity, resets no accounting, and creates no valid handle. Handle exhaustion fails with `SAS_PAIRING_HANDLES_EXHAUSTED` before the core is entered, so core state that could not receive a handle is never created, and no rollback path exists.
  5. **The runtime owns its authorities.** The runtime holds a map from authority handle to the real `TrustedAuthority`: no raw, leaked, or foreign pointer. Rust RAII stays authoritative: an authority's ABI lifetime ends only by removing it from that map. One runtime may own several authorities for different canonical scopes; the core's ownership rules decide each registration.
  6. **Release.** `sas_pairing_authority_release(runtime, authority)` removes the handle from the runtime first, then calls the core's explicit release and maps its result. The handle is invalid forever once the call returns, whatever the result: a core error (`Busy`, `OwnershipUncertain`) is reported and never restores the handle or creates a replacement. A second release gives `SAS_PAIRING_INVALID_HANDLE`. An uncertain release keeps its P6-D-002 meaning: registration of that authority fails closed for the rest of the process.
  7. **Status.** `sas_pairing_authority_status` reads the core's own status path (`CeremonyExecutor::status`) and translates it into `sas_pairing_authority_state_t` (`INVALID = 0`, `READY = 1`, `BUSY = 2`, `EXHAUSTED = 3`) plus a remaining count (for `READY`; `0` otherwise). The Rust `Status` layout is never exposed. P7.2 adds no canonical-identity export: no consumer needs it yet.
  8. **Runtime destroy cascades.** Destroying a runtime removes the runtime handle, which invalidates every authority handle it owns, then drops the owned `TrustedAuthority` values (best-effort cleanup through the core's own `Drop`, which records an uncertain lease release as P6-D-002 requires), and returns as before. Callers need not release authorities first. There is no aggregate error object. Destroy never resets fatal state, creates accounting, or does ceremony work. A panic during destroy is contained centrally (fatal, `SAS_PAIRING_FATAL`), and the runtime is never reinserted.
  9. **Fatal.** Register and status are normal, core-entering operations: after fatal they return `SAS_PAIRING_FATAL` without entering the core. Release, like runtime destroy, is cleanup and stays allowed. Cleanup never clears fatal, creates an authority, refreshes accounting, resets the runtime, or starts ceremony work.
  10. **Validation precedence.** For normal authority calls: (1) structural raw-argument validation (null, misaligned, impossible length, wrapping or overlapping ranges); (2) output slots set to their invalid values; (3) the process fatal state; (4) the runtime handle; (5) the authority handle, where applicable; (6) the core; (7) the mapped core result. Memory-safety errors are never overridden by core errors, and after fatal no normal operation reaches the core. Release, as cleanup, skips step 3.
  11. **Concurrency.** Runtime destruction serializes with stateful authority operations: in P7.2 every authority operation, and destroy's cleanup, runs while holding the runtime slot's mutex. A call admitted against a live runtime finishes; once destroy has taken the runtime out of the slot, no new authority operation is admitted (`SAS_PAIRING_INVALID_HANDLE`). There is no use-after-free, no authority mutation after its runtime is gone, and no lock-order cycle: the ABI slot is always taken before the core's registry and session locks, and the core never calls back into the ABI. Later bounded ceremony or network operations may refine the locking while keeping these lifecycle semantics.
  12. **Process session versus handle.** Neither release, re-registration, runtime destroy, nor a new runtime ends or refreshes an authority's process-session accounting. They end only a registration (its OS lease). Under P7-D-002 one native image stays resident for the process, so `REGISTRY`, the opportunity budget, and the START-limiter history cannot be recreated through any supported loader operation. That is a supported-host invariant, not protection against hostile in-process code.
- **Why:** One counter makes kind confusion and stale reuse structurally impossible. Reserving the handle before entering the core removes the only hard failure case (core state without a handle) with no rollback logic. Owning the real `TrustedAuthority` keeps the reviewed RAII lifecycle authoritative instead of re-implementing it. Holding the runtime slot across short authority operations gives destroy a simple, race-free meaning without executors, worker pools, or lock-free registries.
- **Unchanged:** the core's authority semantics (scope rules, canonicalization, OS ownership, process session, budget, START limiter, release uncertainty), ABI version `1`, every earlier status value and signature, and the wire, cryptography, ceremony, deadlines, and P6 decisions.
- **Status:** decided by the owner for P7.2, 2026-10-03; normative in the [ABI contract](abi-contract.md#15-authorities); implemented in `core/src/abi/authority.rs` and `core/src/abi/runtime.rs`.

## P7-D-004 — Stable Core Error Mapping

Not to be confused with P6-D-004 (native panic containment).

- **Inputs:** the core's `Error` enum (`core/src/lib.rs`) has eleven variants: `InvalidScope`, `AlreadyRegistered`, `OwnershipUnavailable`, `UnsupportedPlatform`, `OwnershipUncertain`, `Busy`, `MissingAuthorization`, `StaleAuthorization`, `Exhausted`, `Terminated`, `ResourceLimited`. The P7.1 contract reserves 100–199 for authority, resource, and core errors and 200–299 for ceremony and protocol errors, and forbids exposing Rust discriminants.
- **Decision (owner-selected):**
  1. **Frozen values.** `SAS_PAIRING_INVALID_SCOPE = 100`, `SAS_PAIRING_ALREADY_REGISTERED = 101`, `SAS_PAIRING_OWNERSHIP_UNAVAILABLE = 102`, `SAS_PAIRING_UNSUPPORTED_PLATFORM = 103`, `SAS_PAIRING_OWNERSHIP_UNCERTAIN = 104`, `SAS_PAIRING_BUSY = 105`, `SAS_PAIRING_EXHAUSTED = 106`, `SAS_PAIRING_RESOURCE_LIMITED = 107`; `SAS_PAIRING_MISSING_AUTHORIZATION = 200`, `SAS_PAIRING_STALE_AUTHORIZATION = 201`, `SAS_PAIRING_TERMINATED = 202`. `OK = 0`, `INVALID_ARGUMENT = 1`, `INVALID_HANDLE = 2`, `ALREADY_INITIALIZED = 3`, `HANDLES_EXHAUSTED = 4`, and `FATAL = 900` are unchanged; nothing is renumbered.
  2. **One explicit mapping.** `abi::status::map_core_error` is the only translation: an exhaustive `match` with one arm per variant, no wildcard, no `as` cast, no discriminant, and no `Debug` or `Display` string matching. A new core variant therefore does not compile until P7 assigns it an ABI value.
  3. **The meaning is the core's.** The ABI translates and never reinterprets: `OWNERSHIP_UNAVAILABLE` is not an authentication failure, `RESOURCE_LIMITED` is not compromise and spends or refunds no opportunity, `EXHAUSTED` is not a protocol rejection, and distinct core errors are never collapsed into one generic code. The contract documents each value with the core's meaning.
  4. **Ceremony values frozen now.** The 200-range values are frozen now because the mapping must be exhaustive; P7.2 exports no operation that can return them.
- **Unchanged:** the core `Error` enum and its meanings; ABI version `1`. Wrappers still treat every non-zero value, known or not, as failure.
- **Status:** decided by the owner for P7.2, 2026-10-03; normative in the [ABI contract](abi-contract.md#3-status-codes); implemented in `core/src/abi/status.rs`.

## P7-D-005 — Hosting Context Ownership and Router Lifetime

- **Inputs:** the reviewed core hosts one pairing authority through a crate-private `Router` (`core/src/router.rs`): `Router::new(executor)` takes a `CeremonyExecutor` clone of the authority, the router owns every run routed through it, and dropping it drops those runs, whose own cleanup releases their slots, reservations, and guard. Several routers of one authority are allowed; the authority's resource and security controls (opportunity budget, START limiter, guard, pending and preliminary caps) stay in the authority's shared state, so all its routers share them. A router is not authority ownership. The network layers above it borrow it: `WindowsOwnerLoop<'r>` (`windows_owner_loop.rs`) holds `&'r Router` and owns an already-bound listener and the connections it accepts; `AcceptPermit<'r>`, `TransportConnection<'r>` (`transport.rs`), `HostConnection<'r>` (`host.rs`), and `WindowsTcpConnection<'r>` (`windows_tcp.rs`) borrow it too. `Router::new` can fail only when its process-wide router-ID counter is exhausted, which it reports as `RouteError::Ceremony(CeremonyError::Owner(Error::OwnershipUncertain))`. In the ABI, `TrustedAuthority::release` needs the only reference to the authority's state (`Busy` otherwise, P7-D-003), and every router holds one through its executor.
- **Why P7.3 is narrowed:** giving the ABI a long-lived owner loop over a router is a self-referential ownership problem (the loop borrows the router that the same ABI object must own) on top of listener handoff, bounded driving, and event representation. P7.3 settles only the parent hierarchy (runtime → authority → host → router) and its destroy semantics; P7.4 solves the borrow bridge and networking against that fixed hierarchy instead of redesigning both at once.
- **Decision (owner-selected):**
  1. **Host handle.** `typedef uint64_t sas_pairing_host_t;` with `SAS_PAIRING_HOST_INVALID = 0`. A host handle is opaque, process-local, and non-zero, and names one ABI object lifetime: one hosting context. It is not a pointer, socket, peer, connection, run, authority identity, or `ceremony_identity`.
  2. **Shared namespace.** Host handles come from the one process-lifetime `HandleCounter` of P7-D-001 and P7-D-003, shared with runtimes and authorities (and later connections and runs). No kind has its own counter, so a value of another kind presented as a host (or a host as another kind) names nothing: `SAS_PAIRING_INVALID_HANDLE`. Values are never reused under the loader invariant of P7-D-002.
  3. **Host meaning.** One host is one local routing and hosting context for one registered authority. In P7.3 it holds its parent authority's handle and one real core `Router` built over that authority's executor, and nothing else: no listener, socket, connection, owner loop, thread, or run state. A P7.3 host is intentionally inert; P7.4 extends it with networking.
  4. **Several hosts per authority.** One authority may have several hosts, each with its own router, as the core permits. They share the authority's one opportunity budget, START limiter, guard, and process-session accounting through the authority's core state. A host is not a security session, and host handles never refresh accounting.
  5. **Ownership hierarchy.** The runtime owns everything: its authorities (handle → `TrustedAuthority`) and its hosts (handle → host context, which records its parent authority handle and owns its router). No raw `Router` pointer or other Rust object pointer crosses the ABI or is stored in it.
  6. **`Box<Router>`.** A host context owns its router in a `Box<Router>`, so the router has a heap-stable address however the host context, the map nodes, or the runtime move. P7.3 creates no reference that outlives an ordinary borrow: no `'static` reference, `Box::leak`, lifetime transmute, raw router pointer, `ManuallyDrop` loop, self-referential helper crate, or `Arc<Router>` refactor. The stable address is groundwork for P7.4, which must audit the borrow bridge separately; pointer identity is not ABI semantics.
  7. **Create.** `sas_pairing_host_create(runtime, authority, out_host)` validates in this order: (1) `out_host` null or misaligned → `SAS_PAIRING_INVALID_ARGUMENT`, nothing written; (2) the output is set to `0`; (3) process fatal → `SAS_PAIRING_FATAL` without entering the core (neither `executor()` nor `Router::new` runs); (4) the runtime handle; (5) the authority handle, which must name an authority of that runtime; (6) the host handle is reserved (exhaustion → `SAS_PAIRING_HANDLES_EXHAUSTED`, no router is built); (7) `Router::new(authority.executor())`, the reviewed constructor, with no second routing implementation; (8) the host context is installed; (9) the handle is written. On a constructor failure the reserved value is burned (never issued), nothing is installed, and the output stays `0`.
  8. **Narrow constructor error boundary.** The constructor's one documented failure (router-ID exhaustion, `Ceremony(Owner(OwnershipUncertain))`) maps to `SAS_PAIRING_OWNERSHIP_UNCERTAIN`. Any other `RouteError` from the constructor violates its documented invariant: the process is marked fatal and `SAS_PAIRING_FATAL` is returned, never an ordinary host-creation failure. P7.3 adds no route-error ABI; P7.4 defines the translation of `OwnerLoopError`, `TcpError`, `HostError`, `RouteError`, and ceremony outcomes that network driving needs.
  9. **Accounting neutrality.** Host creation consumes no opportunity, refreshes no budget, resets no START limiter, acquires no OS lease, registers nothing, creates no ceremony, opens no router session, generates no protocol randomness, and opens no listener or socket. Host destruction is equally neutral.
  10. **Destroy.** `sas_pairing_host_destroy(runtime, host)` removes the host from the runtime first (its handle is invalid forever), then drops the host context and its router (the router's own drop path). A second destroy, or zero, random, stale, or other-kind handles, give `SAS_PAIRING_INVALID_HANDLE`. Destroying a host never releases or invalidates its authority, never touches sibling hosts, and resets nothing. It is cleanup: admitted after fatal, never clearing fatal, creating a router, recreating an authority, or resetting accounting.
  11. **Authority release cascades.** `sas_pairing_authority_release` first checks the authority handle, then removes and drops every host of that authority (their routers, and with them their executor clones), then removes the authority handle, then calls `TrustedAuthority::release` and maps its result. When it returns, the authority handle and every child host handle are invalid forever, whatever the core result; no host is restored. A `BUSY` result can therefore never be caused by an ABI-owned host's router; it still reports any other genuine holder of the authority state.
  12. **Runtime destroy cascades.** Runtime destruction invalidates the runtime handle, then explicitly drops every host (all routers), then drops the authorities (the core's own `Drop` per authority), in that order in the cleanup code, never by field declaration order: routers own executor clones and must be gone before authority ownership ends.
  13. **Concurrency.** Host create and destroy run under the runtime slot like the P7.2 authority operations, so they serialize with authority release and runtime destroy. A create admitted before a release or destroy may return `OK`, and the release or destroy then removes that host; once a release or destroy is admitted first, the create gives `SAS_PAIRING_INVALID_HANDLE`. Exactly one path removes and drops any host. No async executor, background thread, lock-free registry, or callback is added.
  14. **Three lifetimes.** The authority's *process session* (long-lived accounting, P6-D-002), an *authority handle* (one registration, P7-D-003), and a *host handle* (one router and hosting-object lifetime) are three different lifetimes. Host and authority handle churn never ends or refreshes a process session.
- **Why:** owning the router in the runtime hierarchy keeps the reviewed RAII lifecycle authoritative, as P7-D-003 did for authorities. Cascading host cleanup before the core release preserves the existing release semantics (a release with live ABI hosts would otherwise always be `BUSY`), and an explicit hosts-before-authorities destroy order keeps the core's ownership order visible. A heap-stable router gives P7.4 the address stability any borrowing loop needs without deciding the unsafe or lifetime question prematurely.
- **Unchanged:** `router.rs`, `host.rs`, `transport.rs`, `windows_tcp.rs`, `windows_owner_loop.rs`; the core's authority semantics; ABI version `1`; every earlier status value and signature (no new status code); the wire, cryptography, ceremony, deadlines, and P6 decisions. P7-D-002 still applies: hosts and routers are module state of the one resident image.
- **Status:** decided by the owner for P7.3, 2026-10-03; normative in the [ABI contract](abi-contract.md#16-hosting-contexts); implemented in `core/src/abi/hosting.rs`, `core/src/abi/authority.rs`, and `core/src/abi/runtime.rs`.

## P7-D-006 — Windows Listener Ownership and Responder Configuration

- **Inputs:** `WindowsOwnerLoop::from_bound_listener(listener, router, local, expected)` (`core/src/windows_owner_loop.rs`) takes an ALREADY-BOUND `std::net::TcpListener` from trusted outer code, a `&'r Router`, the local Responder `Bootstrap` for accepted connections, and an optional exact expected peer `Bootstrap`. Its only work is `set_nonblocking(true)`; its only failure is `OwnerLoopError::ListenerIo(kind)`, after which the listener has been dropped and nothing exists. It never binds, connects, or reads an address. The loop is cooperative and synchronous: nothing happens until `drive_once` (or `recheck_after_resume`) is called. `drive_once` returns an `OwnerStep` of `OwnerEvent`s: `Accepted(ConnectionRef)`, `AcceptRefused`, `ListenerDisabled`, `Step(ConnectionRef, TcpStep)`, `Closed(ConnectionRef, ConnectionEnd)`, plus a fail-closed `failure`. A `TcpStep` (`windows_tcp.rs`) carries at most one `TcpEvent` (for example `Inbound { request_id, run: Option<RunRef>, event }`) and at most one `PairingResult`, the one-shot local verified completion of a ceremony (P6-D-005). `WindowsTcpConnection` retains at most one outbound frame (`PendingWrite`) and writes it to its own socket in `on_writable`; neither `TcpStep` nor `OwnerStep` ever carries outbound bytes. Bootstrap validity is decided by `Bootstrap::new` (`protocol.rs`), which bounds each field (application identity 1–1024 bytes, key algorithm 1–64 bytes of `[a-z0-9.-]` starting with a letter or digit, public key 1–4096 bytes, shared context 0–8192 bytes) and the canonical frame (`MAX_BOOTSTRAP_FRAME` = 16384).
- **Why P7.4 is narrowed.** The roadmap's earlier P7.4 combined the listener, the owner loop, and a bounded drive/event ABI. A drive export would have to hand over everything `drive_once` returns, and none of it is disposable: a `PairingResult` must never be silently dropped by an ABI call; later local ceremony actions (authorize, expose, approve, reject, cancel, finish) need stable references for the core's `ConnectionRef` and `RunRef`; and every `TcpEvent`, `OwnerEvent`, and loop error needs a defined representation. Those designs come first. P7.4 therefore owns only the listener handoff, the Responder configuration the loop needs, the owner-loop lifetime bridge (P7-D-007), attach/detach/replacement, cleanup order, and panic and ownership-transfer safety. Bounded driving with connection, run, event, and result representation is P7.5.
- **Decision (owner-selected):**
  1. **The caller binds.** The ABI never binds a socket, chooses an address, interface, loopback or LAN exposure, or port, or configures discovery, a firewall, or an outgoing connection. Trusted outer code does all of that and hands the ABI one already-bound, listening Windows socket. TCP stays the experimental P4 carrier: the socket handle, address, and port are not protocol identity, authenticated identity, or security identity, and enter no transcript, MAC, authorization, routing, limiter, or accounting decision.
  2. **Socket type.** `typedef uintptr_t sas_pairing_socket_t;` with `SAS_PAIRING_SOCKET_INVALID` = `UINTPTR_MAX` (Windows `INVALID_SOCKET`). A socket is an OS resource handed into the ABI, not a handle of the P7 `HandleCounter`.
  3. **Export.** `sas_pairing_host_attach_windows_listener(runtime, host, sas_pairing_socket_t *inout_listener, const sas_pairing_bootstrap_view_t *local, const sas_pairing_bootstrap_view_t *expected)`. `local` is required; `expected == NULL` means no exact expected peer Bootstrap. The export exists on every platform; off Windows it returns `SAS_PAIRING_UNSUPPORTED_PLATFORM` and leaves the slot unchanged, with no fake listener or loop.
  4. **In/out ownership slot.** On entry `*inout_listener` is the caller's socket. Ownership transfers at one linearization point (item 6); the slot then holds `SAS_PAIRING_SOCKET_INVALID` and the ABI owns and closes the socket. The caller never closes, uses, or re-hands a socket its slot no longer holds. The slot makes the transfer observable whatever the status.
  5. **Trusted caller precondition.** A non-invalid slot value is one valid, already-bound Windows listening `SOCKET`, owned exclusively by the caller at entry and not closed or used by anyone else during the call. The ABI cannot prove an integer is such a socket, so this is a precondition like any pointer validity, not a validated property; arbitrary integers are not claimed to be memory-safely rejected.
  6. **Order and adoption point.** (1) structural validation: `inout_listener` non-null and aligned, `local` non-null and aligned, `expected` aligned if non-null, every byte view well formed, and a slot value other than `SAS_PAIRING_SOCKET_INVALID`, else `SAS_PAIRING_INVALID_ARGUMENT`; (2) off Windows, `SAS_PAIRING_UNSUPPORTED_PLATFORM`; (3) the Bootstrap configuration, copied and built with `Bootstrap::new`, else `SAS_PAIRING_INVALID_BOOTSTRAP`; (4) the process fatal state, `SAS_PAIRING_FATAL`; (5) the runtime and (6) the host handle, `SAS_PAIRING_INVALID_HANDLE`; (7) an attached listener, `SAS_PAIRING_LISTENER_ALREADY_ATTACHED`; (8) **adoption**: the raw value becomes one Rust-owned `TcpListener`, then `SAS_PAIRING_SOCKET_INVALID` is written to the slot, with nothing that can fail or panic between them; (9) `WindowsOwnerLoop::from_bound_listener`, exactly as the core expects; (10) installation in the host. Steps 1–7 leave the slot unchanged and the socket with the caller. From step 8 on the slot reads `INVALID` and Rust closes the socket exactly once on every path: with the loop on detach or teardown, or as a dropped listener if a later step fails or panics. The Bootstrap check precedes the fatal check because it is a pure value check of copied bytes that touches no authority, router, registry, accounting, randomness, or socket, and it keeps that copy outside the runtime slot; every stateful step still follows the fatal check.
  7. **Post-adoption failures.** The constructor's one documented failure (`ListenerIo`) is `SAS_PAIRING_LISTENER_SETUP_FAILED` (not fatal: the host stays attachable). Any other constructor error breaks its invariant: the process is marked fatal and `SAS_PAIRING_FATAL` returned. A caught panic after adoption is `SAS_PAIRING_FATAL` with the slot `INVALID`; the unwinding listener closes the socket, and no loop is installed. Raw `ErrorKind` values are not ABI semantics.
  8. **Bootstrap views.** `sas_pairing_bytes_view_t { const uint8_t *data; size_t len; }` and `sas_pairing_bootstrap_view_t { application_identity, key_algorithm, public_key, shared_context }` are input views only. `len == 0` never dereferences `data` (which may be null); `len > 0` needs non-null `data`, `len <= PTRDIFF_MAX`, and a range that does not wrap. The bytes are copied during the call into the reviewed `Bootstrap::new`, which alone decides validity: no duplicate field validation, no fake wire frame, no public `Bootstrap::decode`, no `protocol.rs` change. A field longer than `MAX_BOOTSTRAP_FRAME` is refused without being copied (an allocation bound with the same outcome, since no such field fits the canonical frame). No pointer is retained.
  9. **Status values.** `SAS_PAIRING_INVALID_BOOTSTRAP = 203`: the supplied trusted-local Bootstrap configuration failed the core's Bootstrap validation (no `CodecError` layout, `Debug` string, or field name is exposed). New range 400–499, host, listener, and transport-boundary lifecycle: `SAS_PAIRING_LISTENER_ALREADY_ATTACHED = 400`, `SAS_PAIRING_LISTENER_SETUP_FAILED = 401`. 200–202 are unchanged; nothing is renumbered. P7.5 owns the complete `OwnerLoopError`/`TcpError`/`HostError`/`RouteError` translation that driving needs.
  10. **One listener per host.** A host holds at most one network context (one owner loop over one listener). A second attach returns `SAS_PAIRING_LISTENER_ALREADY_ATTACHED` before adoption and never replaces the existing one. Replacement is detach, then attach; there is no replace-in-place export.
  11. **Attach drives nothing.** Successful attach leaves one owner loop, a listening socket, and zero connections. It does not call `drive_once`, `recheck_after_resume`, accept, `Router::open_session`, or `AcceptPermit::begin`; no network event occurs. No Rust thread, worker, scheduler, timer, or callback is created, so the P6-D-004 thread-root obligation stays not applicable.
  12. **Detach.** `sas_pairing_host_detach_listener(runtime, host)` is cleanup: admitted after fatal (never clearing it), idempotent (`SAS_PAIRING_OK` for a valid host without a listener), and it ends the network context while the router is alive: the loop's own `close` drops the listener and closes every connection it owns. Its report maps narrowly: clean, or already failed closed (`Closed`), is `SAS_PAIRING_OK`; `OwnershipUncertain` (a connection's cleanup could not be established, so the core keeps that capacity held) is `SAS_PAIRING_OWNERSHIP_UNCERTAIN`; anything else is fatal. The host, its router, its authority, and all accounting stay. After fatal, attach stays `SAS_PAIRING_FATAL`.
  13. **Parents.** Host destroy, authority release, and runtime destroy end every affected network context before its router, and every router before authority ownership (P7-D-007). Host destroy reports the close result (the handle is invalid whatever it says, never restored); the cascades are best effort, like the rest of their cleanup.
  14. **Accounting neutrality.** Attach, detach, replacement, and the cascades consume or refund no opportunity, reset no budget or START limiter, change no guard, start no session, admit no connection, and start no ceremony. Listener replacement is hosting/frontend lifetime only: no new process session, budget, limiter, or authority ownership (P6-D-002).
  15. **Concurrency.** Attach and detach run under the runtime slot like every host operation, so they serialize with host destroy, authority release, and runtime destroy. An attach admitted first may adopt and install, and the later destruction closes the socket; a destruction admitted first makes attach return `SAS_PAIRING_INVALID_HANDLE` before adoption, so the caller still owns the socket. A detach admitted first ends the network context and the later destruction finds none; a destruction admitted first makes detach return `SAS_PAIRING_INVALID_HANDLE`. Exactly one owner closes each socket.
  16. **No drive, connection, run, result, or outbound-byte API.** P7.4 adds no drive, poll, or recheck export, no connection or run handle, no event array, and no result access, so it cannot produce, and therefore cannot lose, a `PairingResult`. It adds no outbound buffer or send API: the TCP adapter owns and writes its outbound frame, and P7.5 keeps that architecture unless a real blocker is found. No handle is derived from a socket value, request ID, Router session, or address.
- **Why:** an in/out slot makes ownership observable on every status, so no wrapper can double-close a socket or leak one. Validating everything that can fail before adoption, and making adoption itself infallible, leaves exactly one owner at every instant, including under a caught panic. Reusing the reviewed constructor and `Bootstrap::new` keeps one implementation of setup and validation.
- **Unchanged:** `windows_owner_loop.rs`, `windows_tcp.rs`, `host.rs`, `transport.rs`, `router.rs`, `protocol.rs`, the ceremony, cryptography, deadlines, and process-session accounting; ABI version `1` and every earlier value and signature. P7-D-002 still applies: listeners and owner loops are module state of the one resident image.
- **Status:** decided by the owner for P7.4, 2026-10-03; normative in the [ABI contract](abi-contract.md#17-windows-listener-ownership).

## P7-D-007 — Owner-Loop / Router Lifetime Bridge

- **Inputs:** `WindowsOwnerLoop<'r>` holds `&'r Router`, and so does everything it will own: an accepted `WindowsTcpConnection<'r>` holds a `HostConnection<'r>`, which holds a `TransportConnection<'r>`, which holds `&'r Router` (`AcceptPermit<'r>` too, transiently). P7-D-005 keeps each host's router in a `Box<Router>` inside a runtime-owned host context. A host context that owns both the router and a loop borrowing it is self-referential, which Rust lifetimes cannot express directly.
- **Options considered:** converting the reviewed transport stack to `Arc<Router>` (rejected: a broad change to frozen reviewed code for one ABI need); a self-referential helper crate (`self_cell`, `ouroboros`, `owning_ref`; rejected: a new dependency for one site); `Box::leak` (rejected: it leaks the router and its executor clone, so authority release would stay `BUSY` forever); storing a raw router pointer (rejected); one contained lifetime extension (selected).
- **Decision (owner-selected):**
  1. **Shape.** `HostContext { authority, network: Option<WindowsNetworkContext>, router: Box<Router> }`, where `WindowsNetworkContext` owns `WindowsOwnerLoop<'static>`. The `'static` is an internal representation, not a claim that the router lives forever: it stands for "as long as this host context's router", which the invariants below guarantee. Host contexts are boxed in the runtime's map (`Box<HostContext>`), so a host context, and with it the router's box, is never moved or passed by value after construction; map changes, removal, and cascades move only the outer box pointer.
  2. **One unsafe lifetime extension.** A private `unsafe fn router_for_owner_loop(&Router) -> &'static Router` in `core/src/abi/hosting.rs` re-borrows through a raw pointer local to the function (no `transmute`, no stored pointer), with a detailed `SAFETY` contract. Its one caller, `HostContext::attach_network`, passes its own boxed router and stores the result only in its own `network` field. No other lifetime-related `unsafe` exists in the ABI.
  3. **Frozen lifetime invariants.** (a) The router's box is never replaced or reassigned, the router is never moved out of it, nothing writes through it, and no `&mut Router` is created (the field is private to `hosting.rs` and only read). (b) The network context never leaves its host context (private field; no method moves it out). (c) It is ended before the router on every path. (d) No reference to the router, the owner loop, or the network context crosses the ABI or is returned by any function (a test-only accessor aside). (e) No method can reach the owner loop after the router is dropped. (f) Accepted connections are owned by the loop and die with it, so the deepest borrow chain (loop → `WindowsTcpConnection` → `HostConnection` → `TransportConnection` → router) is covered by the same ordering.
  4. **Explicit teardown order, not field order alone.** `HostContext::detach_network` takes the network context out first, then closes it (listener, then every connection, through the loop's own `close`), then drops it, with the router untouched. Detach calls it on the host in place. Host destroy removes the host (invalidating its handle), then detaches its network in place, then drops it (and the router). Authority release removes every child host, detaches each network, then drops the hosts, and only then releases the `TrustedAuthority`. Runtime destroy takes the runtime out of the slot, detaches every host's network, drops all hosts (routers), then drops the authorities. `impl Drop for HostContext` detaches as a backstop before any field is dropped, and `network` is declared before `router` as a second line of defence only.
  5. **Panic safety.** A panic during attach before installation leaves no network context; a panic during teardown drops the network context (already taken out of its host) during unwinding while the router is still owned by the host context; the process becomes fatal through the central boundary (P6-D-004). No unwind can leave a loop referring to a dropped router.
  6. **Evidence.** A test-only probe in the network context, dropped right after the owner loop, records the authority's live-connection count and the number of holders of the authority state (the router's executor is one while the router lives). Tests show, for detach, host destroy, authority release, and runtime destroy, and with a real accepted connection driven internally (no ABI drive), that every connection is gone and the router is still alive when the loop has dropped, and that the router goes afterwards.
  7. **Scope.** The bridge is within the one-image loader invariant (P7-D-002): no self-pinning, no duplicate-image handling, no reload recovery.
- **Why:** the transport stack is reviewed and frozen with plain borrows; one audited extension contained in the type that owns both sides keeps it so, with no leak and no dependency. Boxing host contexts keeps the borrowed router box from ever being moved or passed by value, which avoids depending on unsettled details of Rust's aliasing model for moved boxes.
- **Unchanged:** every core networking file, the router's semantics, ABI version `1`. The aliasing argument is reasoned, not machine-checked: Miri cannot run this WinSock path.
- **Status:** decided by the owner for P7.4, 2026-10-03; normative in the [ABI contract](abi-contract.md#177-owner-loop-lifetime-bridge).
