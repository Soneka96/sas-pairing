## P7-D-001 — Native Runtime, Handle, and Fatal Containment Unit

- **Inputs:** [P6-D-004](../p6-remediation/decisions.md#p6-d-004--native-panic-containment-policy) (native panic containment, including the P6.4.1 payload-disposal rule, item 14) leaves the exact containment unit to P7's handle design; [P6-D-002](../p6-remediation/decisions.md#p6-d-002--f-003-owner-session-policy) forbids any same-process accounting reset; the [P7 roadmap](../../roadmap/P7-native-abi.md) lists the mandatory handoff.
- **Decision (owner-selected):**
  1. **One runtime per OS process.** At most one sas-pairing native runtime is active per OS process. A second create while one is active returns `SAS_PAIRING_ALREADY_INITIALIZED` and does not replace it. Later increments may place several pairing authorities inside the runtime; P7.1 implements none.
  2. **The runtime is the fatal-containment unit,** and its fatal state is process-wide native ABI state. P6-D-004's "affected native context" is therefore the whole native ABI of the process.
  3. **Normal lifecycle:** process → `sas_pairing_runtime_create` → runtime handle → later P7 operations → `sas_pairing_runtime_destroy`. After a normal destroy a new runtime may be created in the same process, and it receives a new handle.
  4. **Caught panic → permanent fatal.** When the ABI's containment boundary catches a Rust panic, the process's native ABI state becomes permanently fatal: no new runtime or normal core operation can start (they return `SAS_PAIRING_FATAL` without entering the core), destroy stays allowed, and recovery requires restarting the OS process. There is no "clear fatal", "reset runtime", or registry-clearing API, in production or in tests.
  5. **Destroy is the cleanup path.** Fatal state does not prevent destroy. Destroy invalidates the handle first, then performs best-effort runtime destruction. It never clears fatal state, starts protocol work, creates fresh accounting, or re-registers an authority. After fatal + destroy, create still returns `SAS_PAIRING_FATAL` until process restart.
  6. **Opaque `uint64_t` handles.** `sas_pairing_runtime_t` is `uint64_t`; `0` is never valid. Handles are process-local and opaque: not pointers, network identities, security secrets, authority identities, or protocol identifiers. They come from one monotonic, process-lifetime counter and are never reused within one OS process, so a destroyed handle can never alias a later runtime. If the counter would wrap, creation fails closed (`SAS_PAIRING_HANDLES_EXHAUSTED`) instead of reusing a value. There is no generation-reset API.
  7. **Runtime creation is infrastructure only.** It does not call `TrustedAuthority::register`, consume an opportunity, acquire the authority OS lock, start a listener, create a ceremony, or generate protocol randomness. Authority lifecycle belongs to P7.2.
- **Why conservative:** P6-D-004 requires a caught panic to poison the context that owns the panicking core state, and P6-D-002 forbids any same-process reset of authority accounting. A process-wide fatal unit satisfies both directly: no handle juggling (destroy and re-create, a second runtime, re-registration) can reach fresh accounting after a panic, and no partially updated Rust state is used again. The cost (one fatal event disables the native ABI for the rest of the process) is accepted because a caught panic is a catastrophic internal failure, never an ordinary error.
- **Wire, cryptography, ceremony authentication, result semantics, deadlines, and accounting:** unchanged. P7 wraps the frozen candidate.
- **Status:** decided by the owner for P7.1, 2026-10-02; implemented in P7.1 (`core/src/abi`). The P6-D-004 exit test through a real core-entering ABI operation remains open until later P7 increments add one ([README](README.md#mandatory-p6-handoff)).

## P7-D-002 — Native Library Residency and Loader Lifetime

- **Inputs:** P7-D-001 states its guarantees (one runtime per process, handles never reused, fatal until process restart) for the OS process, but P7.1 stores that state in module statics of the loaded library image (`static PROCESS: AbiState` in `core/src/abi/mod.rs`; the core's authority registry is also a module static, `REGISTRY` in `core/src/lib.rs`). A module static lives exactly as long as the image that contains it. P7.1.1 measured this against the release DLL ([evidence](README.md#p711-evidence)): after `FreeLibrary` and a new `LoadLibraryW` of the same file, the handle counter and the runtime slot started over (the first handle was `1` again, even with the earlier runtime never destroyed), and two copies of the DLL under different paths each created a live runtime with handle `1` in one process. [P6-D-002](../p6-remediation/decisions.md#p6-d-002--f-003-owner-session-policy) forbids any same-process reset of authority accounting, and [P6-D-004](../p6-remediation/decisions.md#p6-d-004--native-panic-containment-policy) makes process replacement the only panic recovery.
- **Decision (owner-selected): supported loader invariant.**
  1. **Exactly one image.** Supported use has exactly one loaded sas-pairing native library image per OS process. A host must not load an independent duplicate (another path, filename, copy, or rename of the library).
  2. **Process-lifetime residency.** Once stateful ABI use begins, and no later than the first `sas_pairing_runtime_create`, that image stays resident until the OS process terminates. The host keeps its load of the library (its module handle or library object) for the rest of the process.
  3. **No unload or reload recovery.** None of these is supported, after stateful use and in particular after `SAS_PAIRING_FATAL`: `FreeLibrary` then `LoadLibrary`; `dlclose` then `dlopen`; `NativeLibrary.Free` then `NativeLibrary.Load`; loading the library from a copied, renamed, or alternate path; wrapper re-initialization that loads another image. After `SAS_PAIRING_FATAL`, the only supported recovery is an OS process restart.
  4. **Process-lifetime claims are conditional on this invariant.** Under the supported one-image, process-lifetime-residency loader invariant, the native ABI state has OS-process lifetime semantics: handles are never reused, fatal is permanent, and at most one runtime is active, for the life of the process. The implementation's storage stays module static; Rust statics do not outlive the unloading of their module, and a second image has its own. A host that breaks the invariant gets no uniqueness, singleton, or fatal guarantee across images.
  5. **Trusted in-process host.** The ABI is not a sandbox against code with arbitrary control over the process's loader. A caller that unloads the library or loads independent copies violates the ABI's preconditions and is outside the supported security contract. That is not a reset API, and the library does not try to detect it.
- **P6-D-002 connection.** From P7.2 on, the ABI will hold `TrustedAuthority` state, whose accounting (opportunity budget, START limiter and its clock, process-session state) lives in native module state. Unloading and reloading the library, or loading a second image, would give that image fresh module state, so under this decision neither is a supported way to obtain fresh opportunities, limiter history, or process-session accounting. This decision is the precondition that lets P7.2 carry P6-D-002 across the ABI. P7.1 itself holds no authority accounting. The per-account authority lock file excludes only concurrent ownership; it carries no accounting, so it is not relied on here.
- **P6-D-004 connection.** P6-D-004 requires caught panic → fatal native context → no same-process recovery → process replacement. A library reload is not process replacement, so it is not a supported panic recovery.
- **Enforcement (deliberately none in the library).** P7.1.1 adds no self-pinning (`GetModuleHandleExW` with `GET_MODULE_HANDLE_EX_FLAG_PIN`, `RTLD_NODELETE`), `DllMain` logic, named mutex, shared memory, file, registry key, or module enumeration, and no new status code. Pinning one image cannot stop a host from loading a separate copy, so it would suggest enforcement that does not exist; the wrappers are trusted local callers; and P8 and P9 own library loading, where the obligation is placed ([P8](../../roadmap/P8-dart-package.md), [P9](../../roadmap/P9-dotnet-package.md)).
- **Unchanged:** ABI version `1`, every signature and status value, and the wire, cryptography, ceremony authentication, result semantics, resource limits, deadlines, and process-session accounting implementation. P7-D-001 is unchanged; this decision states the loader condition its process-lifetime wording depends on.
- **Status:** decided by the owner for P7.1.1, 2026-10-03; normative in the [ABI contract](abi-contract.md#14-native-library-loading-and-residency) and the header.
