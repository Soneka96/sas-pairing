# P4 Conformance Closure

## Scope and Claims

This is the implementation-evidence index for the experimental P4 native Rust security core (`core/`) against the current normative P3 requirements. It traces each current requirement to the code that implements it, the evidence for it, and a verdict.

- **Experimental only.** It covers the owner-selected experimental vodozemac baseline ([decision 0002](decisions/0002-experimental-vodozemac-selection.md)). It is not production-security approval, a release decision, or P5 review.
- **Not formal verification.** Tests show the implementation behaves as specified on the exercised inputs. They do not prove cryptographic security, and no independent professional audit has taken place.
- **P3 remains authoritative.** The [profile](p3-vodozemac-ceremony-profile-draft.md) is the normative source. The [conformance cases](p3-conformance-cases.md) are traceability aids, and this document changes neither.
- **Evidence over prose.** A verdict cites tests, real-OS runs, or a dated manual record. Comments, the [core README](../core/README.md), and the [roadmap](../roadmap/P4-native-security-core.md) state design intent; they are not evidence.

## Evidence Classification

**Test names.** `module::name` means the unit test `module::tests::name` in `core/src/module.rs`. `transport::limits::frozen_transport_limits_are_exact` is the one unit test in another submodule. `it::name` is an integration test in `core/tests/security_core.rs`. Tests marked **(new)** were added by this closure. Symbols are written `module::Type::method`.

**Evidence types.** *Unit* means a deterministic in-process test, using hand clocks and barriers and no sleeps. *Live* means two real vodozemac endpoints with fresh keys. *Vector* means byte comparison with `vectors/p3-remote-vodozemac-draft-01.json`. *OS* means real Windows process, file-lock, or loopback-socket behavior, run in CI on `windows-latest`. *Manual* means the dated owner-run record. *Source* means a structural property of the code, cited only next to executable evidence.

**Verdicts.** These use the exact meanings from the closure task:

| Verdict | Meaning |
|---|---|
| PASS | Implemented, with sufficient executable evidence. |
| PASS — MANUAL | As PASS, but part of the evidence is the dated manual record. |
| PARTIAL | Implemented, but one part of the evidence cannot be produced. The reason is bounded and named. |
| GAP | Missing or wrong in the core. |
| EXTERNAL | Assigned outside the core by P3/P4 architecture. |
| LIMITATION | The profile documents the environment as unsupported rather than promising mitigation. |
| NOT-APPLICABLE | Does not apply to this profile. |

**`PASS · EXTERNAL part`** means every obligation the profile assigns to the core passes, and a named remainder belongs to an outer consumer, deployment, or OS integration. Those remainders are listed in [External Integration Boundaries](#external-integration-boundaries). Totals count such rows as PASS and give the number with an EXTERNAL part separately.

### Duplicate semantics

Audited against `RemoteCeremony::duplicate`, `Router::classify_start`, and the receive entry points.

| Message | Exact duplicate | Changed duplicate | Wrong state or role | Unknown route |
|---|---|---|---|---|
| START | Ignored by its key (installed or still admitting); no limiter charge or output | Fails the run, or marks the claim conflicted; never a new candidate | At an Initiator's key: conflict, run fails | New candidate (`Router::receive_start`) |
| ACCEPT | Ignored | Run fails | Run fails (for example at R) | Session-fatal |
| INITIATOR_KEY | Ignored | Run fails | Run fails | Session-fatal |
| RESPONDER_KEY | Ignored | Run fails | Run fails, including before INITIATOR_KEY | Session-fatal |
| BOOTSTRAP_MAC | `AlreadyAuthenticated`, no MAC work | Run fails | Before SAS, or the wrong sender role: run fails | Session-fatal |
| INITIATOR_FINISH | `AlreadyAccepted`, no output or MAC work | Run fails | At I, or before approvals: run fails | Session-fatal |
| RESPONDER_FINISH_ACK | Ignored, no second final ACK | Run fails | At R: run fails | Session-fatal |
| INITIATOR_FINISH_ACK | R has succeeded: `Completed` | `Completed` (result unchanged) | At I, or out of order: run fails | Session-fatal |
| CANCEL | Run already terminal: nothing changes | Run already terminal: nothing changes | Before SAS, or the wrong role: run fails | Session-fatal |

**Roles.** START creation, INITIATOR_KEY, INITIATOR_FINISH, and INITIATOR_FINISH_ACK are produced only by an Initiator run. ACCEPT, RESPONDER_KEY, and RESPONDER_FINISH_ACK are produced only by a Responder run. BOOTSTRAP_MAC and CANCEL may come from either role but must name the expected peer. Wrong-role inputs are covered by `ceremony::out_of_order_or_wrong_role_completion_is_terminal_without_mac_work`, `ceremony::wrong_role_request_id_tag_or_frame_is_terminal`, and `ceremony::initiator_finish_requires_authenticated_approvals_and_the_initiator_role`.

## Explicit Limitations

- **Fork, VM snapshot, restored process state, duplicated cryptographic or authority state** (`R-OWNER-013`, `R-OWNER-018`). These are unsupported. Rand's `ThreadRng` documents no automatic reseed after `fork`, and no freshness-restoring mechanism is implemented. No snapshot or rollback resistance is claimed.
- **RNG failure.** `Sas::new()` may panic on OS entropy failure. Tests show the panic cannot yield a contribution, result, or refund. No graceful protocol error is promised (P3 §5).
- **Fixed-secret vectors** (`R-MAC-001`, `R-MAC-015`). The pinned vodozemac API cannot load the fixture's fixed X25519 private inputs, so the fixture's SAS bytes and tags are compared as framed bytes but not recomputed.
- **Monotonic time across suspend.** Ceremony, transport, and limiter clocks use `std::time::Instant` (on Windows, `QueryPerformanceCounter`). This audit has no automated evidence of whether it counts time spent suspended. The resume hook re-evaluates against those clocks and fails closed on an unusable reading, but it cannot add suspended time the clock did not count.
- **Zeroization** is limited to the x25519-dalek `EphemeralSecret` / `SharedSecret` drop boundary (P3 §5). Derived SAS bytes, HKDF/HMAC temporaries, buffers, swap, and crash dumps are not guaranteed.
- **Ownership scope** is the tested Windows account-scoped configuration only (decision 0003). Other platforms fail closed with `UnsupportedPlatform`.

## Source Audits

- **Forbidden regressions (searched in production code).**
  - No request-ID-only lookup: every route is `RoutingKey { session, request_id }`, and `HostConnection::confirm_sent` checks the session.
  - No socket or address keying, retry, reconnect, thread, sleep, or async runtime.
  - At most one retained outbound frame (`Option<PendingWrite>`). The only `VecDeque` is the limiter's ≤12-instant history.
  - No automatic authorization, exposure, MATCH, BOOTSTRAP_MAC, or INITIATOR_FINISH: each is its own host or adapter call.
  - The contribution is generated only after `reserve`.
  - There is one guard and one counter per authority, and `Shared` is created only in `TrustedAuthority::register`.
  - No wall-clock time is used.
- **Panics on peer-controlled paths.** Production `unwrap`s are `try_into` on exact 4-byte slices (`protocol::parse`, `wire_frame_extent`). `unreachable!()` follows a match on the same state. `expect`s are the ASCII-only Base64url string (`crypto::capped_base64url`) and two router invariants (`start_initiator_run`, `route_start`). Slicing in `transport` and `windows_tcp` stays within checked bounds. None is reachable from a frame, socket event, or consumer input. The only panic source is the upstream `Sas::new()` entropy panic described above.
- **Allocation.** Every declared length is validated before payload is retained or reserved (`wire_frame_extent`, `Partial::extend` with `reserve_exact` toward a validated target ≤ 65,536). Field counts are fixed per type. Request IDs are capped at 64, the nested bootstrap at 16,384, and generated Base64url at 65,536 with checked sizing. The retained read suffix is a fixed 8 KiB box. Per-call work is bounded: 8 routes per deadline poll, 17 sockets per wait, one frame per call.
- **`unsafe`.** `lib::os_lock` has the Win32 calls `OpenProcessToken`, `GetTokenInformation`, `IsValidSid`, `GetLengthSid`, `slice::from_raw_parts` over the SID, `GetUserProfileDirectoryW`, `LockFileEx`, `UnlockFileEx`, `CloseHandle`, a zeroed `OVERLAPPED`, and `unsafe impl Send for Lease`. `windows_owner_loop::wsa_poll` has `WSAPoll` and `WSAGetLastError`. All are generated `windows-sys` bindings with no handwritten FFI, and every input comes from the OS or local state. **Resolved (Increment 20.1):** `authenticated_account` previously formed a `&TOKEN_USER` over a `Vec<u8>` buffer, which Rust does not guarantee is aligned for `TOKEN_USER`. It now truncates the buffer to the size returned by the second `GetTokenInformation` call. The private `os_lock::token_user_sid` checks there are at least `size_of::<TOKEN_USER>()` bytes, copies the header with `ptr::read_unaligned`, and keeps the null, `IsValidSid`, `GetLengthSid`, 8–68-byte bound, and owned-copy checks while the buffer is still borrowed. The test-only `ownership_probe` binary had the same cast and now uses the same unaligned read. `windows_tests::token_user_parsing_does_not_assume_buffer_alignment` parses a synthetic `TOKEN_USER` and SID at every offset within one alignment unit, which covers every misaligned case. Restoring the old reference cast makes it abort on the debug-build misaligned-dereference check, before the dereference happens. The real-Windows `account_identity_comes_from_windows_and_is_stable` and the ownership integration tests remain green.
- **Concurrency and cleanup.** Lock order is run mutex → router table → session lifecycle (leaf). The authority mutex is taken only under a run lock or with nothing held, never across a Router call, and no cryptography runs under the table lock. Close waits on a condition variable with no lock held. Every resource is RAII-released once: `PreliminaryPermit`, pending slot and request ID in `Ceremony`, `AcceptPermit` (`held`), `IncompleteSlot`, the transport live count (`ended`), and the host, adapter, and loop teardowns. A poisoned lock or uncertain cleanup keeps the count held and never reports release.
- **Dependencies.** `vodozemac = "=0.11.0"`, `default-features = false`, lockfile checksum `ba935af0…2574` (matches decision 0002). Lock: `x25519-dalek 3.0.0`, `curve25519-dalek 5.0.0`, `rand 0.10.3`, `rand_core 0.10.1`, `getrandom 0.4.3`, `hkdf 0.13.0`, `hmac 0.13.0`, `sha2 0.11.0` (vodozemac) and `0.10.9` (core), `zeroize 1.9.0`, `base64 0.23.1`. No dependency changed in this increment.
