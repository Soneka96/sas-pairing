# P10 Owner Decisions

Stable owner decisions taken during P10. IDs `P10-D-NNN` are never reused. A decision records policy and its rationale; the [P10 package README](README.md) tracks increments and evidence, the [consumer boundary](consumer-boundary.md) and the [portability assessment](portability-assessment.md) hold the analysis that a decision relies on. P10 consumes the frozen [native ABI v1](../p7-native-abi/abi-v1-manifest.md) ([P7-D-013](../p7-native-abi/decisions.md#p7-d-013--abi-v1-final-freeze-and-wrapper-handoff)), the Dart package ([P8 final closure](../p8-dart-package/final-closure.md)), and the .NET package ([P9 final closure](../p9-dotnet-package/final-closure.md)), and changes none of them.

## P10-D-001 — Consumer Boundary, Platform Boundary, and Portability Discipline

- **Inputs:** the [threat model](../threat-model.md) result contract (authenticated bootstrap bytes, no proof of possession, consumer-owned trust); the frozen P3 profile §4 and §9 (Bootstrap record and result semantics, [P3 profile](../p3-vodozemac-ceremony-profile-draft.md)); [P6-D-005](../p6-remediation/decisions.md#p6-d-005--local-completion-and-final-ack-deadline-boundary) (local completion; either side may be the only result holder); [P7-D-010](../p7-native-abi/decisions.md#p7-d-010--pairingresult-ownership-and-foreign-access), [P7-D-012](../p7-native-abi/decisions.md#p7-d-012--sas-presentation-identity-binding-and-local-action-statuses), and [ABI contract §21](../p7-native-abi/abi-contract.md#21-wrapper-handoff-p8-p9) item 11 (no wrapper owns comparison UX or trust policy); [P8-D-005](../p8-dart-package/decisions.md#p8-d-005--dart-pairingresult-ownership-data-access-and-local-completion) and [P9-D-005](../p9-dotnet-package/decisions.md#p9-d-005--net-pairingresult-ownership-reads-and-immutable-snapshots) (results are local completion only, nothing is trusted or persisted); the DovahLink repository at `main` `4a69ee5057029878200b6e16614f67a136e3e032`, read only (re-verified by P10.1.1 at the live `main` `9f4e925cc8dcba0db37d1bd7d38b39f0927b9387`: no cited file changed and no item of this decision is affected), in particular its identity and transport contract, which already selects "bootstrap evidence → pending authorization for one exact attempt → Pair / Reject / Block → durable trust only after Pair" as DovahLink-owned architecture (DovahLink `ai/context/security/identity-and-transport.md` §10). The evidence for every item is in the [consumer boundary](consumer-boundary.md) and the [portability assessment](portability-assessment.md).
- **Decision (owner-directed in the P10.1 task):**
  1. **Responsibility boundary.** `sas-pairing` owns the pairing protocol, its cryptography, SAS generation, the ceremony transcript, `ceremony_identity`, the authentication of the selected Bootstrap and shared-context bytes, the protocol attempt and accounting controls, result lifetime, and protocol-level failure semantics. The consumer (DovahLink) owns application identities and long-term keys, proof-of-possession policy, pending application authorization, Pair / Reject / Block, KnownHost and KnownDevice persistence, reconnect credentials and normal trusted reconnect, session establishment, discovery, UX, and user authorization. Nothing in the second list moves into `sas-pairing`; the boundary stays application-neutral ([consumer boundary §2](consumer-boundary.md#2-responsibility-boundary)).
  2. **Windows-only implementation for P10.** P10 integrates on Windows x64 only, the one supported pairing platform of ABI v1. P10 adds no other platform implementation and claims no other platform support.
  3. **Platform-neutral consumer boundary.** DovahLink domain and application services depend on consumer-level pairing concepts (for example a pairing candidate, a SAS presentation, pairing evidence, a pending authorization, a pairing outcome), not on Windows socket or FFI mechanics. Never acceptable inside domain or trust policy: a WinSock `SOCKET`, `SafeSocketHandle`, `Socket` handed to `sas-pairing`, `SasPairingWindowsListenerSocket`, a native handle, an FFI pointer, a native library path, or a Windows readiness concept. Such things stay in a Windows infrastructure adapter below that boundary. This is a boundary principle, not permission to design abstraction layers ahead of the increment that needs them; exact interfaces are designed in P10.3 and P10.4.
  4. **Portability classification.** Every integration dependency is classified exactly once as **PN** (platform-neutral consumer concept), **WE** (Windows-specific but properly encapsulated), or **AB** (concrete future Android blocker, with current implementation evidence). There is no fourth category; uncertainty is written down with the missing evidence and the P10 experiment or P11 question that resolves it ([portability assessment §2](portability-assessment.md#2-portability-classification-pn--we--ab)).
  5. **ABI v1 presumed sufficient.** ABI v1 is presumed sufficient for P10 until a concrete DovahLink Windows integration requirement is shown not to be expressible through it safely. P10.1's verdict is **ABI-V1-P10-B** ([portability assessment §9](portability-assessment.md#9-abi-v1-p10-assessment)): sufficient, with named experiments that must pass before major integration.
  6. **No Android implementation in P10.** No Android code, packaging, native carrier, authority mechanism, isolate design, or platform channel is added in P10. Concrete Android blockers are recorded, not solved.
  7. **No ABI evolution from speculation.** No export, status, record, or ABI version is proposed because Android, another platform, elegance, or future-proofing would like one. An ABI change may be raised only with a concrete P10 integration gap, the exact missing capability, why the public Dart and .NET APIs cannot express it, why it is not merely an Android concern, and why no adapter can solve it safely; it then STOPs the affected work for an owner decision on ABI version and compatibility (P7-D-013 item 14). It is never designed automatically.
  8. **PairingResult is local only.** A `PairingResult` is THIS endpoint's locally verified completion of one `sas-pairing` ceremony. It never means bilateral completion, that the peer holds a result, persisted trust, authorized us, or completed long-term authentication, that a DovahLink Pair happened, that reconnect is configured, or that durable trust exists. This meaning is preserved all the way into DovahLink's domain model ([consumer boundary §4](consumer-boundary.md#4-pairingresult-boundary)).
  9. **CeremonyIdentity binds the exact attempt.** Every SAS decision (MATCH, MISMATCH, CANCEL) and every application decision taken on the strength of a ceremony is bound to that ceremony's exact `ceremony_identity`. Approval is never modelled as `approveClient(clientId)` or `approveHost(hostId)`. `ceremony_identity` is an attempt identity, not a durable peer identity, reconnect credential, trust record, `clientId`, or `hostId`, and a stale approval can never authorize a later ceremony ([consumer boundary §5](consumer-boundary.md#5-ceremonyidentity-boundary)).
  10. **Proof of possession is DovahLink's.** `sas-pairing` authenticates the exact selected Bootstrap and context bytes; it does not prove possession of any private key those bytes describe. Where DovahLink requires proof of possession of a long-term credential, DovahLink's own authentication and session layer provides it. P10.2 audits whether DovahLink already does ([consumer boundary §6](consumer-boundary.md#6-proof-of-possession-boundary)).
  11. **Pair / Reject / Block are DovahLink's.** A user's MATCH approves one exact SAS comparison only; it is not a Pair. Pair, Reject, and Block are DovahLink application policy, taken in a separate step bound to the same exact attempt ([consumer boundary §7](consumer-boundary.md#7-pair--reject--block-boundary)).
  12. **Durable trust is DovahLink's.** KnownHost and KnownDevice records, their persistence, revoke, block, reset, and forget stay with DovahLink. `sas-pairing` persists nothing and no `sas-pairing` outcome writes durable trust by itself ([consumer boundary §8](consumer-boundary.md#8-durable-trust-boundary)).
  13. **Reconnect is separate from SAS.** An already-trusted peer reconnects through DovahLink's normal authentication and proof of possession into a fresh runtime session. SAS runs to establish trust or to deliberately re-establish it, never on every connection ([consumer boundary §9](consumer-boundary.md#9-normal-reconnect-boundary)).
  14. **Network location is not identity.** An IP address, port, socket, connection handle, network interface, or listener address never identifies or authenticates a peer and never becomes trust material. Trust identity comes from authenticated DovahLink identity material ([consumer boundary §10](consumer-boundary.md#10-network-identity-boundary)).
  15. **P10.8 owns the Android classification.** P10.8 answers the frozen closure questions and selects exactly one of: A (ABI v1 reusable directly with native platform implementation work), B (ABI v1 survives, but additional native or platform transport or ownership work is required), C (concrete P10 evidence demonstrates that ABI evolution is required). P10.1 does not choose ([portability assessment §13](portability-assessment.md#13-p10-closure-portability-questions-p108)).
  16. **P11 stays milestone-level.** P11 (Android / cross-platform native support) is recorded as a milestone with inputs and investigation areas only: no increments, no Kotlin, JNI, or POSIX design, no iOS, macOS, or Linux rollout, no ABI v2 ([roadmap](../../roadmap/README.md#p11--android--cross-platform-native-support-milestone-only)).
- **Why:** the library has been built application-neutral from P1 onwards, and DovahLink's own architecture already reserves application identity, authorization, and trust for itself; writing the boundary down before integration keeps P10 from leaking DovahLink policy into the library or Windows mechanics into DovahLink's domain. Android is the expected next platform, so the boundary is drawn where it costs nothing now and saves a redesign later, while the rule against speculative ABI or abstraction work keeps P10 from paying for a platform it does not implement.
- **Unchanged:** every P7 file, export, value, layout, and ownership rule (ABI v1 frozen by P7-D-013); every P8 and P9 file and decision; the frozen protocol candidate; DovahLink (read only, unchanged).
- **Status:** decided by the owner for P10.1, 2026-10-05; documentation only (`git diff b938016 -- core dart/lib dotnet/src` is empty).

## P10-D-002 — Canonical DovahLink Bootstrap v1 Mapping

- **Inputs:** the frozen Bootstrap record ([P3 profile §3.1, §4](../p3-vodozemac-ceremony-profile-draft.md#4-request-id-and-bootstrap-record)): four exact, never-normalized fields with bounds 1–1,024 / 1–64 ASCII `[a-z0-9][a-z0-9.-]*` / 1–4,096 / 0–8,192 and a complete frame of at most 16,384 bytes, `shared_context` independently supplied by each side; [ABI contract §17.5, §19.3, §20.4](../p7-native-abi/abi-contract.md#175-attach) (Responder Bootstrap per listener, Initiator Bootstrap per run, the peer Bootstrap returned only as its exact canonical frame); P8-D-005 J and the P9 result types (no wrapper parses the frame, no wrapper exposes canonical bytes); DovahLink at `9f4e925` (`hostId` and `clientId` UUIDs; DER SPKI and ECDSA P-256 selected for the Client key, the Host algorithm unselected, the S6 guard tying the Host identity to its TLS certificate SPKI); the [authentication audit](authentication-audit.md); owner choices of 2026-10-05: ECDSA P-256 for the Host too (P10-OD-05) and the binary RFC 9562 UUID form (P10-OD-04). Full specification: [bootstrap-mapping.md](bootstrap-mapping.md).
- **Decision:**
  1. **`applicationIdentity`** = ASCII `dovahlink.application-identity.v1` (33 bytes) ‖ role byte (`0x01` Host, `0x02` Client) ‖ the 16 UUID bytes of `hostId` / `clientId` in RFC 9562 network order: exactly 50 bytes. No name, endpoint, address, port, or session value. The .NET Host writes UUID bytes with `Guid.TryWriteBytes(…, bigEndian: true, …)`, never `Guid.ToByteArray()`.
  2. **`keyAlgorithm`** = ASCII `dovahlink.ecdsa-p256.spki-der.v1` (32 bytes) for both roles: a NIST P-256 key used only for ECDSA signatures, represented as in item 3; the signature hash and encoding belong to the protocol using the key (TLS 1.3 for the Host, P10.6 / S7 for the Client).
  3. **`publicKey`** = the exact 91-byte DER SubjectPublicKeyInfo of the role's long-term key: prefix `3059301306072a8648ce3d020106082a8648ce3d03010703420004` ‖ X ‖ Y, uncompressed point on the curve. The full key is authenticated, never only its fingerprint (`SHA-256(SPKI)` stays DovahLink display / storage). The Host's key is also its TLS certificate key; the Client's is also its reconnect PoP key (both forced by DovahLink's architecture).
  4. **`sharedContext`** = ASCII `dovahlink.sas-pairing.bootstrap-v1.pairing` (42 bytes), a constant each side compiles independently; never copied from the peer; no per-attempt contribution. `ceremony_identity` is the fresh, authoritative attempt identity; a two-sided public-nonce context was analysed and rejected (no cryptographic gain against an active attacker; incompatible with a per-listener Responder Bootstrap).
  5. **Roles (P10-OD-10):** Client = Initiator, Host = Responder; open mode on first contact, the pinned Host values as `expected` only for a deliberate re-pair.
  6. **Peer Bootstrap access (P10-OD-13, E-13):** exact comparison of the whole authenticated peer frame with the canonical frame each side builds from candidate values it holds before the ceremony (candidate `clientId` and Client SPKI on the Host; `hostId` and the provisional TLS certificate SPKI on the client) and its own context; plus `peerRole`, context, and profile checks. No decoder, no wrapper helper, no ABI change.
  7. **Authority scope (P10-OD-14, bytes):** ASCII `dovahlink.pairing-authority.v1` ‖ role byte ‖ the installation UUID (47 bytes), from local state only; one pairing authority per Host installation and per client installation; runtime behaviour stays E-11 (P10.3).
  8. **Vectors:** [vectors/dovahlink-bootstrap-v1.json](vectors/dovahlink-bootstrap-v1.json), labelled DovahLink consumer mapping vectors (not `sas-pairing` conformance), verified by `tooling/tests/test_p10_dovahlink_bootstrap_mapping.py`, whose frame encoder first reproduces the frozen core-generated P3 Bootstrap frames.
- **Why:** each field carries exactly one meaning with exactly one byte form: fixed-length binary identity removes UUID text aliasing and the .NET mixed-endian trap; a namespaced, versioned algorithm identifier has a defined external meaning; the full SPKI is what later possession proofs verify against; a constant context is independently constructible and is the only context a per-listener Responder can carry; exact frame equality converts candidate values into authenticated evidence without a second parser.
- **Unchanged:** every `sas-pairing` file under `core/`, `dart/lib/`, `dotnet/src/`; ABI v1; P8 and P9 decisions; DovahLink (read only).
- **Status:** decided 2026-10-05 for P10.2; documentation, vectors, and a test-only verifier.

## P10-D-003 — DovahLink Authentication Disposition and PoP Boundary

- **Inputs:** the [authentication audit](authentication-audit.md) of DovahLink `9f4e925` (answers A–AB and AC–AF, property matrix, verdict); DovahLink's selected target architecture (`identity-and-transport.md` §4–§21, `crypto-stack-selection.md`), labelled there as selected and unimplemented; [P10-D-001](#p10-d-001--consumer-boundary-platform-boundary-and-portability-discipline) items 8–14; the owner's acceptance on 2026-10-05 of the replacement scope into P10, with transport in its own increment.
- **Decision:**
  1. **Verdict: 🔴 DOES NOT PROVIDE ADEQUATE AUTHENTICATION — REPLACEMENT REQUIRED** for durable trust and normal reconnect. Deciding evidence: the long-term Client primitive is a reusable bearer secret (no possession proof, no freshness, no session binding, clonable), there is no long-term Host primitive at all, and the client sends the bearer in `hello` before any Host claim. The replacement of the six-digit ceremony is not counted in the verdict.
  2. **Nothing of the bearer path remains.** The bearer credential, its verifier, and the six-digit flow are removed atomically at cutover (bearer: P10.7, DovahLink S9 / S10; six-digit policy: P10.5, P10-OD-07), with no dual mode.
  3. **Preserved unchanged:** typed Trusted / Revoked / Blocked / Unpaired / unknown outcomes; immediate session invalidation; idempotent administration; the security fence generation and Known Device incarnation; the conditional trust write; DPAPI per-user persistence with fail-closed corruption handling; Host-scoped client recovery; the separate developer-authentication provider (P10 does not change it).
  4. **PoP boundary:** `sas-pairing` authenticates `applicationIdentity`, `keyAlgorithm`, `publicKey`, and `sharedContext` and proves no possession. DovahLink proves possession on the provisional DovahLink session before any pending authorization: the Host by TLS 1.3 with a certificate whose SPKI is byte-equal to the authenticated Host `publicKey`; the Client by an ECDSA P-256 signature, verified against the authenticated Client `publicKey`, over a domain-separated pairing-PoP statement containing the exact `ceremony_identity` and a fresh Host challenge (bytes and vectors in P10.6). Proof of possession stays DovahLink-owned (E-07).
  5. **Authorization sequence:** local result → exact peer-frame check → Host key proof → Client PoP → `PendingPairingAuthorization` keyed by `ceremony_identity` and fenced by the captured generation → Pair / Reject / Block → durable trust only on Pair. A result is never trust; `request_id` is never authority; asymmetric local completion never creates trust.
  6. **Reconnect boundary:** no SAS; pinned Host verification over TLS 1.3, fresh Host challenge, Client ECDSA P-256 PoP (S7), current Host trust state, fresh session.
  7. **Minimum replacement and owners:** Host key P10.3 (S3); Client key P10.4 (S4); authenticated transport (WSS / TLS 1.3, provisional and pinned) in the new increment **P10.5A** (S6, S5 plumbing); Host verification, Client pairing PoP, KnownDevice key binding, and Known Host pin P10.6 (S5, S6 guard); reconnect PoP and cutover P10.7 (S7, S9, S10). Each DovahLink part follows DovahLink's own workflow as pre-alpha P10 work; DovahLink's production gate stays closed.
- **Why:** the audit found no property of the current primitive that a targeted change could make adequate, while DovahLink has already selected the replacement architecture; `sas-pairing` authenticates public keys, so the keys must exist and their possession must be proved for its evidence to mean anything.
- **Unchanged:** `sas-pairing` code and ABI; DovahLink code (P10.2 implements none of this).
- **Status:** decided 2026-10-05 for P10.2; documentation only.
