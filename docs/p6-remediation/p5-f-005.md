This is a disposition, not a remediation. The core's panic behavior is real and stays as it is; it was reviewed and accepted as fail-closed. What it needs is a containment rule at the native boundary, and that boundary is built in P7. P6.4 records the rule and makes it a P7 obligation. It does not claim P7 has implemented it.

## 1. Finding

`vodozemac::sas::Sas::new()` returns `Sas`, not `Result`. It draws its ephemeral key from rand's `ThreadRng`, which panics if seeding or reseeding from the OS fails. The core reaches `Sas::new()` in two places:

- **Responder:** START admission, inside `Router::route_start`. Admission runs outside the table lock, after the `(session, request_id)` key has been claimed as `Route::Admitting`.
- **Initiator:** local `expose_key`, under the Router's `on_run`, which holds the run's mutex while the operation runs. This happens after the opportunity and the exposed-ceremony guard were reserved.

The panic unwinds out of the Router, `Tcp::on_readable`, `Tcp::expose_key`, `WindowsOwnerLoop::drive_once`, and `WindowsOwnerLoop::expose_key` to the caller. If the caller catches it and keeps going, conservative residue is left behind.

Source checked at `43eca55` with nothing changed since P5: `core/src/crypto.rs` (`EphemeralSas::new` → `Sas::new()`), `core/src/ceremony.rs` (the `ResponderAdmitted` and `InitiatorReserved` pause points fire immediately before generation, with nothing in between), `core/src/router.rs` (the claim is inserted and admission runs outside the lock; there is no RAII guard for the claim; `on_run` holds the run mutex), `core/src/lib.rs` (P6.3 process session; reactivation fails closed on non-quiescent or poisoned accounting). The lock file still pins rand 0.10.3 and getrandom 0.4.3.

## 2. P5 evidence

P5.1 derived the finding from source. P5.3 reproduced it deterministically at every layer by injecting the panic at the P4 pause points and catching it around the real calls ([deep review §7](../p5-security-review/dependency-unsafe-deep-review.md#7-p5-f-005-entropy-panic)):

- **Responder** (F005-001, 002, 004): no ACCEPT and no contribution; the pending slot and permit unwind; the START-limiter charge is kept. The `Admitting` claim survives until session teardown, so an exact copy of the START (including the adapter's retained replay) becomes an ignored duplicate, and a frame for that key marks the claim conflicted. Teardown releases everything.
- **Initiator** (F005-003 with four next operations, and 005): the run mutex is poisoned. The authority reports `Busy` and `remaining 9`: the opportunity is consumed and not refunded. The next presentation, deadline poll, inbound frame, close, or owner-loop drive returns `OwnershipUncertain`, and the adapter or loop fails closed. Dropping the detached run releases the guard and the request-ID reservation, still with no refund. One live-connection slot and one CLOSING Router session stay held.
- **Safe in every case:** no `PairingResult`, no exposure without consumption, no refund, no premature guard reuse, and no stale route that accepts a valid ceremony.

## 3. Triggerability

rand 0.10.3 `ThreadRng` panics on a failed initial seed (`thread.rs:163`) or a failed reseed after 64 KiB of output per thread (`thread.rs:70`). A failed reseed never reuses or extends output. getrandom 0.4.3 on Windows uses `ProcessPrng`, which upstream documents as always returning TRUE on Windows 10 and later. A remote peer controls when Responder admission runs, so it can cause more RNG use and more reseeds, at the START-limiter rate. It cannot make the OS entropy provider fail. **Not remotely triggerable.** On supported Windows the panic is practically unreachable; it is a fault-model case, not an attacker capability.

## 4. Security impact

None for pairing security. The availability residue (an orphan claim bounded by its session; one live slot and one CLOSING session per caught Initiator panic) appears only after a catastrophic, non-attacker event, and only if the caller catches the unwind and keeps going. Under P6.3 that residue also makes the process session non-quiescent, so the same process cannot re-register the authority to get fresh accounting ([§10](#10-process-session-accounting-interaction)). The one real requirement is at the boundary: a Rust panic must never escape into a foreign caller, and a caught panic must never become a reset.

## 5. P6-D-004

The owner selected [P6-D-004 — Native Panic Containment Policy](decisions.md#p6-d-004--native-panic-containment-policy):

1. The protocol core does no broad panic recovery and gains no internal `catch_unwind`.
2. The supported P7 ABI catches every panic inside Rust before it can cross `extern "C"` or an equivalent boundary, at every export, preferably through one central dispatch mechanism.
3. The affected native context becomes permanently fatal. Later calls return a stable fatal-state error without entering the core.
4. There is no same-process retry, resumption, re-registration, or release-and-reacquire recovery.
5. Process restart is the conservative recovery boundary.
6. No panic payload is part of the ABI contract, and the caught payload's destructor is not run on the containment path (P6.4.1, [§8.1](#81-panic-payload-disposal-p641)).
7. The supported artifact uses a panic strategy that `catch_unwind` can catch.
8. P7 CI tests panic containment.
9. `extern "C-unwind"` is not a supported contract.
10. `panic = "abort"` is not the selected ABI policy.

## 6. Why panic=abort was not selected

P5 had suggested `panic = "abort"` as the simplest option. The owner rejected it as the ABI policy. The native core is meant to be embedded in a consumer process (a Dart or .NET application), and that whole process should not be terminated on purpose because the pairing library hit a catastrophic failure that a fail-closed boundary can contain. Abort would also make `catch_unwind` useless ([§11](#11-current-rust-abipanic-behavior)), so no fatal-state reporting would be possible. P6.4 changes no Cargo profile. Today the project sets no `panic` key anywhere, so it uses Rust's default, which is `unwind` ([§11](#11-current-rust-abipanic-behavior)). P7 must make the supported artifact's setting explicit and tested.

## 7. Why broad core recovery was not selected

A panic can happen while a mutex is held, after an opportunity reservation, after resource acquisition, or partway through an internal transition. Making every core layer safe to unwind through, and able to resume, would be a much larger semantic commitment than F-005 calls for. It would also trade today's fail-closed outcome (a poisoned run reports `OwnershipUncertain`, produces no result, and is never reused) for complex recovery code that is hard to review. The chosen boundary is to contain the panic at the P7 ABI, poison the context, and stop using it. The optional hardening P5 mentioned (an RAII guard that removes the Responder's `Admitting` claim, and releasing transport accounting for a poisoned run) is **not required** for the protocol freeze, the F-005 disposition, or P7 correctness under P6-D-004, because a panicked context is fatal anyway. It stays optional robustness hardening and was not implemented, since source review found no independent correctness defect.

## 8. Required P7 containment model

```text
foreign caller
  -> native export (extern "C", non-unwinding)
       -> if context is fatal: return FATAL_STATE (core not entered)
       -> Rust catch_unwind boundary (one central dispatch for every export)
            -> reviewed core
       <- Ok(value) | ordinary error           -> normal ABI result
       <- caught panic: Err(payload)           -> mark context permanently fatal
                                               -> suppress payload destruction (destructor never runs)
                                               -> return stable fatal error
```

- The panic is caught inside Rust, before it reaches the export's `extern "C"` frame. Foreign code never sees a Rust unwind or a payload as control flow.
- The caught payload is neither exposed nor dropped normally ([§8.1](#81-panic-payload-disposal-p641)).
- Coverage: every export that can run Rust code tied to the native runtime or authority, including create/open, destroy/close, drive/poll, receive/send, local authorization, exposure, approve/reject, presentation and result access, callbacks, and any later helper. The exact export set does not exist yet; P7 defines it and proves the coverage, preferably mechanically through one dispatch path.
- Rust-owned threads: if P7 adds background, worker, or callback threads, each thread root has the same containment and marks the relevant context fatal. A worker never dies quietly while ABI calls carry on.

### 8.1 Panic-payload disposal (P6.4.1)

The P6.4 text said the caught payload was "dropped". That was incomplete. `catch_unwind` returns `Err(payload)` and gives the containment code ownership of the panic payload, and the official `catch_unwind` documentation warns that dropping that payload may itself panic ([§11](#11-current-rust-abipanic-behavior)). A payload type with a panicking `Drop` would then raise a second panic inside the `extern "C"` export, outside any `catch_unwind`, and the host process would abort. Catching the first panic therefore does not by itself prove that no panic escapes the ABI. P6.4.1 closes that gap in [P6-D-004](decisions.md#p6-d-004--native-panic-containment-policy) (item 14):

- **Rule:** the caught panic payload must not be allowed to execute an uncontained panicking destructor. The fatal path does not perform an ordinary drop.
- **Selected handling and order:** `Err(payload)` → mark the context fatal → do not expose the payload → intentionally suppress its destruction → return the stable fatal error. The fatal transition comes before the final ABI return, so the context never looks healthy if something unexpected happens after the catch. P7 may implement the suppression with `std::mem::forget(payload)` in an internal helper; the normative requirement is only that the destructor does not run. Reclaiming the payload is not required.
- **Why a leak is acceptable here:** this path is reached only on catastrophic internal failure. The context is then permanently fatal, no normal core operation runs on it again, and recovery already means restarting the process. The leaked payload is bounded by the number of fatal events, process-local, and reclaimed when the process terminates. That is preferable to running an arbitrary destructor that can panic again and abort the host. It is not a normal resource-management strategy and applies only to this path.
- **Not done:** no ordinary drop, no nested `catch_unwind` layers around the drop, and no downcasting, formatting, `Display`/`Debug`, serialization, or return of the payload. Each of those can run arbitrary Rust code; the only stable outcome is the fatal error. Optional diagnostics stay outside the security-critical return path.
- **Scope:** containment covers unwinding panics that reach the ABI's `catch_unwind` boundary. P7 must not install a custom panic hook that deliberately panics or otherwise defeats it. Aborting failures, memory corruption, and arbitrary process corruption are outside what this policy claims, and `panic = "abort"` stays incompatible with it.

## 9. Fatal-state lifecycle

| Event | Required behavior |
|---|---|
| Panic caught in an export | The context enters a permanent fatal state (P7 picks the name, such as `PanicPoisoned`, `Fatal`, or `InternalFailure`); the call returns the stable fatal error |
| Any later call on that context | The same stable fatal-state error, returned before any core entry. No retry, no resumed ceremony, no new run, no fresh ephemeral |
| Destroy or close | Allowed. Best-effort Rust ownership cleanup without normal pairing logic; the handle is invalidated. It does not reactivate pairing or reset the process session |
| New handle for the same authority in the same process | Refused by P7 with the fatal error: the authority stays fatal for the rest of the process session. Underneath, the core gives no fresh accounting either; non-quiescent or uncertain state fails closed with `OwnershipUncertain` (P6.3) |
| Recovery | Restart the native owning process, establish a fresh process session, and safely reacquire ownership |

**Containment unit.** At minimum, the authority or native ownership context that owns the panicking core state becomes unusable. If P7 puts several authorities in one runtime handle, its design must name the unit explicitly. The safe default is to poison the enclosing native runtime or authority context. P6.4 decides nothing about unrelated authorities beyond that minimum.

## 10. Process-session accounting interaction

P6.3 made the opportunity budget and START limiter belong to the owning process's session. Reactivation continues the same accounting and fails closed with `OwnershipUncertain` while runtime resources are still held or the accounting is poisoned (`core/src/lib.rs`, `register_with`). Applied to F-005:

- **Initiator panic:** the caught panic leaves one live-connection slot held, so the process session is not quiescent. Dropping every handle (adapter, router, executor, trusted authority) and registering the same canonical authority in the same process returns `OwnershipUncertain` every time. It never returns `Ready { remaining: 10 }`, and the spent opportunity stays spent (`remaining 9`, live slot 1). New P6.4 test evidence for this is in [§13](#13-new-test-only-evidence-if-any).
- **Responder panic:** after session teardown nothing is held, so re-registration succeeds. It continues the same process session: the START-limiter charges, including the one from the panicked admission, are kept, and no fresh limiter is created. New P6.4 test evidence.
- **Therefore** a panic handler that tried "drop authority → register authority → continue" would gain nothing in the current core: it would either fail closed or continue the same accounting. P6-D-004 forbids that pattern anyway, because it would undermine P6-D-002, ten-opportunity process-session accounting, and the START limiter's lifetime.

## 11. Current Rust ABI/panic behavior

Checked against current documentation and with a throwaway experiment. Toolchain: rustc 1.99.0 (b940084d7 2026-09-28), Windows 11 Pro 26200, x86_64-pc-windows-msvc.

**Sources (fetched 2026-10-02):**

- Rust Reference, [Panic](https://doc.rust-lang.org/reference/panic.html): `unwind` "is potentially recoverable" and `abort` "is non-recoverable". `"C"` is a non-unwinding ABI and `"C-unwind"` permits unwinding. It is undefined behavior to call an unwinding Rust `extern` function from code that does not support unwinding. A foreign exception caught by `catch_unwind` either aborts or returns an opaque `Err`, and which one happens is unspecified. A different instance of the Rust standard library counts as foreign.
- [`std::panic::catch_unwind`](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html) "*only* catches unwinding panics, not those that abort the process". For callers that cannot unwind, an `extern "C"` function makes a panic abort the process automatically. `catch_unwind` is for "more graceful error-handling". *Added in P6.4.1 (re-checked 2026-10-02):* the same page says the `Err` holds the panic payload and that dropping it may in turn panic, and that a custom panic hook runs before the panic is caught.
- [Rust 1.81.0 release notes](https://blog.rust-lang.org/2024/09/05/Rust-1.81.0/): since 1.81, non-unwinding ABIs such as `"C"` abort on an uncaught unwind, which closed the old soundness hole.

**Experiment (throwaway, in a scratch directory outside the repository, not committed).** A `cdylib` with four exports was loaded by a foreign host, a Python `ctypes` process. It was built once with the default (unwind) dev profile and once with a `panic = "abort"` profile.

| Export | Profile | Observed | Host exit |
|---|---|---|---|
| Panic escapes a plain `extern "C"` export | unwind | "panic in a function that cannot unwind … aborting" | `0xC0000409` (process killed) |
| `extern "C"` export with `catch_unwind` inside, setting a fatal flag | unwind | ok call → `0`; panicking call → `-1` (fatal; this P6.4 experiment used an ordinary string payload and dropped it, see the P6.4.1 note below); next call → `-2` (fatal state, core **not** entered: 2 core entries in total); host prints "exit normally" | `0` (host survives) |
| Panic escapes an `extern "C-unwind"` export into the foreign frames | unwind | "fatal runtime error: Rust panics must be rethrown, aborting" (the host's own exception handling intercepted the foreign unwind) | `0xC0000409` |
| The same `catch_unwind` export | abort | Only the first ok call returned; the panic aborted before `catch_unwind` could act | `0xC0000409` |
| The other two exports | abort | Abort | `0xC0000409` |

**Conclusions:**

- A panic escaping `extern "C"` aborts the whole host process on this toolchain. That is sound, but it takes the consumer down.
- `catch_unwind` inside the export, under `panic = "unwind"`, contains the panic. The host survives and gets a stable error, and the fatal flag stops any further core entry.
- Under `panic = "abort"`, `catch_unwind` cannot recover anything, so the P7 artifact's panic strategy is part of the containment contract.
- `extern "C-unwind"` hands a Rust unwind to foreign frames. What happens next depends on the foreign runtime (here it aborted), and catching a foreign exception is unspecified even in Rust. That makes it unusable as a supported Dart/.NET contract.

**P6.4.1 payload-destructor check (throwaway, outside the repository, not committed; same toolchain).** A non-unwinding `extern "C"` function with `catch_unwind` inside and a fatal flag; the core operation called `panic_any` with a payload type whose `Drop` panics. With an ordinary `drop(payload)` after the catch, the destructor's panic could not unwind out of the `extern "C"` function and the process aborted ("non-unwinding panic. aborting."). With `mem::forget(payload)` after setting the fatal flag, the call returned `-1`, the next call returned `-2` without entering the core (1 core entry in total), and the process exited normally. This is why [§8.1](#81-panic-payload-disposal-p641) forbids an ordinary drop on the containment path.

**Current build audit:** `core/Cargo.toml` has no `[profile]` section and no `panic` key, and no crate type is set (an rlib library plus test and probe binaries). There is no workspace `Cargo.toml` and no `.cargo/config*`. The CI workflows (`rust-core.yml`, `consistency.yml`) pass no panic flags or `RUSTFLAGS`. The project therefore uses Rust's default strategy, `panic = "unwind"`, for every profile, and selects neither `abort` nor `unwind` explicitly. P6.4 does not change that.

## 14. P3 / conformance effects

- **P3:** no change. §5 already says that failed entropy produces no exposed key and no success, that `Sas::new()` may panic, and that no graceful error is promised. ABI containment is an owner-boundary policy, so it lives in P6 and P7 documents, not in the remote protocol.
- **Conformance:** `R-OWNER-013` already covers RNG failure ("do not expose a key unless freshness and unpredictability are restored"). It gets one minimal in-place *P6 amendment (P6-D-004, P6.4)*: an RNG panic or failure produces no exposure or result and does not reset the process session. No row is added, and the count stays at **92** normative rows. No wire or MAC conformance change.

## 15. P7 roadmap handoff

[P7](../../roadmap/P7-native-abi.md) now carries these mandatory requirements, which are part of its scope, security invariants, and exit criteria:

- Every native export contains a Rust panic before it can escape across FFI, through one central dispatch where possible. Rust-owned thread roots are contained too.
- A caught panic becomes a stable, bounded fatal error that is distinct from every ordinary error. No panic payload crosses the boundary.
- A caught panic payload cannot execute an uncontained destructor: the context is marked fatal first, then payload destruction is suppressed (P6.4.1, [§8.1](#81-panic-payload-disposal-p641)).
- The affected native context is permanently poisoned, and later operations fail with the fatal-state error without re-entering the core.
- A fatal handle can still be destroyed. Destroy neither reactivates pairing nor resets the process session.
- No same-process accounting reset, whether by re-registration, release-and-reacquire, or a fresh handle. Recovery means restarting the process.
- The supported build configuration is unwind-compatible, stated explicitly, and checked by a test that fails if the supported artifact moves to `panic = "abort"` while claiming containment.
- Wrappers never receive a Rust unwind or panic payload as control flow, and `extern "C-unwind"` is not the supported API.
- **Exit criterion (deterministic test):** an injected core panic → the ABI call returns the fatal error → the host process survives → the next ABI operation returns the fatal-state error → the core operation is not retried → no fresh authority accounting appears → destroy succeeds and the handle becomes invalid.
- **Exit criterion (Drop-panicking payload, P6.4.1):** the same test with a custom payload whose `Drop` panics (`panic_any(PanicOnDrop)` through the core test seam or ABI test path) → the original panic is caught → the context becomes fatal → the payload destructor is **not** executed → the ABI returns the stable fatal error → the host process stays alive → the next ABI operation returns the fatal-state error without re-entering the core → destroy remains possible.

P7 must not be marked complete until all of these hold.

## 16. Final disposition

**P5-F-005 → DISPOSITIONED-IN-P6 (P6.4) — mandatory P7 ABI containment requirement.**

- **Core security behavior: reviewed and accepted.** The panic is real, not remotely triggerable, and fails closed. It produces no result, no refund, no uncharged exposure, no guard reuse, no stale successful route, and, after P6.3, no fresh same-process accounting.
- **ABI containment requirement:** deferred to the phase that owns it, P7. The implementation obligation remains.
- It is not `REMEDIATED-IN-P6` (the ABI does not exist), not `FALSE-POSITIVE` (the panic behavior is real), and not `ACCEPTED-LIMITATION` (P7 has a mandatory obligation).
- **Does not block the protocol freeze.** F-005 is a reliability and safety requirement for the native boundary. It does not change the remote protocol's semantics: no wire, cryptography, ceremony-authentication, or accounting change is needed. That holds as long as the panic stays non-remotely-triggerable, no authentication or accounting violation exists, the current core fails closed, and P7 is gated on meeting P6-D-004 before it can complete.

### Panic containment threat review

| # | Sequence | No false success | No refund | No fresh accounting | No resumed ceremony |
|---|---|---|---|---|---|
| 1 | Entropy panic before exposure (Responder admission) | No ACCEPT, no contribution, no result | Nothing reserved, so nothing to refund; the limiter charge is kept | Re-registration continues the same limiter (F005-001) | The orphan claim only ignores duplicates or refuses; teardown removes it |
| 2 | Entropy panic after reservation, before contribution (Initiator) | No `INITIATOR_KEY` written, no result | `remaining 9` kept after every next operation and drop | Re-registration fails `OwnershipUncertain` (F005-003, F005-005) | The run is poisoned; every operation reports `OwnershipUncertain` |
| 3 | Panic while a Router claim exists | The claim never becomes a run, and a conflicting frame marks it conflicted | — | Session teardown releases it exactly once | An exact START copy is `Duplicate`, never re-admitted |
| 4 | Panic while the run mutex is held | The poisoned run yields no result | Guard and reservation released only on drop, with no refund | Held live slot → session non-quiescent → re-registration fails closed | No mutex-poison recovery exists; teardown reports `OwnershipUncertain` |
| 5 | Caught panic at the future ABI boundary | The P7 handler marks the context fatal, suppresses the payload's destructor, and returns only the fatal error; it never returns `Ok` | The handler performs no accounting | The handler never releases and re-registers | The handler never retries |
| 6 | Foreign caller invokes the same handle again | Fatal-state error before any core entry | — | — | The core is never entered (P7 exit test) |
