## 1. Finding

Two lifetimes were conflated. A **registration** (`TrustedAuthority::register` until `release()` or the final drop) is the interval in which this process holds the authority's OS lease; trusted code can end and start registrations many times inside one live process. The **process session** is the owning OS process's lifetime for that authority. P3 ties the opportunity budget and the START limiter to the process session. The P4 core tied them to the registration: inside one live process, release (or dropping every handle) followed by `register` of the same scope produced a fresh `Ready { remaining: 10 }` and a fresh START limiter. Trusted local code had to trigger it, not a remote peer, so the finding is LOW; but a future binding that re-registers on a frontend restart, UI reconnect, or error recovery would have multiplied the ten-opportunity window without any process replacement.

## 2. Existing normative policy

P3 already required the behavior P6.3 implements:

- §11.1: "The process has at most 10 exposed remote SAS opportunities". The budget is "volatile session accounting: a legitimate process restart starts a new local session budget only after the previous owner has terminated and exclusive ownership has been safely established." "If the budget has consumed 10 opportunities, no remote ceremony can cross exposure for the remainder of that owning process/session. A verified replacement owner starts a new session budget after the previous process terminates".
- §11.1.1, START limiter "Lifetime and reset": owned "by the owning process/session"; a replacement begins fresh "only after §11.1.2 establishes prior-owner termination and safe exclusive acquisition"; not reset by a frontend restart or by "inactivity alone (idle time only refills credit toward 4)".
- §11.1.2(3): "The native security core owns one process-wide authority registry; for each identity it owns the exclusive process lease, exposed-ceremony guard, volatile ten-opportunity counter, pending-state limits, and preliminary-work limits."
- §11.1.2(4)–(5): failed acquisition refuses pairing; "uncertain acquisition or release disables pairing and fails closed"; "A replacement starts a fresh volatile ten-opportunity process/session budget only after safe exclusive acquisition; restarting a frontend while the owning process remains alive does not reset that budget."
- Conformance: `R-OWNER-006` (exhausted for the remainder of the session), `R-OWNER-012` and `R-OWNER-021` (cross-process exclusion; a process-local mutex is not proof), `R-OWNER-017` (fresh budget only after prior-owner termination), `R-OWNER-022` (frontend restart is not a session replacement), `R-OWNER-031` (release and replacement), `R-OWNER-034`/`035` (burst and rolling behavior), `R-OWNER-037` (one authoritative state per authority), `R-OWNER-038` (limiter lifetime), `R-OWNER-039` (unsafe limiter clock).

## 3. P6-D-002

[P6-D-002](decisions.md#p6-d-002--f-003-owner-session-policy), recorded by the owner in P6.1, governs this increment and is not revised: **keep the current P3 process/session semantics.** The owner session is not the `TrustedAuthority` registration lifetime, and P3 is not changed to ratify the P4 implementation. A same-process release, drop, frontend or listener restart, re-registration, or UI reconnect creates no fresh ten-opportunity budget or START limiter for the same canonical authority. Fresh volatile accounting begins only after the previous owning process has terminated and the new process has safely established exclusive ownership. P6.3 implements this decision; it takes no new owner decision and adds no `P6-D` ID.

## 4. Root cause

At `e8f887a` (`core/src/lib.rs`):

```rust
static REGISTRY: OnceLock<Mutex<HashSet<Vec<u8>>>> = OnceLock::new();

struct State {
    identity: Vec<u8>,
    shared: Mutex<Shared>,               // budget, guard, limiter, runtime counts
    ownership: Mutex<Option<os_lock::Lease>>,
    limiter_clock: Clock,                // "for its whole owner lifetime"
}

impl Drop for State {
    fn drop(&mut self) {
        if let Ok(mut known) = REGISTRY.get_or_init(...).lock() {
            known.remove(&self.identity);           // the authority is forgotten
        }
    }
}

fn register_with(scope: &[u8], limiter_clock: Clock) -> Result<Self, Error> {
    ...
    if !known.insert(identity.clone()) { return Err(Error::AlreadyRegistered); }
    let lease = os_lock::Lease::acquire(&identity)?;   // (removes the entry on failure)
    Ok(Self(Arc::new(State {
        identity,
        shared: Mutex::new(Shared {
            remaining: MAX_OPPORTUNITIES,               // fresh 10
            ...
            start_limiter: StartLimiter::new(),         // fresh limiter
            ...
        }),
        ownership: Mutex::new(Some(lease)),
        limiter_clock,                                  // fresh clock origin
    })))
}
```

The registry recorded only "is this identity registered right now?". All accounting lived in `Shared`, owned by the per-registration `State`. When the last `Arc<State>` dropped (after `release()` or the final handle drop), `State::drop` removed the identity and `Shared` died with it; the next `register` built a new `Shared` with 10 opportunities, `StartLimiter::new()`, and a new `system_clock()` origin. `release()` also let an uncertain lease release (`OwnershipUncertain`) fall through to that same drop, so even an ambiguous release made the authority re-registrable with fresh state. P4 designed and tested this deliberately (`process_ownership_and_full_reservation_lifecycle` expected `Ready { remaining: 10 }` after exhaustion and re-registration; `ownership_is_never_released_while_ceremony_state_remains` expected 10 after one spent opportunity; `a_safely_replaced_owner_starts_with_a_fresh_limiter` expected a fresh limiter in the same process).

## 5. Process-session model

After P6.3 the two lifetimes are separate types:

```text
REGISTRY: Mutex<HashMap<canonical identity, ProcessSession>>     (process static, never evicted)

ProcessSession                                 State (one active registration)
  shared: Arc<Mutex<Shared>>  ────────────────►  shared: Arc<Mutex<Shared>>   (same mutex)
  limiter_clock: Clock        ────────────────►  limiter_clock: Clock         (same clock)
  registration: Inactive | Active | Uncertain    ownership: Option<Lease>     (this registration's)
                                                 live: bool                   (end runs once)
```

| Registration state | `register(scope)` | How it is left |
|---|---|---|
| no entry (never owned by this process) | Acquire the OS lease; on success create the entry (`Shared::new()`: 10 opportunities, fresh limiter, empty resources; the clock), `Active`. On failure: error, **no entry created** | — |
| `Inactive` | Require quiescent runtime resources and an unpoisoned `shared` (else `OwnershipUncertain`), then acquire the OS lease **anew**; on success `Active` with the **same** `shared` and clock. On failure: error, entry and accounting unchanged | — |
| `Active` | `AlreadyRegistered` | `release()` or the final drop: release the lease, then `Inactive`, or `Uncertain` if the release was uncertain |
| `Uncertain` | `OwnershipUncertain`, always | Never: process replacement only |

- **Canonical key.** Only the existing canonical bytes `sas-pairing-authority-v1 || u32be(scope_length) || scope`, built from the trusted local scope. Nothing about a registration, `State`, `Arc`, connection, request ID, thread, listener, Router, PID, or peer participates. Network input reaches only `CeremonyExecutor` methods of an existing registration and cannot construct an identity (I6).
- **Strong registry ownership.** The registry entry owns an `Arc<Mutex<Shared>>` and the clock for the life of the process. No `Weak` reference is involved, so the last registration ending cannot make the accounting disappear. There is no eviction, idle timeout, LRU, or "remove when inactive".
- **OS lease stays authoritative.** The registry is not cross-process proof. Every transition into `Active` acquires a new `os_lock::Lease` while the registry lock is held; the old lease is never reused. Same-process re-registration reuses the **accounting** and reacquires **OS ownership**: separate concerns.
- **First ownership.** A process session exists only after this process first successfully acquired the lease for that identity. A failed first acquisition (`OwnershipUnavailable`, `OwnershipUncertain`, or `UnsupportedPlatform` off Windows) leaves no entry, so it creates no artificial owner session.
- **Ending a registration.** `release()` (after `Arc::try_unwrap`; with live clones it still returns `Busy` and changes nothing) and the final `Drop` share one path, `State::end`, which runs once: release the lease with `UnlockFileEx` (the drop path now also unlocks explicitly before the handle closes), then, under the registry lock, mark the entry `Inactive`, or `Uncertain` if the release failed. The lease is released before the entry becomes `Inactive`, so a racing registration sees `AlreadyRegistered` until the lease is free. `end` touches only the registry entry, never `shared`.
- **Reset only by process exit.** The registry is in process memory only. Process termination destroys it (and the OS frees the file lock); a new process starts with an empty registry, so its first successful acquisition creates fresh accounting. No reset, new-epoch, or clear API exists, public or crate-private, and nothing is written to disk: the lock files stay empty.
- **Memory tradeoff.** One entry (a small `Shared`, at most 12 limiter instants, an empty request-ID set when inactive, and an `Arc` clock) per canonical authority this process has successfully owned, kept until process exit. This is the deliberate P6-D-002 lifetime, not a leak: scopes are trusted local configuration, network input cannot create entries, entries are process-local, termination frees them, and evicting one would be exactly the reset P3 forbids.

**Lock order.** Registry → one session's `shared` (only in `register`, for the quiescence check, released before the lease is acquired). `State::end` takes only the registry. Router and transport code take their own locks and then `shared`, never the registry; nothing takes the registry while holding `shared`, a Router lock, or a run lock, and no ceremony work runs under the registry lock. The OS lease acquisition stays under the registry lock, as in P4, so registration remains serialized. There is no cycle.

**Exposure atomicity.** The guard (`active`), the budget (`remaining`), and every other `Shared` field stay in the one authority-wide mutex; `reserve` is unchanged (check `active`, check `remaining`, decrement, set `active`, in one critical section). Moving the mutex behind an `Arc` changes ownership, not locking.

## 6. Persistent / transient state table

| Field | Process-session persistent? | Registration-local? | Reason |
|---|---|---|---|
| `Shared::remaining` | **Yes** | No | P3 §11.1: at most 10 per owning process/session; never refilled by time, release, or re-registration |
| `Shared::start_limiter` (tokens, remainder, `last`, rolling instants) | **Yes** | No | P3 §11.1.1 "Lifetime and reset": owned by the process/session; changes only by elapsed-time refill and 60-second expiry |
| `limiter_clock` (session clock) | **Yes** (owned by `ProcessSession`, shared by each `State`) | No | One monotonic origin for every limiter instant of the session; a new registration cannot rebase or replace it |
| `Shared::active` (exposed-ceremony guard) | Stored in the persistent mutex | Its value is: must be `None` when no registration exists | Released by ceremony termination or drop; `Some` at reactivation means an unreleased guard, so `OwnershipUncertain` |
| `Shared::initiator_request_ids` | Stored in the persistent mutex | Must be empty at reactivation | Live Initiator reservations die with their ceremonies; non-empty means unreleased state, so fail closed |
| `Shared::pending_responders` | Stored in the persistent mutex | Must be 0 at reactivation | Owned by live Responder ceremonies |
| `Shared::preliminary_operations` | Stored in the persistent mutex | Must be 0 at reactivation | Held by `PreliminaryPermit`, which holds an `Arc<State>` |
| `Shared::pending_accepts` | Stored in the persistent mutex | Must be 0 at reactivation | Held by `AcceptPermit` (through its Router's executor) |
| `Shared::live_connections` | Stored in the persistent mutex | Must be 0 at reactivation | An uncertain transport teardown keeps its count for good, so a nonzero count after the last handle means fail closed |
| `Shared::incomplete_frames` | Stored in the persistent mutex | Must be 0 at reactivation | Held by a connection's frame assembler |
| `State::ownership` (OS lease) | No | **Yes** | Released by `State::end`; each activation acquires a new one |
| `State::identity` | (the registry key) | Copy per registration | Canonical bytes, identical for every registration of the scope |
| `State::live` | No | **Yes** | Makes `State::end` run exactly once (explicit release, then drop) |
| `ProcessSession::registration` | **Yes** | Describes the current registration | `Inactive`/`Active`/`Uncertain`; `Uncertain` is terminal for the process |

Keeping every `Shared` field in one persistent mutex preserves the single critical section that makes guard and opportunity reservation atomic. Every holder of a runtime resource (ceremony, permit, connection, Router) holds an `Arc<State>` directly or through a `CeremonyExecutor`, so when the last `State` ends nothing can still release a count; reactivation therefore checks that every runtime count is already zero and **never resets** one. A nonzero or poisoned value fails closed with `OwnershipUncertain` until process replacement.

## 7. Production changes

| File | Change |
|---|---|
| `core/src/lib.rs` | `REGISTRY` becomes `Mutex<HashMap<Vec<u8>, ProcessSession>>` behind `registry()`. Recovered capacity in these tests comes only from the limiter's existing equations (`total = remainder + (now − last)`, expiry at age ≥ 60 s), applied at the next evaluation on the session clock. **Process replacement (I5).** `every_new_process_starts_fresh_but_its_re_registration_does_not` runs `ownership_probe --session` twice in succession for one scope: each process prints `FIRST Ready { remaining: 10 }` (a genuinely new process, after the previous one exited, starts fresh) and then `AGAIN Ready { remaining: 9 }` (its own release and re-registration keeps its session). The test process, which never owned the scope, then registers it fresh. `graceful_shutdown_allows_replacement_with_fresh_volatile_budget` stays as it was and still passes. The START limiter is not observable through the public API, so a new process's fresh limiter is shown structurally: the registry is a process static, the first-acquisition branch is the only place `Shared::new()` (and so `StartLimiter::new()`) runs, and the unit test's never-owned scope exercises that branch.

**Failure and uncertainty (I7).**

- *Lease acquisition failure*: first acquisition creates nothing; reactivation leaves the entry `Inactive` with its accounting (above).
- *Release uncertainty*: with `FAIL_NEXT_RELEASE`, `release()` returns `OwnershipUncertain` and the session becomes `Uncertain`; the same through the final drop. Every later `register` returns `OwnershipUncertain`; the entry keeps 9. No fresh accounting is ever granted after an ambiguous release; process replacement is required (`an_uncertain_release_disables_the_session_without_resetting_it`).
- *Mutex poisoning*: `poisoned_shared_state_fails_closed` (extended) poisons `shared`, releases the authority (release does not need `shared`), and then `register` returns `OwnershipUncertain` twice. The poisoned entry is never discarded or rebuilt.
- *Held runtime resources*: a live-connection count left behind (what an uncertain transport teardown leaves) makes reactivation fail with `OwnershipUncertain`, entry kept (`a_held_runtime_resource_blocks_reactivation`). The P5 F-005 evidence test `p5_f005_003_adapter_initiator_exposure_panic_poisons_the_run` leaves exactly such a held live slot, which is why its four cases now each use their own scope (see §11).
- *Registry poisoning*: `register` maps it to `OwnershipUncertain`, as before; `State::end` then cannot mark the entry, which stays `Active` and so also refuses.

## 11. P3 / conformance effects

**P3: no change.** §11.1, §11.1.1 "Lifetime and reset", and §11.1.2(3)–(5) already state the process/session policy; the implementation now matches them, and no clarification was needed in the profile.

**Conformance: amended in place** under "*P6 amendment (P6-D-002, P6.3)*", with a sentence in the P6 header note. No row added or renumbered; the current normative set is still the 92 rows the P4 conformance closure mapped, and historical P4 counts stand.

| Row | Amendment (clarification of existing P3 semantics) |
|---|---|
| `R-OWNER-006` | The session is the owning OS process's; same-process release and re-registration (or dropping and re-creating handles) is not a restart; the budget continues; never more than 10 in one process |
| `R-OWNER-017` | Same-process release and re-registration is not a replacement process: it reacquires exclusive ownership and continues the existing budget and limiter; a failed or uncertain reacquisition leaves the accounting unchanged and never creates fresh accounting |
| `R-OWNER-022` | Neither is a release and re-registration while the native process stays alive (frontend or listener restart, UI reconnect, error recovery) |
| `R-OWNER-031` | Releasing the lease ends only the registration; only a replacement process starts fresh; an uncertain release disables rather than resets |
| `R-OWNER-038` | The "verified replacement owner" of (c) is a new OS process after the previous owning process terminated, never merely a new `TrustedAuthority` registration in the same live process, which falls under (a) |

`R-OWNER-012`, `021`, `034`, `035`, `037`, and `039` needed no change; their evidence is unchanged and extended by §9–§10.

**History.** P4 implemented and tested "owner session = registration lifetime" (P4 conformance closure note on `R-OWNER-006`; the integration assertions above). P5 identified the mismatch with current P3 (P5-F-003). P6-D-002 kept P3. P6.3 corrected the implementation and inverted the P4 assertions with comments saying so. The P4 closure and P5 documents are not rewritten.

**Test isolation.** With a process-lifetime registry, two tests sharing a scope would share accounting. A temporary instrumentation pass over the whole crate test binary logged every same-process reactivation: the only one was the intended `only_a_new_process_session_starts_a_fresh_limiter`. Three looping tests that re-created the same scope per case and expected fresh state (`windows_tcp::tests::connection_lifetime::ownerless_output_has_absolute_and_no_progress_deadlines` and `quiescent_connection_after_a_completed_ceremony_releases_its_live_slot`, and the P5.3 evidence test `p5_f005_003_adapter_initiator_exposure_panic_poisons_the_run`) now use one scope per case; their assertions are unchanged. No registry-clearing helper exists, test-only or otherwise.

Further checks:

- **Two active registrations.** `Active` is set only in `register` under the registry lock after a successful lease acquisition, and cleared only by the one `State` that holds that registration (`live` makes `end` run once, so an earlier registration's late drop cannot clear a newer one's `Active`). New ceremonies of an earlier registration cannot exist: reactivation needs every `Arc<State>` of the previous registration gone, and `authorize`/`reserve` compare `Arc` identity.
- **Stale active flag.** If `end` cannot lock a poisoned registry the entry stays `Active`; every later `register` already fails on the poisoned registry. A panic inside `register` after `Active` is set cannot happen: the only operations after it build the `State` (no fallible step).
- **OS bypass.** The quiescence check and lease acquisition both precede `Active`; mutation M7 (reactivation acquiring a different lock) is caught by two tests.
- **Deadlock.** Lock order registry → `shared` only in `register`, and `shared` is released before the lease call; `end` takes the registry alone, from `Drop` of the last `Arc<State>`, which never runs while that thread holds `shared` (every guard on `shared` borrows a live `Arc<State>`), a Router lock, or a run lock (those borrow a live Router, which holds an executor).
- **Uncertainty.** `Uncertain` is terminal; poisoning and held counts fail closed; no path converts `OwnershipUncertain` into a new entry or `Shared::new()`.
- **I6.** The map key is built only in `register_with` from the trusted scope; executors cannot reach the registry.
- **Interaction with P5-F-005 (recorded, not remediated).** An entropy panic that leaves a live slot or poisoned state held (the P5.3 F-005 evidence) now also makes same-process re-registration of that authority fail with `OwnershipUncertain` until process replacement, where P4 would have handed out a fresh registration. This is a more conservative consequence of the process-lifetime accounting, not a change to F-005's panic, unwind, Router `Admitting` claim, or ABI behavior. **P5-F-005 stays OPEN.**
- **Observation, not a finding.** During the first mutation pass, `router::tests::p5_concurrency_review::p5_router_race_002_close_versus_start_admission` failed once while mutation M4 was applied. That test never re-registers (the instrumentation pass showed no reactivation outside the intended test) and M4 cannot affect it. It did not reproduce in 30 isolated runs, 10 runs of the race module, and 22 further full suite runs (10 with default threads, 12 with `--test-threads=8`); its failure message was not captured. It is recorded as an unreproduced, load-sensitive observation in a test that uses a 10-second channel timeout.
