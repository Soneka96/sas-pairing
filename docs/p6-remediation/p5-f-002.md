## 1. Finding

An admitted connection with no inbound frame in progress had no finite lifetime. P5 reproduced three subcases with one root cause:

- **A, first header:** admitted, zero bytes, held forever.
- **B, idle after its run:** a run ended, no new frame begins, held forever.
- **C, owner-less retained output:** the run is gone, an outbound frame (its timeout CANCEL, or a local REJECT's or CANCEL's frame) stays retained for a peer that never reads, held forever.

With `MAX_LIVE_UNAUTHENTICATED_CONNECTIONS = 16`, sixteen silent peers held every live slot of the authority indefinitely, at no ongoing cost. Availability only; no authentication, budget, limiter, or secret effect.

## 2. Normative requirement

P3 §11.1.1 "Incoming connections" (the cap of 16 includes connections that have not sent a frame), "Incomplete frame reception" (finite header/whole-frame deadlines plus an idle-read deadline), and "Lifetime and cleanup" (temporary resources released on timeout); `R-OWNER-023`, `R-OWNER-026`. A finite bound was mandatory. Its model and values were not frozen.

## 3. Owner decision

[P6-D-001](decisions.md#p6-d-001--f-002-connection-lifetime): 10 s first-frame (pre-frame) deadline; 10 s quiescent deadline with no live run; 10 s absolute and 2 s no-progress deadlines for owner-less retained output; the existing 10 s / 2 s incomplete-frame deadlines unchanged; live ceremonies governed only by their ceremony deadlines. The model was implemented as decided; no value or rule was changed or added.

## 4. Root cause

P4 started every transport deadline at a frame's first retained byte and had no other connection-level bound:

| Subcase | Old behavior (at `e21ff0b` / `57131ad`) |
|---|---|
| A | `TransportConnection::poll_frame_deadlines` returned at once, reading no clock, when no frame was partial (`transport.rs:299–307`). Activation recorded no instant. Nothing else in the transport, the adapter, or the owner loop ever closed a frameless connection. |
| B | When a run ended (deadline, success, REJECT, CANCEL), only the run's route was removed. The connection kept its live count until an explicit close, EOF, or failure; a connection with no route had no deadline. |
| C | A terminal run's best-effort CANCEL (or a local REJECT's or CANCEL's frame) was retained with `owner: None`. The adapter's owner preflight in `on_writable` checks only owned frames, and the owner-loop sweep only polled frame and ceremony deadlines, so an owner-less frame to a peer that never reads (and the socket reads it blocks) stayed forever. |

All three are the same missing layer: no connection-level lifetime outside an incomplete frame.

## 5. Lifetime model

One explicit state, `transport::Lifetime`, owned by the connection's `TransportConnection` and evaluated on its existing injected monotonic transport clock. It is re-derived at every evaluation from what the connection holds: whether its Router session has a live run (an installed `RemoteCeremony`), whether the adapter retains an outbound frame, and whether a frame is incomplete. It is never derived from socket activity.

| State | Holds | Governing deadline | Refresh | On expiry |
|---|---|---|---|---|
| `WaitingForFirstFrame` (`Lifetime::FirstFrame`) | Nothing yet since activation | 10 s from activation | Never | `FirstFrameTimeout` |
| `FrameInProgress` (`Partial` present) | An incomplete inbound frame | 10 s whole frame, 2 s no progress (unchanged) | Retained-byte progress, 2 s deadline only | `WholeFrameTimeout` / `IdleTimeout` |
| `LiveRun` | At least one installed run on the session | The runs' ceremony deadlines (5 min absolute, 60 s inactivity, 60 s pending) | As P3 §11.3 / §11.1.1 | The run ends; the connection re-evaluates |
| `QuiescentNoRun` (`Lifetime::Quiescent`) | No run, no incomplete frame, no retained output | 10 s from losing its last run or its output | Never | `QuiescentTimeout` |
| `OwnerlessOutput` | A retained outbound frame and no live run | 10 s absolute and 2 s without write progress, from becoming owner-less | Write progress of at least one byte, 2 s deadline only | `RetainedOutputTimeout` / `RetainedOutputIdleTimeout` |
| `Closed` (`ended`) | Nothing | — | — | Every call reports `Closed` |

Transitions (`Lifetime::settle`, the whole table; `frame_begun` only renames `FirstFrame` to `Quiescent` with the same origin):

| From | Live run? | Retained output? | To |
|---|---|---|---|
| any | yes | any | `LiveRun` |
| `OwnerlessOutput` | no | yes | unchanged (origins kept) |
| `FirstFrame`, `Quiescent`, `LiveRun` | no | yes | `OwnerlessOutput { since: now, progress: now }` |
| `FirstFrame`, `Quiescent` | no | no | unchanged (origin kept) |
| `LiveRun`, `OwnerlessOutput` | no | no | `Quiescent { since: now }` |

Rules that make the model safe:

- **Only resource changes move an origin.** A live run ending or retained output appearing or leaving is a change of what the connection holds. A complete frame that leaves no live run (a refused START, for example) is not: the earlier first-frame or quiescent origin applies at once when the frame completes, so frames that create no live work can never extend a connection.
- **Frame hand-over.** A first byte accepted before the first-frame or quiescent deadline gets the full unchanged frame window. The lifetime underneath is still re-derived during the frame but not enforced.
- **Live-run precedence.** With a live run and no incomplete frame, no connection timer applies and no transport clock reading is taken, exactly as before P6. Ceremony deadlines decide.
- **Teardown first.** A beginning frame is checked against the lifetime before any byte is taken (`feed`), the owner-loop sweep polls the lifetime before any socket I/O in a drive, and the adapter checks it before every write of a retained frame. An expired connection is torn down; nothing more is read, dispatched, or written.
- **Observation.** A state change is observed at the next evaluation: the owner loop's sweep runs at least once per drive (each drive waits at most 250 ms), so a quiescent or owner-less origin lags the true change by at most one drive and is never extended by peer behavior.
- **Exact boundaries.** Expiry is `elapsed >= deadline`. A clock reading that is missing, earlier than one already used, or before an origin fails the connection closed (`ClockUnavailable`).
- **F-001 readiness.** P6.1 leaves `POLLHUP` handling unchanged.

## 6. Production changes

| File | Change | Responsibility |
|---|---|---|
| `core/src/transport.rs` | `Lifetime` state and transition table; `OutboundState`; four named deadline constants (`FIRST_FRAME_DEADLINE`, `QUIESCENT_DEADLINE`, `RETAINED_OUTPUT_DEADLINE`, `RETAINED_OUTPUT_IDLE_DEADLINE`); four `TransportError` reasons; activation instant as the first origin (no usable clock: nothing becomes live); `poll_frame_deadlines` replaced by `poll_connection_deadlines(outbound)`; the lifetime check before a frame begins in `feed`; `record_output_progress` | Owns every connection deadline, the clock, and the one teardown |
| `core/src/router.rs` | `Router::session_has_live_run`: read-only, one table critical section, one ordered-map seek | Answers the only fact the transport cannot know itself |
| `core/src/host.rs` | Pass-throughs `poll_connection_deadlines(outbound)` and `record_output_progress`; the lifetime is checked before a local Initiator start, so no new run starts on an expired connection | Thin dispatch layer, unchanged role |
| `core/src/windows_tcp.rs` | `poll_connection_deadlines()` reports whether a frame is retained; `on_writable` checks the connection deadlines before writing and reports partial-write progress | Reports the adapter-only facts (retained output and write progress) |
| `core/src/windows_owner_loop.rs` | The sweep calls `poll_connection_deadlines()` | Scheduling only: one bounded sweep before I/O, as before |

**Why the transport owns it.** The transport already owns the connection's monotonic clock, its "never go backwards" guard, the frame deadlines, and the one teardown that settles the Router session before releasing the live count. Putting the lifetime there keeps all connection timing arithmetic in one type and one module, reuses that teardown unchanged, and keeps the rule generic (socket-free) for any future adapter. The adapter supplies only what it alone knows. The owner loop keeps its bounded drive (sweep, wait, sweep, at most one socket operation per connection, at most one accept); it gains no timer and no inner loop. No public API was added: everything is crate-private.

## 9. P3 and conformance effects

- **P3 §11.1.1** gains one table row, "Connection lifetime", that records the P6-D-001 policy and distinguishes the five cases: (1) admitted before a frame, 10 s; (2) incomplete inbound frame, the existing 10 s / 2 s; (3) live ceremony, its existing deadlines; (4) quiescent, 10 s; (5) owner-less retained output, 10 s absolute / 2 s no progress. It states that meaningless activity refreshes nothing and that a frame leaving no live ceremony keeps the earlier origin. No wire format, cryptography, ceremony authentication, or other control changed.
- **`R-OWNER-023`** is amended in place (marked *P6 amendment, P6-D-001*) to require the connection lifetime and the 16-idle release. No row was added, none renumbered; the current normative set is still the 92 rows the P4 conformance closure mapped, and that closure's historical statements stay correct as P4 history. The conformance file records the amendment rule in a header note.
- `R-OWNER-026` (release exactly once on transport failure) is unchanged and is exercised by every expiry path above.

## 10. Follow-up adversarial review

The invariant under attack is not "every connection dies within 10 s" but "no resource state exists without a finite governing deadline".

| Attack | Result |
|---|---|
| One byte just before the first-frame deadline | The frame gets its unchanged 10 s / 2 s window. If it leaves no live run, the first-frame origin applies at once: closed. At most 10 s + 10 s without a run |
| Repeated WouldBlock / Interrupted reads and writes | No progress, no refresh (`meaningless_socket_activity…`, `ownerless_output…` Refused case) |
| Exact duplicates | Exist only while a run lives (`LiveRun`, ceremony-governed); after the run, a repeat START is a new admission attempt |
| Malformed frames, wrong request IDs, wrong-state input | Malformed: immediate close (unchanged). A non-START frame with no run: session-fatal close (unchanged). Wrong-state input to a live run: the ceremony decides, and it refreshes no ceremony deadline |
| Repeated complete frames that create no run (refused STARTs) | Never move the origin (`frames_that_create_no_live_run…`) |
| Owner-less output with one byte of progress before each 2 s expiry | Capped at exactly 10 s absolute (`Trickle`) |
| Cycling quiescent ↔ partial frame | The origin never moves; the frame window is the only extension and is used once |
| Repeated run creation and termination | Each run needs a START admission charged to the authority-wide limiter (burst 4, 12 per 60 s) and one of 4 pending slots, and each run is bounded by its ceremony deadlines. This keeps a connection alive only with ongoing, limiter-charged traffic, which is the accepted P5-F-012 behavior, not an unbounded state |
| Owned output to a peer that never reads | Bounded by the owning run's deadlines; its replacement CANCEL is owner-less output (now released, `p5_tcp_out_001`) |
| Backwards or failed transport clock | Fails closed (`a_no_run_connection_with_a_backwards_or_failed_clock…`) |
| Reconnect churn | Each new connection has its own finite first-frame deadline; holding slots now needs continuous reconnection, an ongoing cost the finite caps do not claim to prevent (P3: the numeric defaults are not DoS guarantees) |

**Rebuilt connection resource table.**

| State | Resource held | Governing deadline | Refresh rule | Release path |
|---|---|---|---|---|
| Waiting for first frame | 1 live slot, 1 Router session, ≤ 8 KiB read suffix | 10 s from activation | None | Teardown on expiry, EOF, error, or close |
| Frame in progress | + 1 incomplete-frame slot, ≤ 64 KiB partial frame | 10 s whole, 2 s no progress | Byte progress (2 s only) | Frame complete, or teardown |
| Live run | + the run's own resources (pending slot, permit, guard, or reservation) and possibly one owned retained frame ≤ 64 KiB | Ceremony deadlines: 5 min absolute, 60 s inactivity (suspended only at the SAS), 60 s pending | P3 §11.3 progress rules | The run ends by deadline, result, REJECT, CANCEL, or protocol failure; then the connection re-evaluates |
| Quiescent, no run | 1 live slot, 1 session | 10 s from the run's end or the output's release | None | Teardown on expiry |
| Owner-less retained output | + 1 retained frame ≤ 64 KiB | 10 s absolute, 2 s no write progress | Write progress (2 s only) | Frame written (then quiescent) or teardown |
| Closed | Nothing (or, if Router cleanup was uncertain, the count deliberately held, unchanged from P4) | — | — | — |

There is no longer any row of the form "live connection, deadline = none" except the live-run row, which a live ceremony with its own finite deadlines governs. The uncertain-cleanup residue is the pre-existing fail-closed design (capacity held when cleanup cannot be established), not a lifetime gap.

**Required questions.**

| | Question | Answer |
|---|---|---|
| A | Can 16 silent peers still permanently exhaust the live cap? | **No.** Released at exactly 10 s (transport and owner-loop regressions) |
| B | Can a peer keep one slot forever with slow first-frame bytes? | **No.** One frame window after the first-frame deadline at most; a frame that leaves no run closes it at once |
| C | Can a completed run leave an idle connection forever? | **No.** 10 s quiescent deadline after the run ends (real-ceremony regression) |
| D | Can owner-less pending output live forever? | **No.** 10 s absolute, 2 s without progress |
| E | Can the new 10 s timer kill an active SAS comparison prematurely? | **No.** A live run suspends every connection timer; four silent minutes at the SAS then succeed |
| F | Did budget, guard, or limiter behavior change? | **No.** No accounting code changed; the regressions assert unchanged charges and statuses |
| G | Did wire or crypto change? | **No.** No protocol, codec, ceremony, or crypto code changed |

**Observation (not a finding).** An orphan `Admitting` claim left by a caught entropy panic ([P5-F-005](../p5-security-review/findings.md#p5-f-005)) is not a live run, so such a connection is now also released by the quiescent deadline instead of being held. The P5-F-005 characterization tests do not advance the transport clock and pass unchanged; P5-F-005 stays OPEN and undecided.

**No new finding** was identified. The next free P5 ID stays P5-F-023.

## 12. Final disposition

**P5-F-002 → REMEDIATED-IN-P6 (P6.1).** Every closure condition holds: owner decision P6-D-001 recorded before the code; production fix in `1ce0753`; unit and regression tests; the P5 reproducer passing as a normal test; the follow-up adversarial review above; P3 §11.1.1 and `R-OWNER-023` synchronized; documentation synchronized; full CI green. P5's discovery text in [findings](../p5-security-review/findings.md#p5-f-002) is preserved with a P6 remediation note appended.

**F-001 dependency.** P6.2 will treat `POLLHUP` without `POLLERR`/`POLLNVAL` as readable until EOF and keep writing retained output to a half-closed peer. The P6-D-001 lifetime is what bounds the connection it then keeps open: a half-closed peer that never sends EOF or never drains output is governed by the first-frame, quiescent, owner-less-output, or ceremony deadlines, so draining through hang-up cannot create an unbounded half-closed connection. The adapter's write preflight already runs the connection deadlines before every write, which is where P6.2's writes will go.
