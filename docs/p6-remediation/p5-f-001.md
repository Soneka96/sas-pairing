## 1. Finding

The experimental Windows owner loop treated `POLLHUP` like `POLLERR` and closed a connection before any read or write. Windows reports `POLLHUP` together with readable data after a peer's graceful close or `shutdown(Send)`, so the loop discarded:

- **read side:** complete frames the peer sent before its FIN (a START, or two frames, all `Readiness(0x0102)` with nothing dispatched), and complete frames already read into the adapter's retained suffix;
- **final ACK:** with the loop as Responder, an Initiator that wrote its final `INITIATOR_FINISH_ACK`, obtained its result, and closed at once left the Responder with no result, the outcome P3 §9 attributes to message loss, although the ACK had been delivered;
- **write side:** after a peer half-close the loop reported `POLLHUP | POLLWRNORM` (`0x0012`) and dropped its own retained output, although a half-closed peer still receives.

Every case failed closed (no false result, no accounting effect). LOW, robustness and interoperability.

## 2. Existing normative behavior

P3 already required what the fix delivers; P6.2 adds no protocol rule:

- §3.1 and `R-WIRE-025`: received transport input is stream input, assembled into complete canonical frames.
- §9 and `R-MAC-012`: the Responder's result is its verification of `INITIATOR_FINISH_ACK`. "A disconnect before a participant's local condition is met produces failure locally and no result": the condition is evaluated on what was received before the disconnect, and a graceful end of stream follows the bytes sent before it.
- §11.2: ending a connection is one teardown, whatever ended it.

The P4 rule "hang-up closes without I/O" was an adapter policy (the owner-loop module docs and core README), not a P3 requirement.

## 3. P6-D-003 decision

[P6-D-003](decisions.md#p6-d-003--graceful-tcp-hang-up-handling), for established connections:

| Readiness | Meaning | Handling |
|---|---|---|
| `POLLERR`, `POLLNVAL` (with anything) | Hard failure | Close immediately, before any read or write, whatever else is set or retained |
| `POLLHUP` without `POLLERR`/`POLLNVAL` | Graceful peer FIN or send-half-close: the peer's earlier bytes may still be readable and the peer may still receive | Not a failure. Never discards readable, retained, or pending data. Read toward EOF when nothing is retained for writing; write a retained frame on writable readiness |
| Listener `POLLERR`, `POLLHUP`, `POLLNVAL` | Listener failure | Unchanged: the listener is dropped |

The connection closes only at a read that returns EOF (`TcpError::PeerClosed`), on an actual socket error, on `POLLERR`/`POLLNVAL`, or by the existing deadline and teardown policy. One socket operation per connection per drive; no hang-up timer; deadlines keep their precedence; a close is transport information only and never creates or confirms a result.

## 4. Root cause

At `79fc2dc` (`core/src/windows_owner_loop.rs`):

```rust
const FAILED: i16 = POLLERR | POLLHUP | POLLNVAL;
...
let outcome = if revents & FAILED != 0 {            // close, no I/O
    ...
} else if live.tcp.write_pending() && revents & POLLOUT != 0 {
    Ok(live.tcp.on_writable())
} else if !live.tcp.write_pending() && (revents & POLLIN != 0 || live.tcp.input_buffered()) {
    Ok(live.tcp.on_readable())
} else { ... }
```

One mask served both the listener and connections, and `POLLHUP` ranked with the hard failures ahead of both I/O branches:

| Pending output | Readiness | Old action |
|---|---|---|
| any | any containing `POLLERR`, `POLLHUP`, or `POLLNVAL` | Close, no I/O (`ConnectionEnd::Readiness`) |
| yes | `POLLOUT` | One write |
| no | `POLLIN`, or retained input | One read step |
| otherwise | — | Nothing |

- **Read-side loss:** `POLLHUP | POLLRDNORM` hit the first branch, so readable bytes and the retained suffix were dropped by the teardown.
- **Write-side loss:** `POLLHUP | POLLWRNORM` hit the first branch, so the retained frame was discarded unwritten.
- **Final-ACK consequence:** the Responder's run was torn down with its ACK unread: the Initiator had a result and the Responder had none, without any message having been lost.

The adapter was already correct: `on_readable` serves the retained suffix before one bounded OS read and maps `read == 0` to `PeerClosed`; `on_writable` writes one bounded chunk from the exact offset; WouldBlock and Interrupted change nothing. Only the loop's scheduling was wrong.

## 5. Readiness model

Per established connection, after the deadline sweep (a connection whose sweep reported an event does no I/O in that drive):

| Pending output | Readiness | Action |
|---|---|---|
| any | contains `POLLERR` | Close before any I/O: `ConnectionEnd::Readiness(flags)` |
| any | contains `POLLNVAL` | Close before any I/O: `ConnectionEnd::Readiness(flags)` |
| yes | `POLLOUT` | One `on_writable` |
| yes | `POLLHUP \| POLLOUT` | One `on_writable` |
| yes | `POLLHUP` only | No socket I/O, no close; the governing deadline bounds it |
| yes | `POLLIN` (with or without `POLLHUP`) | No read: write backpressure unchanged |
| no | `POLLIN` / `POLLRDNORM` | One `on_readable` |
| no | `POLLHUP \| POLLIN`, `POLLHUP \| POLLRDNORM` | One `on_readable` |
| no | `POLLHUP` only | One `on_readable` toward EOF |
| no | retained suffix (any non-failure readiness, or none) | One `on_readable` step (suffix first, no OS read) |
| no | `POLLOUT` only, nothing retained | Nothing |
| any | `0`, nothing retained | Nothing |

The adapter then decides as before: retained input first, then at most one OS read; bytes become frames; `0` is `PeerClosed` through the one teardown; WouldBlock is no progress. `POLLIN` in `windows-sys` is `POLLRDNORM | POLLRDBAND`, so `POLLRDNORM` alone is readable.

## 6. Production changes

| File | Change | Why |
|---|---|---|
| `core/src/windows_owner_loop.rs` | `FAILED` split into `CONNECTION_FAILED = POLLERR \| POLLNVAL` (connections) and `LISTENER_FAILED = POLLERR \| POLLHUP \| POLLNVAL` (listener, unchanged behavior); new `READABLE = POLLIN \| POLLHUP` for the read branch; module, `ConnectionEnd::Readiness`, and failure-scope docs updated | The whole remediation: the precedence is now hard failure → pending write → readable or hang-up read → nothing |

`core/src/windows_tcp.rs` is **not** changed: the owner-loop fix exposed no adapter defect. No crypto, ceremony, protocol, router, host, transport, or accounting code changed.

**Bounded work.** Per drive, unchanged: one deadline sweep before the wait, at most one `WSAPoll` (17 sockets, ≤ 250 ms), one sweep after the wait, at most one socket operation per ready connection (one `on_writable` *or* one `on_readable`, never both, never looped), at most one accept. There is no drain-to-EOF or read-until-WouldBlock loop; a hang-up is drained across drives (`retained_input_is_served_frame_by_frame_under_hang_up_before_eof` asserts the exact read and write counts per drive).

## 9. P3 / conformance effects

- **P3:** no normative change. §3.1 (stream input assembled into frames), §9 (the Responder's result is verifying the received final ACK; a disconnect denies a result only before the local condition is met), and §11.2 (one teardown) already require the fixed behavior; nothing in P3 lets a graceful end of stream discard bytes received before it. The P4 "hang-up closes without I/O" wording was adapter documentation, now corrected in the module docs and the core README.
- **Conformance:** two existing rows are amended in place, marked *P6 amendment (P6-D-003)*, and no row is added or renumbered, so the normative set is still the 92 rows the P4 conformance closure mapped (that closure's statements stay correct as P4 history):
  - `R-WIRE-025` (fragmented valid frame reconstructed): bytes received before the peer's graceful end of stream (FIN or send-half-close) are ordinary input; complete frames are dispatched, and EOF never completes a partial frame.
  - `R-MAC-012` (positive `INITIATOR_FINISH_ACK` authentication): the same holds when the Initiator closes immediately after sending the final ACK.
- **Wire, cryptography, accounting:** unchanged. No frame, field, encoding, vodozemac use, transcript, commitment, SAS, MAC, completion or CANCEL authentication, budget, guard, limiter, pending cap, preliminary permit, authorization, request-ID reservation, or routing code changed. Only the owner loop's readiness classification did.

|---|---|---|

Further checks:

- **No result from a close.** Results still come only from `HostConnection` dispatch of a verified frame or from `confirm_sent` after a complete local write; the owner loop never creates one, and `PeerClosed` goes through the unchanged teardown (no result, no CANCEL, no refund). Every new test asserts no stray result.
- **Duplicates.** A frame is consumed from the suffix exactly once (`suffix.start += consumed`); the counts in `retained_input…` and the real two-frame test show one dispatch per frame.
- **EOF ordering.** EOF is read only when no frame is retained for writing, so a frame produced by the last input, including a loop Initiator's final ACK after a Responder half-closes once it sent `RESPONDER_FINISH_ACK`, is written before EOF is consumed. The write path is the same for every retained frame, and a final ACK is confirmed only by the write of its last byte (unchanged, `the_loops_final_ack_result_appears_only_in_the_drive_that_writes_its_last_byte`).
- **EOF semantics unchanged.** EOF still ends the whole connection, as in P4. A half-closed peer can still receive what the loop produces from the input it sent, but a later loop frame that needs a local action (for example after an SAS decision) is not awaited after EOF. P6-D-003 does not invent half-duplex session semantics.
- **Bounded drive and busy-loop.** Each drive does at most one operation per connection. Across drives, Windows reports hang-up level-triggered and `WSAPoll` then returns without waiting. A hung-up connection that makes no progress therefore makes repeated `drive_once` calls cheap but immediate. On real TCP this needs either a read that never reaches EOF after FIN (not expected: after the FIN, reads return the remaining bytes and then `0`) or retained output with hang-up but no writable readiness (the peer's receive window and the local send buffer both full; the loop's frames are small, so this needs a peer that deliberately stops reading). Both cases are bounded by the governing deadline in §10: at most 10 s first-frame or quiescent, 2 s / 10 s owner-less output, and for output a live run owns, its ceremony deadlines (at most the 5-minute absolute deadline, because inactivity is suspended while an SAS awaits a human decision). This is within P6-D-003, which adds no hang-up timer and no sleep. It is recorded here for the outer-driver integration (P7), not filed as a finding.
- **Accounting.** The matrix and every regression assert the START-limiter charge, pending Responders, live and incomplete counts, request-ID reservations, routes, and the budget. A hang-up changes none of them by itself; teardown releases each once.

**No new finding** was identified. The next free P5 ID stays P5-F-023.
