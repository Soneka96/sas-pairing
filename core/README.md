# Native Rust security core

This increment implements canonical scope registration, Windows process ownership, a trusted authorization issuer, a shared ceremony guard, a volatile ten-opportunity budget, terminal cleanup, a standalone canonical P3 remote frame codec, and an internal owner-gated remote ceremony through SAS establishment, local human comparison, the authenticated BOOTSTRAP_MAC approval exchange, the three-message authenticated completion handshake ending in a crate-private, local, ceremony-scoped `PairingResult`, authenticated post-SAS `CANCEL`, the P3 ceremony absolute and inactivity deadlines, honest Initiator request-ID generation with an authority-wide active reservation, and the core-owned P3 §11.1.1 pre-exposure resource controls, including the authority-wide START admission limiter, crate-private P3 §4 pre-establishment routing bound to a local session handle plus request ID, a crate-private, socket-free model of the P3 §11.1.1 transport admission and bounded frame-assembly controls, a crate-private, socket-free host layer that dispatches each complete transport frame to the Router and routes each trusted local ceremony action to exactly one run, an experimental crate-private Windows adapter that drives that host over one already-connected TCP stream with bounded nonblocking reads and partial writes, and an experimental crate-private, synchronous Windows owner loop that hosts the connections accepted from one already-bound listener with bounded `WSAPoll` readiness. Parsing alone cannot acquire an authority, authorize a ceremony, or reserve an exposure opportunity. There is still no public pairing result, SDK, or transport API. Per-requirement conformance evidence for the current normative cases is indexed in [P4 conformance closure](../docs/p4-conformance-closure.md), which also lists the remaining partial, manual, external, and limitation items; this is experimental evidence, not production-security approval or formal verification.

The codec uses the selected experimental profile at `docs/p3-vodozemac-ceremony-profile-draft.md` §§3, 4, and 6. It validates framing, ordered field counts, profile/version, field lengths, bootstrap grammar, role codes, and cancellation reason codes. A crate-private START-candidate classifier shares the same outer-frame parser and stops at the P3 §11.1.1 candidate boundary (see below). The codec itself performs no cryptographic validation. The crate-private ceremony state machine composes it with private crypto and existing authority admission, through the finish handshake to each role's local success point. Shared contexts use exact byte comparison. This layer accepts an optional exact-bootstrap expected-peer constraint; open/expected-peer selection and provenance remain consumer policy, without a generic policy language. The honest Initiator generates its own request ID (see below); fixed-ID constructors exist only under `#[cfg(test)]` for deterministic vectors.

The key-exchange slice exercises R-OWNER-001–005, 007, 010, 016, 029, 033 and R-WIRE-018, 022–024, 026. The coverage notes in each section below are per-layer summaries; the exact tests for every current row are in the closure index. The socket-free transport controls, host dispatch, and the cooperative owner loop that drives deadlines (there is no timer thread or scheduler) are described below. Busy contention uses the existing shared authority guard and budget.

## Honest Initiator request IDs

The crate-private honest Initiator constructor takes only the executor, its admission `Ceremony`, the local canonical bootstrap, and an optional expected peer; the application never supplies or chooses the request ID. The core draws exactly 16 raw bytes from the OS CSPRNG (`getrandom::fill`; Windows `ProcessPrng`) through a minimal crate-private generator boundary that tests replace with scripted candidates. If the OS source fails, construction fails closed with `RequestIdGenerationFailed`: no START, reservation, opportunity, guard, ephemeral key, or ceremony exists. OS error details are not retained.

Before START is built, the candidate is atomically checked and inserted, in one critical section of the authority's existing shared state, into that authority's set of active local Initiator request IDs; the lock is not held while generating. A collision with another live local Initiator of the same authority is an internal retry with a fresh candidate, never an error or protocol event, and no retry limit is imposed; an OS failure still fails at once. `start()` can therefore only return START bytes whose exact ID is already reserved. The reservation is owned by that ceremony's admission `Ceremony` (at most one, never transferred; Responder ceremonies own none) and is released exactly once by the existing terminal cleanup: protocol failure, timeout, local reject/cancel, verified peer CANCEL, clock failure, explicit termination, Initiator success after the confirmed final-ACK send boundary, construction failure after reservation, or drop. Returned best-effort CANCEL bytes and the immutable `PairingResult` keep the ID as historical data only, and a later ceremony may reserve the same ID again; no historical IDs are kept. If the shared lock is poisoned, reservation fails with `OwnershipUncertain` and an existing reservation stays conservatively held rather than being reported released.

The reservation is pre-exposure routing state: it spends no opportunity, does not acquire the exposed-ceremony guard, and does not alter the ownership lease or deadlines, so several distinct pre-exposure Initiator IDs may coexist until resource admission limits them. Different authorities have independent namespaces, and the set is volatile: it is never persisted or written to the lock file, and a replacement owner starts empty. The ID flows unchanged as raw bytes through every message and the result, but it is never ceremony identity, authentication, authorization, a freshness proof, an approval target, or trust; `ceremony_identity` stays authoritative after establishment. Incoming peer request IDs remain canonical opaque 1–64-byte values with no length, entropy, or uniqueness requirement and are never reserved in this set. Active local Initiator ID reservation is implemented, and the session-bound router (see below) registers each routed Initiator under its local session and generated ID before START is returned; there is still no lookup by request ID alone.

## Local SAS comparison boundary

A crate-private `SasPresentation` (the 32-byte transcript-derived `ceremony_identity` and the complete `NNNN NNNN NNNN` decimal SAS) exists only in `AwaitLocalApproval`, after legal key-exchange ordering, commitment verification, contributory DH, and transcript identity are fixed. Local MATCH, MISMATCH/REJECT, and CANCEL each take the exact `ceremony_identity`; a request ID is never an approval target, so equal request IDs cannot transfer approval to another transcript. A decision for any other identity, or when no SAS is live, is rejected without effect. MATCH enters `LocallyApprovedAwaitingAuthentication`, which is not success: it retains the vodozemac session, six raw SAS bytes, identity, role, request ID, and both canonical bootstraps internally, emits nothing by itself, and neither issues exposure `Authorization` nor reserves, consumes, or releases the guard or an opportunity. A repeated MATCH reports `AlreadyRecorded` without effect. REJECT, local CANCEL, generic termination, protocol failure, and drop are terminal: they drop the SAS session and local approval before the existing cleanup releases the guard and never refund the consumed opportunity. Only REJECT and local CANCEL of a live established SAS return a best-effort authenticated `CANCEL` (see below); generic termination, protocol failure, and drop emit no wire message. If guard release is uncertain, the SAS is still invalidated and the guard stays held.

This exercises the local parts of R-OWNER-007–011 (terminal irreversibility, stale/wrong-identity callback rejection, SAS withdrawal, invalidation before guard release, no resumption).

## BOOTSTRAP_MAC approval authentication

After local MATCH, a crate-private `emit_bootstrap_mac` produces exactly one canonical `BOOTSTRAP_MAC / 0x05` frame (exact request ID, local role code, raw 32-byte tag); a repeated call returns `AlreadyEmitted` with no bytes and no MAC work. Before local MATCH it fails with no output and no effect; it never approves. The tag is vodozemac `EstablishedSas::calculate_mac(input, info)`, where `input` is unpadded Base64url of the non-wire `0x33` approval frame (domain, profile ID, `u16be(1)`, sender role, `ceremony_identity`, six raw SAS bytes, the sender's own complete canonical bootstrap) and `info` is `sas-pairing-vodozemac-profile-draft-01/mac/` plus unpadded Base64url of the `0x31` context (domain, profile ID, version, `match-approve-bootstrap`, sender role, receiver role, `ceremony_identity`). Both generated strings use checked sizing and the 65,536-byte cap including the prefix. No project-owned HMAC, HKDF, or comparison exists; the DH secret and `EstablishedSas` stay private.

`receive_bootstrap_mac` decodes, applies exact/changed-duplicate rules, requires a post-SAS state with the peer MAC still pending, checks the request ID and that the wire role equals the expected peer role, then reconstructs the peer's approval statement from retained state (peer role, `ceremony_identity`, six SAS bytes, the retained peer bootstrap) and verifies with vodozemac `verify_mac`. A verified peer MAC records only the peer's approval: arriving before local MATCH it leaves the SAS displayed and awaiting the human, and never generates our MAC. Either order reaches `ApprovalsAuthenticatedAwaitingCompletion`, which is not success: the vodozemac session and ceremony data are retained for the finish handshake, the guard stays Busy, and the consumed opportunity stays consumed. An exact duplicate of the accepted peer frame is ignored without retaining another copy or repeating verification. A changed duplicate, wrong role, request-ID mismatch, codec failure, MAC mismatch, wrong-state arrival, local REJECT, or local CANCEL is terminal: the SAS session and approval state are dropped before the guard is released, and nothing revives the run. Local CANCEL still emits nothing.

The deterministic test compares both directions' approval frames, context frames, Base64url inputs, MAC info strings, and `BOOTSTRAP_MAC` wire framing against the JSON fixture. The fixture's raw tags derive from fixed test-only X25519 private inputs that vodozemac 0.11.0 cannot load, so those tags are not recomputed; live two-party ceremonies verify actual MAC generation and verification in both orders, and binding tests show verification fails if the reconstructed identity, SAS bytes, sender bootstrap, sender or receiver role, direction, or purpose changes. This exercises the local, pre-completion portions of R-MAC-005–009 and the BOOTSTRAP_MAC instances of R-WIRE-016–017 and R-WIRE-020–024, while preserving R-OWNER-005 and 007–010. R-MAC-001 remains partial because fixed-secret SAS bytes and tags are not reproducible through the vodozemac API; R-MAC-004 is shown with live state instead (each SAS context field changes the live SAS and breaks the approval MAC).

## Authenticated completion and local PairingResult

Completion starts only from `ApprovalsAuthenticatedAwaitingCompletion`. It uses the retained `EstablishedSas`, consumes no additional opportunity, needs no new exposure `Authorization`, acquires no second guard, and keeps the one guard held until local terminal cleanup. The only order is `INITIATOR_FINISH / 0x06` (I→R), `RESPONDER_FINISH_ACK / 0x07` (R→I), `INITIATOR_FINISH_ACK / 0x08` (I→R); there is no fourth message or transport acknowledgement. Each carries the exact request ID, the authoritative `ceremony_identity` as its 32-byte transcript digest, and a raw 32-byte vodozemac tag. The tag input is unpadded Base64url of a non-wire `CompletionAuthFrame` (`0x35`/`0x36`/`0x37`: domain, profile ID, `u16be(1)`, sender role, receiver role, `ceremony_identity`, then the purpose `initiator-finish`/`responder-finish-ack`/`initiator-finish-ack` last); the info is `sas-pairing-vodozemac-profile-draft-01/mac/` plus unpadded Base64url of the `0x32` context (domain, profile ID, version, purpose, sender role, receiver role, `ceremony_identity`). The same capped Base64url helper as BOOTSTRAP_MAC generates both strings.

Only the Initiator may call `emit_initiator_finish`, and only once approvals are authenticated; a repeat is `AlreadyEmitted` with no MAC work, and every refusal (Responder role, approvals pending, no live SAS) has no effect. `receive_completion` applies exact/changed-duplicate rules, then requires that this role and state expect exactly this step, checks the request ID, explicitly compares the transcript digest with the local `ceremony_identity`, and verifies the tag against the auth frame and context reconstructed from local state, all before any transition. R answers a valid `INITIATOR_FINISH` with exactly one `RESPONDER_FINISH_ACK` and has no result yet. After verifying `RESPONDER_FINISH_ACK`, I produces exactly one `INITIATOR_FINISH_ACK`, returns it, and enters `AwaitInitiatorFinishAckSend` holding those exact bytes, the live session, and the guard, with no result. Producing or returning the final ACK is not success. The Initiator's local success point is the crate-private `confirm_initiator_finish_ack_sent(bytes)`: an internal transport-adapter contract that the adapter MUST call only after its local send operation accepted exactly that frame. It is a local send boundary, not delivery, peer-verification, peer-success, or storage confirmation, and the ceremony layer performs no network I/O; the Windows TCP adapter below calls it only after the complete local socket write. Any other bytes (including another ceremony's final ACK) or a call with no pending frame is rejected without effect and never creates a result; after success it is `Completed`. An exact duplicate `RESPONDER_FINISH_ACK` while the send is pending is ignored with no second ACK or MAC work, and local termination before confirmation fails the run with no result. The Responder's success point, unchanged, is verifying `INITIATOR_FINISH_ACK`. This is local verified completion, not atomic bilateral success, and either endpoint may be the only one holding a `PairingResult` (P3 §9, decision [P6-D-005](../docs/p6-remediation/decisions.md#p6-d-005--local-completion-and-final-ack-deadline-boundary)): if the final ACK is lost after I's send, I holds a result while R still waits with its guard and session and has none; conversely, if I's deadline is reached after its complete final ACK was written but before the confirmation, I times out with no result while R may verify that ACK and hold the only result. Confirmation is judged at the confirmation instant, never backdated to the write. A result never proves the peer returned one or stored trust, so consumers must tolerate either side being the only result holder. Tests exercise both asymmetries and the never-sent case.

At each success point the core builds an immutable `PairingResult` (exact request ID as a routing handle only, `ceremony_identity`, the peer's role, the peer's exact retained canonical bootstrap frame bytes, the authenticated `shared_context`, profile identifier, and version `1`), then drops the vodozemac session, SAS bytes, approval state, and duplicate-tracking state, and only then releases the guard. The consumed opportunity is never refunded. If guard release is uncertain, the run fails closed with no result, even when the final ACK was already sent. The result contains no DH secret, session, ephemeral key, reusable secret, authorization, or trust/identity/possession verdict. After success every later message is rejected as `Completed` and callbacks find no live SAS; nothing can alter or duplicate the result. A bad tag, wrong digest, wrong request ID, changed duplicate, wrong-role or out-of-order message, or local REJECT/CANCEL during completion is terminal with no result, and nothing revives it. An exact duplicate `INITIATOR_FINISH` at R is ignored with no output or MAC work.

The deterministic test compares all three purposes, role codes, auth-frame types and bytes, `0x32` contexts, Base64url inputs, and info strings with the fixture, and frames the fixture's fixed-secret tags into the fixture's exact wire bytes; the result shape is compared with the fixture's `result_semantics`. The tags themselves are not recomputed (fixed X25519 inputs cannot be loaded into vodozemac 0.11.0), so live two-party ceremonies verify all three real MACs. Binding tests show verification fails if the auth-frame type, purpose, sender, receiver, or `ceremony_identity` changes, and relabelled or cross-ceremony finish tags fail. This exercises R-MAC-010–013 and the completion instances of R-WIRE-001, 016, and 020–024, preserving R-OWNER-005 and 007–010. Contexts are generated internally (checked canonical and unpadded) and never parsed from the network, so R-MAC-014's rejection takes the form of MAC verification failure, which a dedicated test shows for padded, standard-alphabet, nonzero-trailing-bit, and whitespace variants.

## Authenticated CANCEL

Authenticated `CANCEL / 0x09` exists only while a live `SasSession` (and so the retained `EstablishedSas` and the authoritative `ceremony_identity`) exists: `AwaitLocalApproval`, `LocallyApprovedAwaitingAuthentication`, `LocalMacSentAwaitingPeerMac`, `ApprovalsAuthenticatedAwaitingCompletion`, `AwaitResponderFinish`, `AwaitInitiatorFinishAck`, and `AwaitInitiatorFinishAckSend`. It consumes no opportunity, needs no new `Authorization`, and acquires no second guard. The tag is vodozemac `calculate_mac(input, info)`: `input` is unpadded Base64url of the non-wire `CancelAuthFrame / 0x34` (domain, profile ID, `u16be(1)`, sender role, receiver role, `ceremony_identity`, one-byte reason) and `info` is `sas-pairing-vodozemac-profile-draft-01/cancel/` plus unpadded Base64url of the non-wire `CancelMacContext / 0x38` (the same seven fields; no inner purpose field; never the `mac` outer purpose). The wire frame carries the exact request ID, sender role, reason, and raw 32-byte tag; the request ID and tag are never inside the authenticated structures. The same capped Base64url helper generates both strings.

`reject_sas` (reason `0x01`) and `cancel_sas` (reason `0x02`) check the exact `ceremony_identity`, build the authenticated `CANCEL` while `EstablishedSas` still exists, then drop the session (SAS, approval, and any pending final ACK), then release the guard, and only then return a crate-private `LocalCancellation`. Both variants mean the run is already terminal with no result and the opportunity kept: `Emitted(bytes)` is best-effort output only (returning it is not sending it; no send confirmation, delivery acknowledgement, retry, or peer response exists), and `NotEmitted` means construction failed and nothing, not even an unauthenticated frame, is sent. With bounded validated session data construction cannot fail in practice; a test-only fault injection exercises `NotEmitted`. If guard release is uncertain the call returns `Owner(OwnershipUncertain)`, the session is already dropped, the guard stays held, and the built frame is withheld. The same private construction emits `0x03` timeout when a ceremony deadline expires (see below); `0x04` local policy failure has no trigger yet. Wrong-identity or no-live-SAS calls (including before SAS establishment, where local cancellation is plain `terminate`, and after success) have no effect.

`receive_cancel` decodes (codec rejects undefined reasons and non-32-byte tags), requires a CANCEL and a live `SasSession`, checks the exact request ID and that the wire sender is the expected peer role, then reconstructs both non-wire structures with the peer as sender, this endpoint as receiver, the local `ceremony_identity`, and the received reason, and calls vodozemac `verify_mac`. Only then does it return `PeerCancellation { reason }` (diagnostic only; no result, trust verdict, or key material): the run is terminal, the session and any pending final ACK are dropped, and then the guard is released. Nothing is sent back. Any other CANCEL (bad tag, changed reason, wrong role or direction, wrong request ID, another ceremony's tag with the same request ID, or any CANCEL before SAS establishment, where no MAC work happens) is terminal protocol failure and is never reported as peer cancellation. After terminal state an exact or changed CANCEL causes no MAC work, transition, output, or second release; after success it is `Completed` and the result is unchanged. A local or peer CANCEL while the Initiator's final ACK awaits its send confirmation leaves no result, and the stale confirmation is rejected.

The deterministic test compares both fixture directions (I→R reason `0x02`, R→I reason `0x03`): role and reason codes, exact `0x34` and `0x38` bytes, Base64url input, `/cancel/` info string, and the fixed-secret tags framed into the exact `CANCEL / 0x09` wire bytes. As with the other MACs, the fixture tags are not recomputed; live two-party ceremonies verify real vodozemac CANCEL tags in both directions for all four reasons. Binding tests show verification fails for context types `0x31`/`0x32`/`0x34`, other auth-frame types, the `mac` outer purpose, an inner `cancel` field, changed sender/receiver/direction, another `ceremony_identity`, or another reason. This exercises R-MAC-015–023 and the CANCEL instances of R-WIRE-001, 017, and 020–024, preserving R-OWNER-005 and 007–010. R-MAC-015 remains partial only because the fixture's fixed-secret CANCEL tags cannot be verified; live verification covers both directions. The Windows TCP adapter writes a best-effort CANCEL only into a free outbound slot (R-MAC-023).

## Ceremony deadlines

P3 §11.3's two ceremony deadlines are implemented with the exact frozen values: a non-extendable **5-minute absolute** deadline and a **60-second machine/protocol inactivity** deadline, both expiring once `elapsed >= deadline`. The values are constants, not configuration. The crate-private `deadline` module holds the constants, a `MonotonicClock` abstraction, the production `Instant`-backed source, a hand-advanced test clock, and `CeremonyDeadlines`. Each ceremony owns one injected clock for its whole lifetime; no wall-clock, calendar, or `SystemTime` value is used, and callers never supply a timestamp per operation.

The Initiator's absolute deadline starts when its local ceremony state is created. The Responder's starts at the same monotonic instant as its pending pre-exposure resource admission (see below), when the validated `START` passes local admission into active state. Nothing refreshes the absolute deadline: no message, authorization, exposure, SAS establishment, approval, BOOTSTRAP_MAC, finish step, duplicate, callback, CANCEL, or final-ACK confirmation.

One exhaustive state mapping decides the inactivity mode. Inactivity is suspended only in `AwaitLocalApproval`, where the complete SAS is presented and awaits a deliberate human MATCH, REJECT, or CANCEL, including after the peer's BOOTSTRAP_MAC verified there. Every other live state runs it, including the exposure-authorization waits, the BOOTSTRAP_MAC and finish waits, and `AwaitInitiatorFinishAckSend`; `Succeeded` and `Terminal` have no deadline. The absolute deadline keeps running during the human wait, and the effective expiry is always the earliest applicable deadline. A single wrapper runs every state-advancing entrypoint. It checks deadlines first: an expired run times out and the input is never applied, so a late valid message, approval, or final-ACK confirmation cannot rescue it. It then restarts the full 60-second window at that checked instant only if the state's progress point changed (a new state, a recorded exposure authorization, or a verified peer approval MAC). Leaving the human wait by local approval therefore opens a fresh window from the approval time. Exact duplicates, idempotent `AlreadyRecorded`/`AlreadyEmitted` repeats, refused or stale callbacks, mismatched final-ACK confirmations, polls, and queries change nothing and buy no time. `presentation()` is also withheld, read-only, once a deadline has expired or the clock is unusable.

Expiry is terminal. The core-owned timeout reuses the authenticated-cancellation order without any caller-supplied identity: if a live `SasSession` exists it builds the authenticated `CANCEL` with reason `0x03` while `EstablishedSas` exists, drops the session (SAS, approval, any pending final ACK), releases the guard, and only then returns the bytes as best-effort output. Absolute and inactivity expiry use the same wire reason; the distinction is local diagnostics only. Before shared SAS establishment, including for an Initiator that already exposed `INITIATOR_KEY`, timeout is local terminal failure with no wire output. No timeout produces a `PairingResult`, and no opportunity is refunded: a run timed out before exposure spends none, and an exposed run keeps its one. If CANCEL construction fails, the run still times out with nothing to send. If guard release is uncertain, the session is already dropped, the guard stays conservatively held, and the built frame is withheld. A clock that reports no value or goes backwards fails the run closed (`ClockUnavailable`) without claiming an authenticated timeout, because an unusable clock is not evidence that a deadline passed. Large forward jumps are never clamped. A succeeded or terminal run ignores later deadline polls.

**There is no scheduler.** No thread, async task, sleep, or OS timer exists, and expiry is never delivered on its own. Every advancing operation enforces deadlines, and idle expiry is driven through the crate-private `poll_deadlines()`, which reports `Active`, `TimedOut` (with the optional CANCEL bytes), `PendingExpired`, or `Finished`. The host's bounded, cooperative `poll_ceremony_deadlines` (see "Socket-free host dispatch") calls exactly this for the runs of one connection; the experimental Windows owner loop below calls it on every drive. Deterministic tests advance the hand clock and never sleep. This exercises R-RESOURCE-006–009 in-process (the Windows TCP adapter and owner loop deliver the CANCEL best effort) and the timeout instances of R-MAC-015 and R-MAC-023, preserving R-OWNER-005 and 007–010. The separate 60-second pending pre-exposure resource lifetime is described below; the socket-free transport frame and idle-read deadlines are described under "Socket-free transport admission and frame assembly".

## Pre-exposure resource controls

The core-owned P3 §11.1.1 controls are implemented with the exact profile values, as constants. All resource accounting lives in the authority's existing shared state, beside the opportunity budget, the exposed-ceremony guard, and the Initiator request-ID set, so every thread, role, and ceremony of one authority shares it, different authorities are independent, and no separate mutex or per-connection counter exists. No control spends, refunds, or resets any of the ten SAS opportunities, and none touches the exposed-ceremony guard: four pending Responders, or any number of START limiter admissions and refusals, coexist with `Status::Ready { remaining: 10 }`. A refusal is one generic `Error::ResourceLimited`, distinct from `Exhausted`, `Busy`, and every protocol, authentication, SAS-mismatch, or compromise outcome; it names no specific cap.

- **Pending Responders: at most 4 per authority.** A Responder becomes pending in its constructor after the START candidate boundary, START limiter admission, one preliminary permit, and START semantic validation (nested bootstrap, context, expected peer): the core reads the monotonic clock, then immediately acquires the slot with that instant as its admission time, and only then creates fresh ephemeral state, the commitment, and `ACCEPT`. A known semantic mismatch, an unusable clock, or a refusal takes no slot and returns no `ACCEPT`. The slot is owned by that Responder's admission `Ceremony` (at most one; Initiators own none; never transferred) and covers every retained pre-exposure state: awaiting `INITIATOR_KEY`, and after successful DH with or without local authorization. It is released exactly once when `RESPONDER_KEY` has been built for release (after authorization, the atomic guard/opportunity reservation, and session construction), or immediately at any terminal cleanup: protocol or codec failure, malformed or misrouted `INITIATOR_KEY`, non-contributory DH, permit refusal, `Busy`/`Exhausted` exposure refusal (terminal, as before, with no later automatic reveal), pending expiry, ceremony timeout, clock failure, explicit termination, construction failure after admission (by dropping the admission `Ceremony`), or drop. DH success, authorization, or a free guard alone does not release it.
- **Expensive preliminary operations: at most 2 concurrent per authority.** A RAII `PreliminaryPermit` is taken immediately or refused with `ResourceLimited`; nothing waits, queues, or retries, and the authority lock covers only the count, never the cryptographic work. Dropping the permit releases it exactly once. It protects Responder ephemeral generation plus commitment (held from before semantic validation, per P3 §10, until `ACCEPT` is built), Responder pre-exposure DH/contributory validation (taken before the single consuming DH and released after it succeeds or fails; refusal ends the run unexposed without DH), and Initiator ephemeral generation (taken after local authorization and before the atomic reservation, so a refusal ends the run unexposed with nothing spent and the request ID released; a failed reservation returns the permit without generating anything). It is never held across a wait for a message, authorization, or human, and no other MAC, digest, or post-exposure work is counted.
- **Fixed 60-second pending resource lifetime.** It runs from the slot's admission instant and ends only when the slot is released. Unlike the 60-second ceremony inactivity deadline, nothing refreshes or suspends it: valid progress, duplicates, DH success, authorization, polls, and UI activity do not extend it. It is enforced in the same central wrapper before every state-advancing operation and by `poll_deadlines()` (`DeadlineOutcome::PendingExpired`), after the ceremony deadlines; when both have expired the ceremony diagnostic is reported, a local, non-normative choice with identical pre-exposure effects. Expiry is terminal local resource failure (`PendingExpired`): no `PairingResult`, no `RESPONDER_KEY`, no CANCEL or timeout claim, authorization invalidated, slot released, nothing spent, and later input cannot revive the run. After exposure only the ceremony deadlines apply.

If shared state is poisoned, admission and permits fail with `OwnershipUncertain`, and an existing slot or permit stays conservatively counted rather than being reported released. Tests use the hand clock and explicit thread coordination (barriers and channels), never sleeps: they cover the 4/5 boundary, refill after expiry or termination, independent authorities, exactly two of eight simultaneous permit requests, the third-permit refusal and release, each permit-refusal point, every listed release path, the exact 60-second pending expiry with ceremony inactivity still live after progress at 30 seconds, authorization not extending it, and no pending lifetime after exposure. This exercises R-OWNER-024, R-OWNER-027 (resource status only), R-OWNER-029's Responder ordering, R-OWNER-025, and the core cleanup and pending-deadline portion of R-OWNER-026 in-process. The transport controls of R-OWNER-023 and the transport-failure portion of R-OWNER-026 are modelled socket-free (see below); real socket behavior is exercised by the experimental Windows TCP adapter and owner loop below.

### START admission limiter

The frozen P3 §11.1.1 START admission limiter is implemented exactly, in the crate-private `start_limiter` module, with no configurable values:

- **One limiter per authority.** Its state lives in the authority's shared state beside the opportunity budget, the exposed-ceremony guard, the Initiator request-ID set, and the pending/permit counts. It is never global, per ceremony, per connection, per listener, per peer, or per request ID, and its history stores only admission instants. Different authorities are independent; only a new process session (a new OS process that safely acquired ownership) starts with credit 4 and empty history, and nothing is persisted. No ceremony termination, refusal, success, failure, status query, release, or same-process re-registration resets it (see [Ownership guarantees](#ownership-guarantees)).
- **One authority-scoped monotonic clock.** Each authority owns one `Instant`-backed clock created by the first registration of its process session and reused by every later registration in that process, so all admission instants share one origin. Ceremony clocks and `CeremonyDeadlines` are never used, nothing records progress on it, and it is never suspended. Tests inject one shared hand clock per authority through a `#[cfg(test)]` constructor; applications cannot supply timestamps.
- **Burst component.** Capacity 4, initial credit 4, exactly 1 token per 5 seconds. Integer whole tokens (`0..=4`), an elapsed remainder (`< 5 s`), and the last evaluation instant: at a safe `now >= last`, `total = remainder + (now - last)`, `tokens = min(4, tokens + floor(total / 5 s))`, `remainder = total mod 5 s` except zero while full, `last = now`. Checked `Duration` arithmetic, no floating point. Refusals keep refill progress; long idle time yields exactly 4.
- **Rolling component.** At most 12 limiter-admitted candidates in `(now - 60 s, now]`. Records aged `>= 60 s` are dropped before each evaluation, so live history is bounded at 12 instants.
- **Atomic admission.** One authority-mutex critical section reads the limiter clock, applies elapsed-time bookkeeping (refill and expiry, which persist whatever the outcome), and admits only if a whole token exists **and** fewer than 12 records are live, then consumes one token and appends one record. A refusal by either component charges neither. Concurrent candidates are equivalent to a serial order; the clock is never read before the lock. Nothing waits, queues, or borrows.
- **Charging is final.** Admission happens before the preliminary permit, START semantic validation, pending capacity, ephemeral generation, commitment, and `ACCEPT`, and nothing refunds it: semantic failure, permit or pending-cap refusal, later failure, cancellation, timeout, success, or drop all leave it charged. A refusal is the generic `Error::ResourceLimited` (inside the ceremony layer, `Owner(ResourceLimited)`), with no permit, slot, pending lifetime, ceremony state, ephemeral, commitment, or `ACCEPT`.
- **Unsafe clock.** A missing reading, a reading before the last evaluation, or uncomputable arithmetic refuses the candidate with the existing internal `ClockUnavailable` outcome and leaves the limiter state exactly unchanged: no refill, expiry, charge, record, or reset. It is not reported as an authentication failure.

**Structural/semantic boundary.** `protocol::decode` and the crate-private `protocol::start_candidate` share one outer parser (frame maximum, magic, version, exact length-prefixed fields with no truncation or trailing bytes, defined wire type, exact profile ID, 1–64-byte request ID). A START candidate additionally needs type `START` with exactly three fields; its bootstrap field stays opaque. The full decoder's START path is the candidate followed by its semantic decode, so the two cannot drift. Everything about the bootstrap contents — nested type `0x20` and its field structure, the per-field and 16,384-byte complete-bootstrap maxima, `key_algorithm` grammar — plus shared-context, expected-peer, and other §8 checks is START semantic validation after limiter admission. Structural failures (including header version and profile) are codec rejections that never reach or charge the limiter. Responder order: candidate parse → limiter → preliminary permit → semantic validation → pending slot → ephemeral and commitment → `ACCEPT`. An exact duplicate START handed to its existing run (`receive_start_duplicate`, which the session-bound router does for every START whose key is already routed) is not a new candidate and never reaches the limiter.

Tests drive the injected limiter clock by hand and never sleep. They cover the 4/5 burst at one instant, refusal at 5 s − 1 ns and admission at exactly 5 s, two tokens at 10 s, refusals preserving the remainder, the long-idle cap of 4, the exact R-OWNER-035 schedule (refusals at 45 s and 59.999 s, eviction and admission at exactly 60 s, then three more and a refusal), no partial charge by either component, semantic failures (malformed nested bootstrap, oversized nested bootstrap, `key_algorithm` grammar, shared-context and expected-peer mismatch) charged and observed by the next START, structural failures uncharged, permit and pending-cap refusals keeping the charge, the exact admission order, eight barrier-synchronized threads admitting exactly four, contention near the rolling cap never exceeding 12, independent authorities, rotated request IDs and application identities sharing one limiter, duplicate STARTs bypassing it, ceremony events not resetting it, a fresh limiter only for a safely released and re-registered owner, unavailable and backwards clocks, and the clock being read only inside the critical section. Existing tests of other controls let one full rolling window of limiter time pass before each new Responder so only the control under test can refuse. This exercises R-OWNER-025, R-OWNER-027, and R-OWNER-034–039 in-process; connection and real source-port rotation are exercised by the Windows TCP adapter and owner-loop tests.

Still not implemented: OS timers and power-notification subscription (the experimental owner loop below drives every poll cooperatively), a production listener with bind/interface/port/exposure policy (the owner loop takes an already-bound listener), a public SDK/consumer integration, and production-security approval.

## Session-bound pre-establishment routing

The crate-private `router` module implements the P3 §4/§10/§11.2 routing boundary: before establishment, protocol state is located by a local session identity together with the request ID, never by the request ID alone. It is core routing only: there is no socket, listener, byte reading or writing, frame buffering, reconnect, resume, or transport acknowledgement.

- **Local session handle.** A `Router` belongs to one pairing authority (it holds that authority's executor) and issues opaque `SessionHandle`s through `open_session()` for each transport connection's local session context. A handle is a router identifier plus a session number that is never reissued (exhaustion fails closed), so a closed handle and a handle from another router are both rejected with the narrow local `UnknownSession`. Nothing on the wire can create or select a handle, and none is derived from a request ID, address, or key. A handle means only "this locally distinct session context": it is not peer identity, authentication, possession, trust, authorization, or ceremony identity, and it never enters a transcript, MAC, wire frame, vector, or `PairingResult`. Handles and routes are volatile: never persisted or resumed, and gone with the router or process.
- **Routing key and ownership.** The key is `(SessionHandle, request_id)` with the canonical 1–64-byte request ID; peer IDs need not be 16 bytes. The router exclusively owns each routed `RemoteCeremony` inside its own mutex; dispatch takes the routing-table lock only to find the run, releases it, and then takes the run's lock, so no expensive cryptography runs under the table lock and no second mutable path exists (no `unsafe`). The router decides only where bytes go; the run still enforces request ID, message type, role, sequencing, duplicates, commitment, transcript, MACs, and completion. After establishment `ceremony_identity` remains the security identity. One authority may have several routers; their session namespaces are disjoint and all share the authority's limiter, caps, guard, and budget.
- **New, duplicate, and conflicting START.** For an incoming START the router parses only the routing fields, then in one table critical section either claims an absent key (after the structural START-candidate checks, storing the exact START bytes), or finds the existing claim or run. Only the claimer runs the unchanged Responder admission (START limiter → preliminary permit → semantic validation → pending slot → ephemeral and commitment → `ACCEPT`) outside the lock, and the run is installed only if that succeeds and the session is still open; any failure removes the claim. A byte-identical START for an existing key (installed, or still being admitted) is ignored: no admission, limiter charge, permit, slot, ephemeral, commitment, `ACCEPT`, deadline change, or state change; an installed run handles it through its existing `receive_start_duplicate`. A changed START for an existing key terminally fails that run (or marks the in-progress claim so its admission is discarded with no `ACCEPT`), is never a new candidate, and does not reach the limiter. Concurrent identical STARTs therefore create exactly one run with one limiter charge and one slot; concurrent conflicting STARTs never leave two live runs. A START delivered through `deliver` reaches only an existing run; only `receive_start` admits.
- **Isolation.** The same request ID on another session is a different key: a new candidate charged to the authority limiter and admitted independently, with its own ephemeral, commitment, deadlines, and cleanup, even for byte-identical START bytes, and the two runs can never share a `ceremony_identity` or an approval. Later frames are routed by their own request ID and the session they arrived on. There is no request-ID-only lookup and no fallback to "the only run on this session". A frame that is routable but malformed, illegal in the run's state, or a changed duplicate reaches its run and fails it under the existing rules; a non-START frame for a key whose START is still being admitted fails only that admission.
- **Unknown non-START route is session-fatal (P3 §11.2, R-WIRE-016(b)).** A structurally routable non-START frame (it passes the shared outer parser: complete canonical frame, defined type, exact profile ID, 1–64-byte request ID) on a live session whose key names no run reaches no run: with several runs on one session nothing says which one the peer meant. `deliver` instead tears the session down through the same synchronized teardown as `close_session` (every run on it terminal, every route removed, consumed opportunities kept, no result, no CANCEL) and returns `SessionProtocolFailure` only once that is complete. Other sessions, including runs with the same request ID, are untouched, and no authority control is reset. The diagnostic is a local session failure, never authentication, compromise, SAS-mismatch, or exhaustion evidence. A START with no route is still a new candidate through `receive_start` (`deliver` never admits, so it reports `UnknownRoute` with no effect), and a local `with_run` action naming no run is `UnknownRoute` with no effect, since it is not peer input.
- **Routed Initiators.** `start_initiator` generates and reserves the 16-byte ID exactly as before, then registers the run under `(session, request_id)` before returning START. If that key is already routed on the session (a peer chose that ID first), the run is discarded, its reservation released, and a fresh ID generated; incoming `ACCEPT` and later frames reach it through the same key.
- **Cleanup.** After every routed operation, a run that is irrevocably terminal or succeeded has already completed its own cleanup (SAS, approval, and pending final ACK dropped, then guard, slot, and reservation released); only then is its route removed and the key reusable. This covers protocol failure, conflicting START, timeout, pending expiry, clock failure, local reject/cancel or termination, verified peer CANCEL, and success, where the caller that completes the run receives the immutable `PairingResult`, which needs no route. A later START for a freed key on a live session is a fresh, newly charged candidate that inherits nothing. Session teardown terminates each run through the same cleanup: no CANCEL (P3 treats transport loss as local terminal failure), no result, no refund of a consumed opportunity, released slots and reservations, and no transfer to another session; those keys can never be reused because the handle is never reissued. Dropping the router drops every run with the same effects; it cannot race an operation, because every operation borrows the router. Closing, session failure, or dropping never resets the START limiter, the opportunity budget, or any other authority control, and is never owner replacement.
- **Synchronized session lifecycle (P3 §11.2, R-OWNER-040).** Each session is OPEN → CLOSING → CLOSED. Every operation (`receive_start`, `deliver`, `with_run`, `start_initiator`) enters an OPEN session with an RAII lease, counted in the session's own lifecycle mutex, inside a table critical section. `close_session` (or the session-fatal routing failure) marks the session CLOSING in a table critical section, the single linearization point: later operations get `UnknownSession` without touching the limiter, a run, or any resource. Teardown then waits on a condition variable, holding no table, run, or authority lock, until every earlier lease is gone. In-progress route creation never installs into a CLOSING session: a Responder admission drops its run (releasing its preliminary permit and pending slot) and returns no `ACCEPT`, and a routed Initiator drops its run (releasing its request-ID reservation) and returns no START, both before their leases. An operation already inside an installed run finishes its current step under the run lock and keeps its outcome. Only then are the session's routes detached and its runs terminated (SAS, approval, and pending final ACK dropped before the guard), and the session becomes CLOSED. So when `close_session` returns `Ok(())`, the session has no route, claim, in-flight creator, pending slot, permit, request-ID reservation, guard, or SAS/approval/final-ACK state left, and no worker can still return `ACCEPT`, START, a protocol output, or a `PairingResult` for it. START limiter charges are never refunded. Lock order is run → table → lifecycle (a leaf); there is no background thread, sleep, busy wait, or `unsafe`. A poisoned router or lifecycle lock, or uncertain run cleanup, fails closed with `OwnershipUncertain`: the session stays CLOSING forever and is never reported closed or reopened. Router operations must not re-enter the router from inside a `with_run` closure.
- **Bounded deadline enumeration.** The route table is an ordered map keyed by `(session, request_id)` (session first, then request-ID bytes), so one session's routes are contiguous and `poll_session_deadlines` finds the next route after a caller-held `DeadlineCursor` (the last inspected request ID) by one O(log n) seek, cloning only that key and that run's `Arc`. There is no auxiliary poll index, so nothing can go stale and memory stays O(live routes); routing, duplicate/conflict, and teardown semantics are unchanged. Each call holds one session lease, inspects at most `MAX_CEREMONY_POLLS_PER_CALL` = 8 routes (an implementation work cap, not a P3 limit), wraps at most once and never past where it began, skips an `Admitting` claim or a run whose lock is held (`try_lock`, no waiting), polls each other run with its existing `poll_deadlines` outside the table lock, removes a finished route only if it still names that exact run, and stops at the first terminal outcome. Once the session begins closing the call finishes only its current run. A poisoned run lock or uncertain cleanup is `OwnershipUncertain`.

Tests use hand clocks, barriers, channels, and test-only per-thread pause points (no sleeps, no reliance on slow cryptography). They cover distinct and rejected handles, a new key charging the limiter once, 100 exact duplicates leaving the limiter snapshot identical with no second `ACCEPT`, slot, or ephemeral (the original commitment still verifies), duplicates and misrouted frames buying no inactivity time, conflicting STARTs before and after exposure, the same and byte-identical START on two sessions, cross-session and wrong-ID injection, 25 repetitions each of eight concurrent identical STARTs, two concurrent conflicting STARTs, and concurrent equal IDs on two sessions, session close with several pre-exposure runs and after exposure, no limiter reset across sessions, route removal on timeout, pending expiry, protocol failure, termination, local and verified peer CANCEL, and success, key reuse only after terminal state, equal request IDs never sharing `ceremony_identity` or approval, Initiator collision regeneration, router drop, an unknown non-START route on a one-run session (no fallback to that run), on a three-run session beside another session with the same request ID and its untouched deadlines, after exposure (opportunity kept, peer not notified), and for a key still being admitted, plus close paused against an in-flight Responder admission holding its permit and slot, against two admissions with no installed route, against a routed Initiator holding its reservation, and against an operation inside an installed run (close waits, admits nothing new, suppresses `ACCEPT`/START, and returns only with every resource released and limiter charges kept). This exercises R-WIRE-016 (both the run-level and the session-fatal case) and the routing portions of R-WIRE-022–024 (START duplicate/conflict and routed delivery), R-OWNER-040 in-process, R-OWNER-007, 008, 011, and 015, the request-ID and connection-rotation portions of R-OWNER-019 and R-OWNER-037(c), the connection-close portion of R-OWNER-038(a), the core disconnect-cleanup portion of R-OWNER-026, and R-RESOURCE-009 for routed input. The socket-free transport model below maps each connection to one handle and tears its session down on transport failure or close; the Windows TCP adapter below maps socket EOF and failures onto that same teardown.

## Socket-free transport admission and frame assembly

The crate-private `transport` module models the P3 §11.1.1 transport controls that the experimental Windows TCP adapter drives. It is socket-free: there is no TCP, UDP, WebSocket, named pipe, listener, bind/connect, OS `accept`, OS backlog setting, `recv`/`read`, `send`/`write`, TLS, reconnect, resume, async runtime, background thread, or timer. The adapter reports events (an accepted connection, received bytes, a poll, a close) and receives at most one complete frame per call. The values are the exact P3 defaults, as constants with no configuration.

- **Authority-wide accounting.** Pending accept-work tasks, live unauthenticated connections, and retained incomplete frames are three counts in the authority's existing shared state, beside the START limiter and the pending/preliminary caps. Every router, future listener, and adapter object of one authority shares them, different authorities are independent, and nothing is per router, per listener, or keyed by peer address. A poisoned shared lock fails closed with `OwnershipUncertain`: nothing is admitted, no incomplete frame starts, and existing counts stay conservatively held rather than being reported released.
- **Accept queue: at most 4.** An RAII `AcceptPermit` (taken immediately or refused with the generic `ResourceLimited`; no queueing or waiting) is one connection notification the adapter has accepted into bounded application work but not yet made live. Dropping an unused permit releases its slot exactly once. This models the adapter's application work queue; it does not configure or bound an OS listener backlog or kernel socket buffering.
- **Live connections: at most 16.** `activate` turns a permit into a live `TransportConnection` in one shared-state critical section (pending −1, live +1), rechecking the cap there, so with 15 live and four racing permits exactly one wins. At 16 it returns `ResourceLimited` with the pending slot released and no Router session, protocol state, limiter charge, or SAS-opportunity effect. Only then is the connection's one fresh Router `SessionHandle` opened (if that fails, the live count is released again, since no session exists). A connection counts from activation until its teardown has established its session CLOSED, whether or not it ever sent a frame: there is no separate authenticated transport state, and completing a frame, a ceremony, or pairing releases nothing.
- **One connection, one session.** Each connection owns exactly one locally created handle for its whole life, never switches it, and never reuses a closed one (handles are never reissued). Complete frames are handed back to the host dispatch layer (below), which makes the `Router::receive_start`/`deliver` calls on that handle; the transport itself never dispatches, decodes, or bypasses the Router.
- **Incomplete frames: at most 4 per authority, 1 per connection.** The per-connection limit is structural (one optional partial frame). A frame found complete inside one input is returned without retaining anything, so it needs no slot. Otherwise one authority slot is taken (RAII) before the first byte is retained; at 4 the connection fails generically and is torn down, retaining nothing, while the other four are untouched. Later bytes extend that one frame. Completion returns the exact bytes, releases the slot, and clears both timers; the connection stays live.
- **Bounded assembly with the codec's own layout.** Boundaries come only from `protocol::wire_frame_extent`, which shares the codec's header check and its single wire-type field-count table (`wire_field_count`, also used by `decode` and the START candidate), so stream assembly and decoding cannot disagree. It rejects bad magic, an unsupported version, or an undefined wire type as soon as those bytes are present, and checks each declared length when it is read, before any payload is retained, requiring with checked arithmetic that the frame so far plus the remaining fields' length prefixes fit in 65,536 bytes. Bytes are retained only up to the next point it names and never past the frame end, capacity is reserved only toward a validated target, and the buffer never exceeds `MAX_FRAME`; no declared length is used to allocate before validation. An exact 65,536-byte frame is accepted; 65,537 is refused once its last length prefix is read. Nothing else is checked: profile ID, request ID, field contents, and every semantic rule stay with the codec and Router, so a frame with a semantically invalid bootstrap is still returned exactly and then charged and rejected by the unchanged START path.
- **Deadlines.** A retained frame has a 10-second whole-frame deadline from its first retained byte that progress never extends, and a 2-second deadline without progress, where progress means at least one new byte retained by a call. Both expire at `elapsed >= deadline` and are checked before any new byte is accepted, so a byte at exactly 2 s idle or 10 s total is not taken, while one at 2 s − 1 ns is taken and restarts only the idle deadline. Empty input takes nothing, starts nothing, and refreshes nothing. `poll_connection_deadlines()` enforces them without input; there is no scheduler, so the future host drives polling. Each connection has one injected monotonic clock (never a ceremony, pending-lifetime, or START-limiter clock; no ceremony progress is recorded). A missing reading, or one earlier than a reading the connection already used, fails the connection (`ClockUnavailable`) rather than resetting or extending anything. When both deadlines have expired at once, the whole-frame diagnostic is reported; the effect is identical. A frame complete inside one input has no frame timer; since P6 it is still checked against the connection lifetime below before it is taken.
- **Connection lifetime (P6, decision [P6-D-001](../docs/p6-remediation/decisions.md#p6-d-001--f-002-connection-lifetime), remediating [P5-F-002](../docs/p5-security-review/findings.md#p5-f-002)).** Outside an incomplete frame each connection is governed by exactly one finite deadline, re-derived from what it holds at every evaluation: 10 s from activation until its first frame begins; no connection timer while its session has a live run (an installed ceremony), whose ceremony deadlines govern; 10 s once it has no live run, no frame in progress, and no retained output (quiescent); and 10 s absolute plus 2 s without write progress for an outbound frame the adapter retains while no live run exists. Origins move only when what the connection holds changes (a live run ending, output appearing or leaving). A frame that leaves no live run behind, readiness, WouldBlock, polls, empty input, and read-only calls refresh nothing, and only write progress refreshes the 2 s output deadline. A first byte accepted before expiry hands over to the frame deadlines above. Expiry (`FirstFrameTimeout`, `QuiescentTimeout`, `RetainedOutputTimeout`, `RetainedOutputIdleTimeout`) is the one teardown below; no result, CANCEL, limiter, or budget effect. The activation instant is the first clock reading; a connection with no live run needs a usable clock, while one with a live run takes no transport reading outside a frame, as before.
- **One teardown.** Bad header, undefined type, oversized declaration, any frame or connection deadline, an unusable clock, an incomplete-slot refusal, explicit `close`, and drop all use one path: stop accepting input, destroy the partial frame and release its slot, call `Router::close_session_settled`, and only once the session is established CLOSED release the live count. That Router call is the existing synchronized session teardown (every run terminal with I1/I2 invalidation before guard release; pending slots, permits, and request-ID reservations released; no CANCEL; no `PairingResult`; START limiter charges and consumed opportunities kept). If another caller already began the teardown (for example `deliver`'s session-fatal routing failure), it waits for that teardown and takes its outcome, so an in-progress or uncertain teardown is never mistaken for CLOSED. If Router cleanup is uncertain, the connection's live count is never released for the rest of the owner session, so uncertain work can never be replaced by new connections. Drop never panics. A transport error is never SAS mismatch, MAC failure, authentication evidence, compromise, or `OpportunityLimitReached`, and no authenticated CANCEL is synthesized. Transport failure resets no START limiter, opportunity budget, guard, ownership lease, or pending/preliminary cap and affects no other connection.
- **Lock order.** Run mutex → router table mutex → session lifecycle mutex (leaf), with the authority shared mutex taken by ceremony work under a run mutex or with nothing held. The transport adds no mutex (a connection is used through `&mut self`) and takes the authority shared mutex only for its counts with no other lock held, never across a Router call. A connection must not be closed or dropped from inside a `Router::with_run` closure on its own session.

Tests use hand clocks, barriers, channels, and test-only pause points, never sleeps. They cover the 4/5 accept-queue boundary and permit drop; 16 frameless connections and a refused 17th with no session; 25 rounds of four barrier-released activations at 15 live yielding exactly one winner; caps shared across two routers of one authority and independent across authorities; one fresh, never-reissued session per connection; close observed (through a pause point) with the session CLOSED, its run and the partial frame released, and the live count still held; close mid-ceremony after exposure (opportunity kept, no result, peer not notified); failure resetting no limiter and sparing other connections; four incomplete frames across two routers and a fifth closing only its connection; byte-by-byte and every two-read split of every fixture frame of all nine wire types, each reconstruction decoding identically to the original; several frames and a trailing partial frame in one input; empty input; exact 2 s and 10 s boundaries with each timer isolated; backwards and missing clocks; oversized declarations without payload retention; an exact-maximum frame; bad magic, version, and types; no Router state or limiter charge before the Router START path; poisoned accounting; uncertain Router teardown by close, drop, and a failed session-fatal teardown; and waiting on another caller's in-progress teardown. Existing router lifecycle tests are unchanged.

Coverage: R-OWNER-023's connection cap, accept-work queue, incomplete-frame caps, and 10 s/2 s deadlines are covered by the socket-free core model; real reads, fragmentation, and disconnects are exercised by the Windows TCP adapter, while an OS listener backlog and kernel buffering remain unclaimed. R-OWNER-026's transport-failure cleanup through the Router is core-covered, and socket EOF and failures reach it through the adapter. The early header and maximum-size rejections exercise the stream instances of R-WIRE-002–004 and R-WIRE-009; complete-frame validation (R-WIRE-001 and 005–012) is unchanged in the codec.

## Socket-free host dispatch

The crate-private `host` module is the thin, synchronous layer the Windows TCP adapter drives between one `TransportConnection` and its one Router session. It is socket-free like the transport: there is no listener, OS `accept`, `recv`/`read`, `send`/`write`, partial-write driver, kernel backlog, OS disconnect callback, TLS, async runtime, thread, timer, retry or retransmission queue, reconnect, or resume.

- **One host, one connection, one session.** `HostConnection::new` wraps an already admitted connection (`AcceptPermit` → `TransportConnection`) together with the local Responder configuration for new STARTs: the local bootstrap and optional expected peer. It opens no session, takes no capacity, and has no path that bypasses the 16-connection accounting. The configuration is local only (no wire field, request ID, or peer bootstrap can select or change it) and is cloned only into each START admission. The host keeps no ceremony state: it is live or closed exactly as its transport is.
- **One frame per call.** `receive(input)` feeds the transport assembler with its exact `consumed` semantics and dispatches the one frame that call completes, if any. It returns at most one event, one outbound frame (at most `MAX_FRAME` bytes), and one `PairingResult`; remaining input is never queued, so the adapter feeds the unconsumed suffix again. All network bytes go through the assembler (frame maximum, incomplete-frame caps, 10 s / 2 s deadlines); there is no raw complete-frame entry point. `poll_connection_deadlines` and `close` delegate to the transport; dropping a host drops its transport connection, whose own teardown runs once.
- **Dispatch boundary without semantic decoding.** Each complete frame is classified by `protocol::routable`, which shares the codec's outer parser and its single wire-type table: both common fields (exact profile ID, 1–64-byte request ID), and for START the structural candidate (exactly three fields). A START candidate goes to `Router::receive_start`, so the unchanged order START limiter → preliminary permit → semantic bootstrap validation → pending slot → ephemeral and commitment → `ACCEPT` holds; the bootstrap is never decoded before the limiter charges. Every other defined type goes to `Router::deliver` and its run, which still decides type, state, role, duplicates, MACs, transcript, and CANCEL validity.
- **Connection scope.** A complete frame that fails that boundary (wrong profile ID, request ID outside 1–64 bytes; field-count errors cannot survive assembly) is structurally unroutable: under P3 §3.1, §11.1.1, and §11.2 a codec/transport rejection that reaches no run, admission, limiter, or Router state. It cannot be attributed to any run on the connection, so the connection ends through the transport's one teardown (`Unroutable`), exactly like the stream-level magic/version/type rejections. The Router's session-fatal unknown route (`SessionProtocolFailure`), `UnknownSession` (the session already ended elsewhere), and `OwnershipUncertain` also end the connection: the transport teardown settles (or waits for) the Router session before releasing the live count, and keeps it held for good if cleanup is uncertain. Every other Router outcome belongs to one START attempt or one run — limiter, permit, or pending-capacity `ResourceLimited`, semantic START rejection, a changed START, wrong-state or malformed messages, MAC or transcript failure, an invalid CANCEL — and is returned with the connection, its session, and its other runs untouched. Any `Err` from a host method means the connection ended; outcomes that leave it live are inside `Ok`.
- **Immediate outputs only.** The only outbound frames are those the inbound transition itself produced: a new START → `ACCEPT`; a verified `INITIATOR_FINISH` at R → `RESPONDER_FINISH_ACK`; a verified `RESPONDER_FINISH_ACK` at I → the final `INITIATOR_FINISH_ACK`. A verified `INITIATOR_FINISH_ACK` at R returns R's result and sends nothing. Exact duplicates (START, `BOOTSTRAP_MAC`, `INITIATOR_FINISH`) produce no output, crypto, or deadline change, and nothing is retransmitted. Local decisions are never taken on inbound input: they are the explicit local actions below.
- **Final-ACK send boundary.** Returning bytes is not sending them, and sending is not peer receipt. The final `INITIATOR_FINISH_ACK` is returned as a `FinalAck`: the exact produced bytes plus the `(session, request_id)` they belong to, created only by this module and not `Clone`. The adapter keeps it while writing and hands it to `confirm_sent` only after the complete frame was written locally (never after a partial, failed, or merely attempted write). Confirmation consumes the token and goes through the run's own `confirm_initiator_finish_ack_sent`, which checks the exact pending bytes, state, and deadlines and only then builds the result, drops session state, and releases the guard, after which the Router removes the route. Before confirmation the run stays pending with its guard held and no result exists. Closing or failing the connection first terminates the run with no result and the opportunity kept; a closed host confirms nothing, and a token of another connection or of a run that already ended names no run (`UnknownRoute`) and creates nothing.
- **Results and lifetime.** The Responder's result comes from its verified final ACK through `deliver`, the Initiator's from the send confirmation, each exactly once. Pairing success is ceremony-local: the connection, its session, and its live count stay, and another fresh run may use the connection; stale traffic for a finished run is the session-fatal unknown-route case and never a second result.
- **Idle ceremony deadline driving.** The deadline semantics were already implemented in each run (`poll_deadlines` and the check before every advancing operation); this layer adds only bounded idle *driving*, so an idle run is eventually cleaned up without protocol input. `poll_ceremony_deadlines()` is a separate explicit call, never folded into `receive` (which stays one frame, one run) or into the transport's `poll_connection_deadlines`, and it drives only this connection's own Router session: no host scans another session, router, or the authority. Each call makes one bounded pass (`Router::poll_session_deadlines`, at most 8 inspected routes, Responders and local Initiators alike), resuming after the previous call's last inspected route and wrapping, so every continuously live run is reached by repeated calls; a run another operation holds and a START still being admitted are skipped without waiting. Each reached run gets exactly its existing `poll_deadlines`, which alone decides the 5-minute absolute deadline, the 60-second inactivity deadline and its suspension during the human SAS comparison, the fixed 60-second pending lifetime, and the timeout CANCEL; the host computes no deadline, inspects no state, and a poll is not progress. The call stops at the first run that ends and returns `CeremonyPoll { inspected, event, outbound }`: at most one `CeremonyDeadlineEvent` (`TimedOut(Absolute | Inactivity)`, `PendingExpired`, or `ClockUnavailable`, with the request ID as diagnostic routing data) and at most one outbound frame, never a `PairingResult`. After shared SAS establishment a timeout carries the authenticated `CANCEL` reason `0x03` that the run built before dropping its SAS, as an ordinary `Outbound::Frame` (never `FinalAck`): returned is not written and written is not received; it needs no send confirmation and is never retried, because the run is already terminal, its guard released after invalidation, and its opportunity kept. Before SAS no CANCEL exists. Pending expiry and an unusable ceremony clock end only their run with nothing to send. These run outcomes leave the connection, its session, and sibling runs live; a session already closing or closed, a poisoned run lock, or uncertain cleanup ends the connection through the one teardown, with the live count held if uncertain. No scheduler, timer thread, background loop, or retransmission queue exists: the owner loop decides when to poll.
- **Trusted local ceremony actions.** The rest of one remote ceremony is driven through the host too, so an adapter needs no Router access: `start_initiator(local, expected)`, `authorize_exposure(run, &TrustedAuthority)`, `expose_key(run)`, `presentation(run)`, `approve_sas(run, ceremony_identity)`, `emit_bootstrap_mac(run)`, `reject_sas(run, ceremony_identity)`, `cancel_sas(run, ceremony_identity)`, and `emit_initiator_finish(run)`, beside the unchanged `confirm_sent`. Each is one synchronous call to one existing `RemoteCeremony` entrypoint, which alone decides deadlines, state and role legality, authorization, guard and opportunity reservation, MAC construction, and terminality; the host checks no state and chains nothing. Authorizing never exposes, exposing never approves, MATCH never emits `BOOTSTRAP_MAC`, emitting it never emits `INITIATOR_FINISH`, and a guard becoming free exposes no prepared Responder. A `LocalAction { run, event, outbound }` carries at most one ordinary `Outbound::Frame` (START, `INITIATOR_KEY`, `RESPONDER_KEY`, `BOOTSTRAP_MAC`, `INITIATOR_FINISH`, or a best-effort authenticated CANCEL `0x01`/`0x02`), produced and not sent, needing no send confirmation, never retried or refunded if its write fails, and never a `PairingResult`: results still come only from R's verified final ACK and I's `confirm_sent`. Repeated MAC or finish emission is `AlreadyEmitted` with no frame. The Initiator's configuration is an explicit trusted input, never the host's Responder configuration; the core still generates, reserves, and routes its 16-byte CSPRNG request ID before START exists, and nothing is spent until exposure. `presentation` is read-only (no progress, no refresh, and an expired SAS is only withheld until the next action or deadline poll ends the run). A mutating action that finds its run's deadline expired does not happen: the run's own `step` ends it first, and the host reports `LocalEvent::Deadline` exactly as the deadline driver does, with the authenticated timeout CANCEL `0x03` the run built if a SAS existed (never constructed by the host). Errors follow the host convention: run-local refusals (a stale or foreign run reference, wrong identity, wrong role or state, missing or stale authorization, a busy guard, exhaustion, missing approvals) return inside `Ok` with the connection live, and the shared `ends_session` set (`UnknownSession`, `OwnershipUncertain`) ends it through the one teardown, with any built CANCEL withheld under uncertain cleanup.
- **Exact-run targeting.** Request IDs are peer-controlled routing data that may be reused once a run ends, so local actions never name "whatever is routed under this key now". Routing a run (local Initiator start, admitted START) and every dispatch or action that leaves it live return an opaque `RunRef`: this session, the routing key, and the run's in-memory instance (its existing admission `Ceremony` ID, process-unique and never reissued; no new counter). `Router::with_exact_run` acts only if the reference names this connection's session, a route still exists under its key, and that route's run, checked under its own lock before anything runs, is the same instance; otherwise nothing changes (`UnknownRoute`, connection live). A reference kept after its run ended, was replaced under a reused request ID, or whose connection closed, or one from another connection or router, therefore reaches nothing. It holds no run, lock, or `Arc` (the Router stays the only owner and mutation path), is never on the wire, hashed, or persisted, and is not the request ID, `ceremony_identity`, peer identity, authentication, or authorization: holding one grants nothing, and SAS decisions still require the exact `ceremony_identity`. Local methods take no session handle and never scan routes.
- **Clocks and locks.** The transport clock (10 s / 2 s), the authority START-limiter clock, and the ceremony clock stay separate: new Responders and host-started Initiators get a fresh production ceremony clock; tests inject a distinct hand clock and scripted Initiator request IDs. The host holds no lock; every Router call returns, with its leases released, before any teardown, so it never closes a session from inside a run operation.

## Experimental Windows connected-TCP adapter

The crate-private, Windows-only (`#[cfg(windows)]`) `windows_tcp` module is the first real network-I/O adapter: it drives one `HostConnection` over one **already-connected** `std::net::TcpStream`. TCP is one experimental P4 adapter implementation, not a P3 normative carrier: P3 stays carrier-neutral, and nothing about TCP (addresses, ports, the socket) enters any wire frame, transcript, `ceremony_identity`, MAC input, authorization, opportunity or limiter accounting, or authority identity. No peer address is retained or used as a key. Its I/O uses only `std::net`/`std::io` (no new dependency, async runtime, or `mio`); from the existing `windows-sys` it takes only the WinSock `SOCKET` type, for a crate-private readiness-handle accessor an owner's `WSAPoll` needs, which is never an identity. It spawns, sleeps, waits, and schedules nothing: trusted outer code (now the owner loop below) decides when the socket is readable or writable and when deadlines are polled, and every call does bounded synchronous work and returns. On unsupported platforms the module does not exist and remote pairing stays fail-closed.

- **Admission handoff.** `WindowsTcpConnection::from_accepted(stream, permit, local, expected)` requires the `AcceptPermit` that trusted outer code must take immediately after the OS accept (a refused permit means: close the socket and create nothing). It makes the stream nonblocking first (on failure the socket and permit are dropped and nothing becomes live), then the permit's own `activate` takes the live count (refused at 16: the socket is dropped, no session) and opens the one Router session, and the host wraps it. The adapter holds no counter of its own and has no other live-connection path. The pending-accept cap of 4 bounds application accept work only, never the OS listener backlog. One adapter is one TCP connection, one `TransportConnection`, and one Router session for life: no reconnect, socket replacement, resume, or session switch.
- **Read path.** `on_readable()` makes at most one nonblocking OS read of at most `SOCKET_READ_CHUNK = 8192` bytes (I/O plumbing, not a protocol limit) into a fixed buffer, and dispatches at most one complete frame through `HostConnection::receive`. Bytes the host did not take stay in a retained suffix, structurally at most one chunk, and are fed before the socket is read again: one read holding `A || B || partial C` dispatches A, then B, then hands C's prefix to the transport, without another read. Framing, `MAX_FRAME`, the incomplete-frame caps, and the 10 s / 2 s deadlines stay the transport's; the adapter never parses lengths or allocates from them. WouldBlock and Interrupted change nothing (no host call, no deadline refresh) and are never retried inside the call. A read of 0 bytes (EOF) or any other read error ends the connection.
- **Write path.** At most one outbound frame is retained (one `Option<PendingWrite>`: the exact host `Outbound`, its write offset, and the live `RunRef` that produced it, if any). `on_writable()` makes at most one nonblocking OS write from the exact offset; a partial write only advances the offset, WouldBlock/Interrupted change nothing, and nothing is ever re-sent or retried. A frame leaves the slot only once its last byte was written locally, which is never peer receipt; ordinary frames are never confirmed. A zero-byte write or any other write error ends the connection.
- **Final-ACK boundary.** The `FinalAck` stays itself inside the slot through partial writes and WouldBlock. Only the call that writes its last byte passes it to `HostConnection::confirm_sent`, so the Initiator's `PairingResult` exists only after the complete local socket write, exactly once. If confirmation finds the run's deadline passed, the run's own authenticated timeout CANCEL takes the now-free slot and there is no result, even though the final ACK's bytes already left and may still give the Responder its result (P6-D-005; the CANCEL then reaches the Responder's session as an unknown route); a failed or interrupted write is never confirmed and leaves no result.
- **Backpressure.** While a frame is retained the socket is not read, no inbound frame is dispatched, and every mutating local action (Initiator start, authorization, exposure, MATCH, own MAC, REJECT, CANCEL, INITIATOR_FINISH) is refused with `Refused::WritePending` before the host is called, so no second output can form; the peer's TCP flow control holds back its input. Read-only `presentation` and both deadline polls still run, so a peer that stops reading cannot extend any deadline.
- **Deadlines and the retained frame.** `poll_connection_deadlines()` and `poll_ceremony_deadlines()` each make exactly one host poll (the latter at most 8 inspected routes); no cadence or timer value is chosen here. A timeout CANCEL found by a poll, an inbound frame, a local action, or a confirmation is the run's exact frame (never rebuilt) and takes the slot only if it is free; otherwise it is dropped as best effort while its run stays terminal. Before every socket write of a frame a live run owns, `on_writable()` itself makes one exact deadline check of that one run (`HostConnection::poll_run_deadline` → `Router::poll_exact_run_deadlines`: the existing `RemoteCeremony::poll_deadlines` behind the exact `RunRef` instance check, one key, no scan, no cursor), so a frame of a run that has ended is never written further however many routes the session has or wherever the fair 8-route cursor stands; a stale owner reference is treated the same way (`Discarded` before any byte). If the run that ended owns the retained frame, that frame is never continued: unsent, it is discarded (its CANCEL may replace it); partially written, the stream holds a truncated canonical frame that can be neither retracted nor followed, so the whole connection is closed (`AbandonedPartialFrame`) with nothing appended.
- **One teardown.** EOF, read or write failure, an abandoned partial frame, a host error (transport failure, unroutable frame, session-fatal unknown route, uncertainty), `close()`, and drop all stop I/O, shut the socket down, discard the suffix and the retained frame (a `FinalAck` is never confirmed), and close the host, whose transport teardown settles the Router session (every run terminal, no result, no CANCEL, no limiter refund, consumed opportunities kept, guards released after invalidation, pending slots and request-ID reservations released) before releasing the live count, which stays held if cleanup is uncertain. A second `close` reports `Closed`. None of these outcomes is authentication, SAS-mismatch, compromise, or opportunity-exhaustion evidence.
- **Local actions.** The adapter mirrors every host local action with the same `RunRef` targeting and exact `ceremony_identity` requirement; a produced frame moves into the retained slot and only the semantic outcome (`Acted { run, event, write_pending }`) is returned, never a copy of the bytes.

Tests use a crate-private scripted socket (deterministic partial writes, WouldBlock, Interrupted, zero writes, EOF, read and write errors, and chunked reads) and hand clocks, never sleeps, plus two real Windows loopback tests whose listener is test plumbing only (`127.0.0.1:0`, OS-assigned port). They cover constructor ordering and failure (nonblocking refusal, live cap, ambiguous shared state); accept and live caps across two routers of one authority and an independent authority; one read of three frames dispatched one per call with no extra read and nothing lost, duplicated, or reordered, and a frame larger than one chunk crossing two reads; WouldBlock and Interrupted refreshing nothing; EOF and read errors ending several runs of one connection (pending slots and reservations released, no refund) while an equal request ID on another connection continues; EOF after exposure keeping the opportunity; exact-offset partial writes; zero and failed writes; backpressure of reads and all mutating actions with presentation and both polls still running; a full scripted ceremony whose final ACK is written as 3 bytes, WouldBlock, 5 bytes, Interrupted, 1 byte, and the rest, with no result, the route, the guard, and the token retained until the last byte, then exactly one result; final-ACK and contribution write failures (no result, no retry, opportunity kept); an owner timeout replacing an unsent RESPONDER_KEY, START, or final ACK by its CANCEL (or nothing before SAS); an owner timeout after a partial write closing the connection with only the prefix written while another connection is unaffected; a sibling timeout dropping its CANCEL and leaving another run's partly written frame to continue; timeout CANCELs found by inbound frames, actions, and confirmation; the frame deadline closing a connection whose write is blocked; malformed, oversized, unroutable, and unknown-route input closing only their connection; and close, drop, and uncertain cleanup. The real tests drive START → ACCEPT over an OS socket (the peer reads exactly the host's canonical ACCEPT; an unknown route then shuts the real socket down so the peer reads end of stream) and a complete ceremony over one loopback connection with both ends wrapped in adapters, whose Initiator result appears only on the call whose real write completes the final ACK, followed by a real EOF. Mutating the adapter to confirm a final ACK after a partial write, admit a second retained output, continue an orphaned partial frame, read while a suffix is retained, or refund an opportunity on write-failure teardown each fails these tests.

Coverage: with real connected-stream evidence this exercises R-WIRE-025 (fragmented and chunked reconstruction over socket reads), R-WIRE-016(b) (unknown route closing the real connection only), R-OWNER-023 (live and accept-work caps through the adapter constructor, incomplete-frame deadline while a write is blocked; the OS listener backlog is not claimed), R-OWNER-026 (disconnect, transport failure, and write failure releasing pending state exactly once with no SAS charge), R-OWNER-005 (a contribution or final ACK whose write fails keeps its opportunity), R-OWNER-040 (disconnect and local close as one teardown), R-OWNER-037(c) (connections isolated, nothing keyed by address), R-MAC-010–012 (completion over real TCP, Initiator success only after the complete local write), and R-MAC-015/R-MAC-023 (timeout CANCEL surfaced best effort and verified by the peer). Bind/interface/port/exposure policy, discovery, connection establishment (`connect` destination selection), TLS, reconnect/resume, and a public SDK are not implemented; the owner loop below hosts an already-bound listener only.

## Experimental Windows owner loop

The crate-private, Windows-only `windows_owner_loop` module is the one synchronous, cooperative driver of an **already-bound** `std::net::TcpListener` (supplied by trusted outer code) and of the `WindowsTcpConnection`s accepted from it, for one `Router` (one authority hosting context). The core never binds, connects, inspects a local or peer address, or chooses an interface, loopback or LAN exposure, port, discovery, or firewall policy; `WindowsOwnerLoop::from_bound_listener` only makes the listener nonblocking (on failure nothing is created). The only `Cargo.toml` change is the `Win32_Networking_WinSock` feature of the existing `windows-sys 0.59` dependency, for `WSAPoll`, `WSAPOLLFD`, the `POLL*` flags, `WSAGetLastError`, and `WSAEINTR`; the only `unsafe` code is the two calls to those generated functions.

- **One drive.** `drive_once()` is bounded synchronous work with no thread, timer, sleep, channel, or retained event queue: a deadline sweep (per live connection one frame-deadline poll and one bounded ceremony-deadline poll of at most 8 routes), at most one `WSAPoll` over at most 17 sockets (1 listener + the authority-wide 16 live connections) waiting at most `OWNER_LOOP_MAX_WAIT = 250 ms` (not at all when the sweep already found an event or an adapter retains unconsumed input), the same sweep again, then at most one socket operation per connection, then at most one OS accept. A connection whose sweep produced an event does no socket I/O in that drive. A returned `OwnerStep` holds at most 17 events (one listener event plus one per connection) and an optional loop failure. The 250 ms value is scheduling plumbing only: not a protocol deadline or security constant, and added to no deadline; a wake or a zero `WSAPoll` result is not progress, activity, keepalive, or a timeout.
- **Readiness.** Interest is `POLLIN` for the listener, `POLLOUT` for a connection retaining a frame, and `POLLIN` otherwise. For a connection, `POLLERR`/`POLLNVAL` are hard failures that win over any other readiness and over retained input: the connection is closed with no read or write. `POLLHUP` is not a failure (P6, decision [P6-D-003](../docs/p6-remediation/decisions.md#p6-d-003--graceful-tcp-hang-up-handling), remediating [P5-F-001](../docs/p5-security-review/findings.md#p5-f-001)): it is a peer's graceful FIN, which ends only the peer's sending direction. A hung-up connection with no retained frame gets one `on_readable` per drive (retained input first, then one OS read), so bytes the peer sent before its FIN are still dispatched and the read that returns EOF ends the connection as `PeerClosed`; a retained frame is still written on writable readiness, also with `POLLHUP`, and hang-up without writable readiness does nothing. A half-closed peer that never reaches EOF or never accepts output stays bounded by the frame, P6-D-001 connection, and ceremony deadlines; no hang-up timer exists. For the listener, `POLLERR`/`POLLHUP`/`POLLNVAL` still drop it with no accept. One `on_writable` or one `on_readable`, never both and never looped. WouldBlock/Interrupted (socket or accept) do no work and are retried only by a later drive; an interrupted `WSAPoll` makes no progress; any other `WSAPoll` failure fails the loop closed (no busy-poll fallback).
- **Fairness.** Every existing connection is served (at most once) before the one accept, so a continuously readable listener cannot starve established connections, and no connection can drain several frames or writes while others wait.
- **Accept admission.** Right after the OS accept, before anything else touches the socket, `AcceptPermit::begin` (refused: the socket is dropped, nothing exists, nothing is charged), then `WindowsTcpConnection::from_accepted`, whose activation enforces the live cap of 16 (the 17th socket is dropped with no session, host, or protocol state). The loop holds at most one permit at a time, a stronger implementation bound than the unchanged authority maximum of 4; the OS listener backlog stays unclaimed. The peer address returned by `accept` is dropped unread.
- **Failure scope.** EOF, socket errors, error or invalid-handle readiness, transport or routing failures, and abandoned partial frames remove only their connection. A listener accept error or error, hang-up, or invalid-handle readiness drops only the listener (live connections continue; nothing rebinds). `OwnershipUncertain` anywhere (accept admission, a connection's sweep, I/O, local action, or close) or a failed `WSAPoll` fails the whole hosting context closed: listener dropped, every connection's close attempted, nothing admitted again, uncertain capacity held as the existing teardown leaves it.
- **Connection references and local actions.** A crate-private opaque `ConnectionRef` wraps the connection's never-reissued Router `SessionHandle`; it is not an index, socket, address, peer identity, authentication, trust, or authorization, and a reference kept after its connection closed never names a later one in the same storage. The loop mirrors every adapter local action (`start_initiator` on an existing connection only, authorization, exposure, presentation, MATCH, own MAC, REJECT, CANCEL, INITIATOR_FINISH) plus `close_connection`; it locates exactly one connection and the adapter/host `RunRef` checks stay authoritative, so a `RunRef` of another connection is refused, never rerouted. `Refused::WritePending` is returned as is: nothing is queued or retried.
- **Shutdown, drop, restart.** `close()` drops the listener and attempts every connection's close even after an uncertain one; drop uses the adapters' RAII teardown and never panics. The loop is a hosting layer, not the authority: closing, dropping, or replacing it (a frontend or listener restart) releases no ownership lease and resets no opportunity budget, guard, START limiter, or pending control; a new loop over the same Router gets fresh sessions while old `ConnectionRef`s and `RunRef`s stay stale.
- **Resume hook.** `recheck_after_resume()` is an explicit crate-private hook trusted outer code may call after an OS resume notification: one deadline sweep and nothing else (no socket I/O, no accept), against the existing monotonic clocks, where an unusable or backwards clock fails closed as always. Subscribing to OS power notifications is not implemented.

Tests drive the loop with a scripted listener and scripted readiness (`POLL*` results computed from the scripted sockets, overridable for error flags, with time passing inside the wait) over the adapter's scripted sockets and hand clocks, plus real Windows loopback tests (`127.0.0.1:0` bound by the test, never policy) over real `WSAPoll`: one accept per drive from a queued backlog, a real START/ACCEPT, the 17th real connection refused with the other 16 open, a peer hang-up ending only its connection, at EOF (`PeerClosed`), and a complete ceremony with the loop as Initiator (every loop-side transition a drive, every loop-side action through the loop), whose result appears only in the drive that completes the final-ACK write, connections staying live until an explicit close gives the peer EOF. Scripted tests cover the bounds and the source-level absence of bind/connect/address/thread use, the one-wait/one-accept bound up to 17 sockets, both accept refusals charging nothing, uncertain accept admission and uncertain connections failing the loop closed, listener and connection error readiness, the P6-D-003 graceful hang-up regressions (`graceful_hang_up`: the readiness precedence matrix, retained input and pending output under hang-up, EOF, deadline bounds, hard failure over retained input, the final ACK with hang-up, and real close and `shutdown(Send)` cases), connection-local endings, accept flooding versus an established partial write, one operation per connection per drive (including retained input with no readiness), interrupted and failed waits, deadlines with no readiness, deadline expiry during the wait resolved before any I/O, the resume recheck (pre-SAS, post-SAS with timeout CANCEL, partial frame) and unusable clocks after resume, stale and cross-connection references, local actions, shutdown with uncertainty, drop, loop restart preserving budget, START limiter, and registration, and final-ACK expiry before writing (with 16 sibling routes) at offset zero and after a partial write. Mutating the adapter to drop the exact owner check, or the loop to drain the accept queue, name connections by storage slot, write before the post-wait sweep, reset authority state on restart, or write twice per drive, each fails these tests.

## Internal P3 cryptographic foundation

The private `crypto` module pins `vodozemac` to 0.11.0 with default features disabled. It owns single-use ephemeral SAS state, contributory DH validation, the exact responder commitment, transcript identity, and SAS context/info encoding. It exposes none of these operations to applications. The internal state machine releases keys only after the existing authorization and atomic reservation checks. Its only MAC uses are the BOOTSTRAP_MAC approval exchange, the three completion messages, and authenticated CANCEL, through vodozemac's own `calculate_mac`/`verify_mac`; it implements no transport.

The 2026-09-30 Cargo.lock resolves `rand 0.10.3`, `rand_core 0.10.1`, `getrandom 0.4.3`, `x25519-dalek 3.0.0`, `curve25519-dalek 5.0.0`, `hkdf 0.13.0`, `hmac 0.13.0`, `sha2 0.11.0` (vodozemac; the core also uses `sha2 0.10.9`), and `zeroize 1.9.0`. The pinned vodozemac manifest disables default features but explicitly enables `x25519-dalek/zeroize`. The resolved X25519 source zeroizes `EphemeralSecret` and `SharedSecret` on drop. This does not establish zeroization of Rand's internal ThreadRng state, derived SAS bytes, HKDF/HMAC temporaries, encoded context or digest buffers, compiler/runtime copies, swap, or crash dumps.

The core also depends directly on that same resolved `getrandom 0.4.3` (no default features, no new lockfile packages, no second RNG stack) solely for honest Initiator request-ID generation; the ID is public routing data, not secret material, and protocol authentication does not depend on its unpredictability. For Windows 10 and later, resolved `getrandom 0.4.3` uses the system `ProcessPrng` API from `bcryptprimitives.dll`. Rand's `ThreadRng` seeds and periodically reseeds from `SysRng`; an entropy failure can panic through `Sas::new()` because that constructor is infallible. A local result exists only after the complete verified finish handshake, so such a panic cannot become pairing success. Rand documents no automatic reseed after `fork`; forked processes, VM snapshots, and restored RNG state are unsupported for claiming fresh ephemeral keys unless an independently verified fresh-entropy mechanism is established. No such mechanism is implemented here.

The deterministic vector test compares the complete commitment input/digest, transcript bytes/identity, SAS context frame, and exact info string directly against the checked-in JSON. vodozemac 0.11.0 has no public fixed-private-key SAS constructor, so that fixture's six fixed-secret SAS bytes and decimal rendering cannot be reproduced through the API; a separate live test verifies fresh vodozemac DH and equal SAS outputs.

## Ownership guarantees

**Registration versus process session (P6, decision [P6-D-002](../docs/p6-remediation/decisions.md#p6-d-002--f-003-owner-session-policy), remediating [P5-F-003](../docs/p5-security-review/findings.md#p5-f-003)).** A `TrustedAuthority` registration means only that this process currently holds the authority's OS lease; registrations may end and start again inside one process. The ten-opportunity budget, the START limiter, and the limiter clock belong to the process session: the process-wide registry keeps one entry per canonical identity this process has successfully owned, created at the first successful acquisition and kept until the process exits. `release()` or the final drop releases the lease and leaves the entry, so registering the same scope again reacquires the lease (exclusively, as before) and continues the same accounting; while one registration is active, another gets `AlreadyRegistered`. A failed acquisition changes nothing, and a failed first acquisition creates no entry. An uncertain release, poisoned accounting, or runtime resources left held after the last handle disables that authority in this process with `OwnershipUncertain` rather than resetting anything. Only a new process that safely acquires ownership starts fresh; there is no reset API. Entries are never evicted, because eviction would be a reset; they come only from trusted local scopes, so a peer cannot create them.

Windows obtains the current process token's authenticated `TokenUser` SID and profile root from Windows security APIs. The lock file lives under that profile's `AppData\Local\sas-pairing\authority-locks`; `%LOCALAPPDATA%` and caller-provided identity values are not used. Its name is SHA-256 of a length-prefixed SID followed by the existing canonical identity bytes, `sas-pairing-authority-v1 || u32be(scope_length) || scope`. The canonical identity encoding and the value returned by `canonical_identity()` are unchanged. Each path component is checked as a real directory (not a reparse point), and the opened lock handle is checked for a regular, non-reparse file. `FILE_FLAG_OPEN_REPARSE_POINT` protects the final path component. Sharing allows read/write but denies delete/rename while open. Access, path, token, and unexpected OS errors fail closed.

The resulting scope is:

- Multiple processes and logon sessions for one Windows account: the process-token SID and Windows profile API produce the same ownership key and lock location. Manual verification on 2026-09-30 exercised exclusive ownership across two different Windows process session IDs for the same account and canonical authority identity (details below). This verifies the tested Windows configuration, not cross-machine coordination, same-profile attacker resistance, or a formal security property.
- Different Windows accounts: the SID produces independent lock namespaces. This is supported only for genuinely independent pairing capabilities and state; shared cross-account capabilities are unsupported.
- Separate machines: no coordination. Copied identities and restored state across machines remain outside the approved policy guarantee.

Do not reinterpret a Windows logon session as a Windows user account. The trusted local registry identifies the underlying pairing capability, supplies a stable logical scope across restarts, and must reject aliases and conflicting mappings. The core cannot determine whether two app-level scopes name the same capability. Do not pass a scope from network-controlled input. See [decision 0003](../docs/decisions/0003-windows-account-scoped-ownership.md).

`LockFileEx` locks the opened file object, conflicts with exclusive byte-range locks from other processes, and is released when the handle closes or the process terminates. `FILE_FLAG_OPEN_REPARSE_POINT` alone would not secure parent directories; the explicit path-component checks address existing parent junctions and reparse points. They do not defend against an attacker controlling the same user profile while the path is being checked. No protection against that attacker or an administrator/SYSTEM boundary is claimed. Lock files remain empty; no counters are persisted. See Microsoft's [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex) and [CreateFile sharing and reparse-point flags](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) documentation.

## Authorization boundary

The trusted application/configuration boundary keeps `TrustedAuthority`. Only it can issue exact-ceremony, one-shot authorization after obtaining genuine local consent; the Rust core cannot prove human interaction. Give network/protocol execution only `CeremonyExecutor`, which can begin, reserve and terminate a ceremony but has no authorization method. A compile-fail doctest checks this API boundary. The application integration must not expose `TrustedAuthority` to protocol handlers or derive authorization from network input.

Authorization is ceremony-specific and consumed by every valid reservation attempt. Stale, missing, cross-ceremony and terminal authorization cannot reserve. The executor atomically acquires the single shared guard and consumes the opportunity. Reservation is never refunded after failure or termination. Initiator and Responder use the same guard and budget.

## Native ABI (P7, in progress)

The `native-abi` feature compiles the crate-private `abi` module, the language-neutral C boundary for the future Dart and .NET wrappers, into the same crate, so the wrappers stay callers of this one implementation. The crate builds `rlib` and `cdylib`; ABI symbols are exported only with the feature. P7.1 provides the foundation only: `sas_pairing_abi_version` (ABI version `1`, distinct from the profile version), `sas_pairing_runtime_create`, and `sas_pairing_runtime_destroy`, with one runtime per process, opaque never-reused `uint64_t` handles, and frozen `int32_t` status codes. No pairing operation is exposed yet, and runtime creation registers no authority. Every export runs inside one central panic-containment boundary: a caught panic permanently marks the process's native ABI state fatal, the panic payload's destructor never runs, and `SAS_PAIRING_FATAL` is returned (P6-D-004, [P7-D-001](../docs/p7-native-abi/decisions.md#p7-d-001--native-runtime-handle-and-fatal-containment-unit)). The release profile pins `panic = "unwind"`, and the module refuses to compile under `panic = "abort"`. Contract: [ABI contract](../docs/p7-native-abi/abi-contract.md) and [`include/sas_pairing.h`](include/sas_pairing.h).

### Cross-session verification (manual; completed 2026-09-30)

The owner accepted account-scoped Windows authority in [decision 0003](../docs/decisions/0003-windows-account-scoped-ownership.md). The owner manually ran the test-only `--file-control <directory>` probe on Windows 11 Pro build 26200 under one authenticated account using Task Scheduler with the same account and passwordless S4U configuration. Two different actual process session IDs, `0` and `1`, were observed. In every comparison, account identity (SID) and canonical authority identity matched.

- Session 0 acquired ownership; the session 1 contender was denied with `OwnershipUnavailable`, recorded `BLOCKED_BEFORE_EXECUTOR`, and exited 1. The owner then reported release.
- After release, a session 1 process acquired ownership. While it owned the authority, a session 0 contender was denied with `OwnershipUnavailable` before executor/reservation exposure.
- The session 1 owner then reported final release. The owner also confirmed that the scheduled process could acquire ownership with no competing owner, distinguishing contention from a Task Scheduler access/configuration failure.

These are owner-supplied manual observations, not automated CI results, and were not executed by Codex. They verify the tested same-account, same-authority contention and replacement behavior across distinct Windows process sessions. They do not establish cross-machine coordination, resistance to an attacker controlling the same profile, administrator/SYSTEM isolation, cryptographic security, or a formal proof/audit. This ownership verification itself exercised no SAS ceremony. The probe writes a PID-named log and readiness marker, retains ownership until a `release` file appears, and self-releases after five minutes. Its log includes the process token SID, actual Windows session ID, scope, canonical identity bytes, and ownership outcome. A denied contender records that it was blocked before an executor (and therefore could not reserve an exposure).

Task Scheduler's S4U logon type avoids storing a password and uses the named account. A reproduction must still verify the actual session IDs and local profile-lock access on its target Windows host. Microsoft documents S4U as not having network or encrypted-file access; the probe uses a local profile path. See [Task Scheduler logon types](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-logontype-principaltype-element). Do not use SYSTEM or another account.

On the owner’s Windows host:

1. Build `ownership_probe.exe` with `cargo build --manifest-path core/Cargo.toml --bin ownership_probe`. In PowerShell, set `$dir = Join-Path $env:TEMP 'sas-p4-cross-session'` and `$probe = (Resolve-Path 'core\target\debug\ownership_probe.exe').Path`; remove old files from `$dir`.
2. In the normal interactive session, run `& $probe sas-p4-cross-session-check --file-control $dir` in a dedicated PowerShell window and leave it running. Its `<PID>.ready` file marks acquisition; the process PID is in the matching `<PID>.log` filename.
3. In Task Scheduler, create a task whose principal is the same account SID shown by `whoami /user`, select **Run whether user is logged on or not**, and enable **Do not store password** (S4U). Configure its action to run the same executable with arguments `sas-p4-cross-session-check --file-control <directory>`. Set the task execution limit to six minutes (the probe self-releases after five). If Windows requests a credential, enter it locally; do not send it to anyone. Start the task.
4. Read the task process’s `<PID>.log`, then verify the two reported SIDs match and the processes have different actual session IDs; session `0` is not mandatory. The scheduled contender must report `ownership=DENIED` and `reservation=BLOCKED_BEFORE_EXECUTOR`, and exit with code 1; compare `canonical_identity_hex` byte-for-byte. Record Task Scheduler's result and ensure no second process was launched under another principal.
5. Create the directory's `release` file. Confirm the interactive owner reports `ownership=RELEASED`; remove the `release` file, rerun the same task, and require `ownership=ACQUIRED`. Then create `release` again. For the reverse direction, remove `release`, run the task first, and start the identical probe interactively; require its denial before releasing the task-owned process.

For each run, record `Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsBuildNumber`, task name/logon mode/result, both PIDs/SIDs/session IDs, canonical identity, both ownership outcomes, the reservation denial, and release/replacement behavior. Repeat with the scheduled task as initial owner where practical. If Task Scheduler does not produce a different session ID for the same SID, use Windows Server with Remote Desktop Services configured for two same-account sessions and rerun this procedure. This ownership procedure does not exercise ceremony behavior.
